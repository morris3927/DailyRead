# Agent Memory — 2026-05-19

## 1. Hierarchical Long-Term Semantic Memory (HLTM) for LinkedIn's Hiring Agent

- **arXiv**: 2604.26197
- **Link**: https://arxiv.org/abs/2604.26197
- **類型**: arXiv (cs.IR, cs.LG)

### 這篇在說什麼

這篇要解決的問題是：在工業級 LLM agent 產品中，如何建立一個可擴展、低延遲、隱私安全、跨領域泛化、可觀測的長期語意記憶系統？LinkedIn 的 Hiring Assistant（LiHA）是一個已部署的招募 agent，需要從招募者的歷史行為資料中提取個人化偏好、結構化儲存、並在即時對話中低延遲檢索。這不是學術玩具——每天要處理大量的結構化和非結構化資料、嚴格的 GDPR 合規要求、和毫秒級的回應延遲。

這填補的洞是：agent memory 領域的既有工作（MemGPT、MemoryBank、GraphRAG 等）大多在實驗室環境下驗證，缺乏面對工業級五大挑戰（可擴展性、低延遲檢索、隱私隔離、跨領域泛化、可觀測性）的系統性解決方案。HLTM 是第一個在生產環境中部署的 hierarchical memory 框架，而且有量化評估。

### 主要貢獻

1. **HLTM 框架本身**：將文字資料組織成 schema-aligned memory tree，在多個粒度層級捕捉語意知識。Tree 結構支援大規模平行 ingestion、lossless incremental update、和低延遲檢索。

2. **五大工業挑戰的系統性解決方案**：
   - Scalability：tree 結構支援 massively parallel ingestion
   - Low-latency retrieval：多粒度表示讓 serving time 只需要 lean retrieval
   - Privacy-aware storage：memory hierarchy 跟 business scope（seat、project）對齊，嚴格隔離
   - Adaptability：自動 query pattern 分析 + adaptive k 選擇，不需手工商業規則
   - Observability：保持對 source of truth 的 reference，支持 debug、governance、和一致性更新

3. **量化評估**：answer correctness 和 retrieval F1 都提升超過 10%，同時推進了 query latency 和 indexing latency 之間的 Pareto frontier。

4. **已部署在 LinkedIn Hiring Assistant**：不是 prototype，是 production system。

### 方法 / pipeline

HLTM 的架構：

**Memory tree**：將文字資料組織成多層樹狀結構，每個節點是不同粒度的語意摘要。Root 是最粗粒度的全域知識，leaf 是最細粒度的具體事實。Schema-aligned 意味著樹的結構跟業務 schema（recruiter、job、candidate 等）對齊。

**Ingestion pipeline**：
1. 從多種來源（結構化資料庫、非結構化文字、互動 log）提取信號
2. LLM-based extraction 和 summarization 產生多粒度記憶節點
3. Massively parallel ingestion：每個 recruiter 的記憶可以獨立平行處理
4. Lossless incremental update：當 source of truth 更新時，只需更新受影響的子樹

**Retrieval**：
- Serving time：lean retrieval path，只取需要的粒度層級
- Adaptive k 選擇：根據 query pattern 自動調整檢索的節點數量和粒度

**Privacy**：
- Memory hierarchy 跟 business scope 對齊（seat-level、project-level）
- 嚴格的 tenant isolation
- 支援 GDPR deletion：刪除某個 recruiter 的所有記憶只需移除對應子樹

**Adaptability**：
- 自動 query pattern 分析：學習哪些 query pattern 最常見
- Adaptive k：不同 pattern 可能需要不同的檢索深度和廣度
- 跨領域泛化：同一框架可以服務不同的 LinkedIn 產品

### 實驗設計

Evaluation 在 LinkedIn's Hiring Assistant 上進行：

主要指標：
- Answer correctness（回答正確性）
- Retrieval F1（檢索準確率）
- Query latency
- Indexing latency

主要結果：
- HLTM 比 baseline（沒有 HLTM 的 LiHA）在 answer correctness 和 retrieval F1 上提升超過 10%
- 顯著推進了 query latency 和 indexing latency 之間的 Pareto frontier（同時降低兩者或其中一者降低而另一者不變）

從 HTML 前段能確認的是框架設計和主要結果的趨勢；詳細的 ablation（不同樹深度的比較、adaptive k 的效果、privacy isolation 的具體實作）需要看全文的 Table 和 Figure。

Disclaimer：論文本身提到 "Results may vary in production environments or with different datasets"。

### かに讀後判斷

這篇在 agent memory 領域的重要性在於它是第一個在生產環境中部署的 hierarchical memory 框架，而且有量化評估。跟前幾天讀的 Multi-Layered Memory Framework（2603.29194）和 H-MEM（2507.22925）比起來，HLTM 更偏工程系統面——它的貢獻不是新的 memory 架構概念，而是如何在工業約束下（GDPR、毫秒級延遲、每天處理海量資料）實際部署和維護一個 hierarchical memory。

跟 H-MEM 的 positional index encoding 比起來，HLTM 用的是更直觀的 schema-aligned tree，但加了 adaptive k 選擇和隱私對齊。兩者互補：H-MEM 強調 index-based routing 取代 exhaustive search，HLTM 強調生產約束下的系統設計。

值得深讀的部分：
- Memory tree 的具體結構——schema-aligned 是怎麼對齊的？
- Adaptive k 選擇的演算法——如何根據 query pattern 自動調整？
- Privacy isolation 的實作細節——如何確保跨 tenant 不洩漏？
- Pareto frontier 的具體數據——latency 的 trade-off 曲線長什麼樣？

這篇因為是已部署的生產系統，對 Morris 在思考 agent memory 的工程實作面有直接的參考價值。
