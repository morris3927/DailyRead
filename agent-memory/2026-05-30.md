# Agent Memory — 2026-05-30

## 1. MemGym: A Long-Horizon Memory Environment for LLM Agents

- **arXiv**: 2605.20833
- **Link**: https://arxiv.org/abs/2605.20833
- **Authors**: Wujiang Xu, Yu Wang, Kai Mei, Kaiqu Liang, Zhenting Wang, Mingyu Jin, Han Zhang, Shi-Xiong Zhang, Wenyue Hua, Sambit Sahu, Dimitris N. Metaxas (Rutgers, Capital One, Princeton, Microsoft Research)

### 這篇在說什麼

現有的 agent memory benchmark（LoCoMo、LongMemEval、MemoryAgentBench、MemoryBench）主要評估多輪對話中的個人資訊記憶保留，忽略了 agent 在長期執行過程中動態記憶形成的問題。MemGym 認為有三個核心障礙：(i) 現有的 agent benchmark 只報告最終任務成功率，把 memory 失敗和 reasoning / retrieval / tool-use 錯誤混在一起（entangled metrics）；(ii) 表面上看起來 memory-intensive 的設定其實不需要真正的 memory 管理——事實可以從 repo 重新找到或從 pretraining 恢復（illusory memory pressure）；(iii) 在 SWE-Gym 上跑一個 episode 就要 Docker + 數十步執行，memory 設計迭代在學術預算下不可行（evaluation cost）。

MemGym 補的洞是：給出一個統一的 memory evaluation interface，讓你在不同 agentic regime 下測試 memory 策略，而且分數反映的是 memory 本身的效果，不是推理或工具使用的混淆。

### 主要貢獻

1. **Memory-isolated scoring**：MemGym 用 paired baseline-vs-memory 比較，固定 reasoner，只改 memory module。分數差值（memory gain）直接反映 memory 效果，不受推理能力或工具使用能力的干擾。這在之前是沒有的——SWE-Gym、τ²-bench、WebArena 都只報告 end-task success rate。

2. **五軌統一 interface**：MemGym 把 τ²-bench（tool-use dialogue）、SWE-Gym（coding）、WebArena-Infinity（computer use）、加上自建的 MemGym-DR（deep research search）和 MemGym-CodeQA（coding QA）統一到一個 shared memory contract（BaseMemoryEnvironment, BaseAgent, BaseMemoryManager, BaseRunner）下。加新環境或新策略是 one-file change。

3. **Controllable synthetic pipelines**：MemGym-CodeQA 和 MemGym-DR 的長度可控，每個階段都有 ablation verification，確保測的是 memory channel（不是 parametric leakage 或 distractor recall）。和下游 coding / search 場景緊密對齊。

4. **MemRM reward model**：Qwen3-1.7B 用 QLoRA fine-tune 的 lightweight reward model，AUROC 0.985 在 SWE-Gym IID split 上，把 Docker rollout 替換成 sub-second scalar classifier call，讓 coding 環境的 memory 評估在學術預算下可行。

### 方法 / pipeline

MemGym 的核心是一個 per-step cycle：`env.reset() → memory_manager.manage_context → agent.act → env.step`。Memory manager 包裝送給 policy LLM 的 prompt，回傳 `FilteredContext` 加上 `condensation_event`（summary、forgotten-message indices、compression metadata）。

七個 memory family 加上一個 no-memory None control，在 1717 個 (track, strategy) cells 上評估。Memory operations 用 `manage_context` contract，透過 `PipelineMemory` wrapper 組合 per-stage statistics。

Replay-and-fork harness：多個 runtime backend（Docker、Singularity、BubblewrapBackend、SwerexDockerBackend、local tempfile），加上 WebArena 的 port allocation 和 idle-pool reuse。Replay-and-fork 協議用記錄的 tool actions 重建 repository state，只在 compaction-triggering steps 重新 query policy LLM，達到 10× policy call savings。

MemRM training：18.6K (context, action, label) triples，從三個來源聚合 safe/harmful labels：(i) episode-level task resolution、(ii) counterfactual replay、(iii) LLM-as-judge。Train/eval split 按 repository group 而非 instance group，消除 same-repo leakage。

### 實驗設計

- **Five evaluation tracks**: τ²-bench, SWE-Gym, WebArena-Infinity, MemGym-DR, MemGym-CodeQA
- **Memory strategies**: passthrough, LLM summarizing, structured per-environment summary, retrieval-style, observation masking, 等 7 families + None control
- **Memory-isolated scoring**: 固定 reasoner，paired comparison，memory gain = memory score - baseline score
- **MemRM**: AUROC 0.985 on SWE-Gym IID split
- **已讀來源**: arXiv HTML 全文已讀到 §3.3。Section 4 實驗結果和附錄部分從 abstract 和 HTML 前段確認到核心方法論，完整實驗數據表需要進一步確認。

### かに讀後判斷

MemGym 是目前 agent memory 領域最完整的 evaluation framework。之前 DailyRead 收錄的 LoCoMo、LongMemEval、A-Mem、MemLineage、GroupMemBench 等都只測對話場景的 memory，MemGym 第一次把 coding、web navigation、tool-use dialogue、deep research search 放在同一個 memory interface 下測試，而且用 memory-isolated scoring 解決了「memory 效果和 reasoning 效果混在一起」這個根本問題。

和前幾天收錄的 MemLineage（2605.14421）比起來，MemLineage 解決的是 memory security（provenance enforcement），MemGym 解決的是 memory evaluation（怎麼測 memory 到底有沒有用）。兩者是互補的。

值得深讀的部分：§3.2 的 unified memory infrastructure 設計細節、§3.4 的 synthetic pipeline construction（特別是 ablation verification 怎麼做）、§4 的完整實驗結果（特別是各 memory family 在不同 regime 下的表現差異）。如果你在思考怎麼評估自己 agent 的 memory system，MemGym 的 memory-isolated scoring 方法論是最值得參考的。

## 2. Storage Is Not Memory: A Retrieval-Centered Architecture for Agent Recall (True Memory)

- **arXiv**: 2605.04897
- **Link**: https://arxiv.org/abs/2605.04897
- **Authors**: Joshua Adler (Sauron Labs)
- **Type**: Technical report

### 這篇在說什麼

這篇的核心論點是一句話：「Extraction at ingestion is the wrong primitive for agent memory」。所有主流的 agent memory 產品（Mem0、Zep、Graphiti、Supermemory、EverMemOS）都遵循同一個模式：在 ingestion 時用 LLM 把對話內容解析成結構化表示（atomic facts、entity nodes、knowledge graph、hierarchical summary），存進 vector DB 或 graph store，query 時做 similarity search。問題是：ingestion 時你還不知道 query 是什麼，被 extraction 丟掉的內容在 retrieval 時不可恢復。

True Memory 把整個系統的重心從 storage schema 移到 retrieval pipeline：事件在 ingestion 時保留 verbatim，用 encoding gate（novelty / salience / prediction-error 三信號）做過濾，higher-order structure（summaries、entity profiles、consolidation）是 post-ingestion 或 query-time 才計算的。整個系統跑在單一 SQLite 檔案上，不需要 vector DB、graph store、GPU。

### 主要貢獻

1. **Architectural reframing**：把 agent memory 從 storage schema 重構為 retrieval architecture。Ingestion、consolidation、query-time ranking 是同一個 pipeline 的三個階段，不是被 database boundary 分開的獨立模組。

2. **Encoding gate**：三信號 gated ingestion——novelty（用 gzip compression cost 計算，AUC 0.788 vs cosine baseline 0.484）、salience（混合 scorer：短訊息用 rule-based speech-act classifier，長訊息用 L3 salience scorer）、prediction error（embedding pair-difference scoring，AUC 0.730 standalone，三信號組合 AUC 0.816）。兩個信號（novelty 和 prediction error）查詢的是同一個 stored message substrate，ingestion 和 retrieval 共享 representation。

3. **Empirical results**：LoCoMo 93.0%（3-run mean），對比 Mem0 61.4%、Supermemory 65.4%、Zep ~71%、EverMemOS 94.5%（但 EverMemOS 用 GPU-served embedder + Neo4j graph store）。LongMemEval 87.8%，BEAM-1M 76.6%（超過之前 Hindsight 的 73.9%）。56-configuration ablation 只有 1.3 percentage point spread。

4. **Retrieval-as-bottleneck diagnostic**：在 357 個 LoCoMo 錯誤回答中，把完整對話給同一個 answer model 後恢復了 92%，定位瓶頸在 retrieval pipeline 而不是 storage layer。

### 方法 / pipeline

True Memory 是六層架構（L0–L5），三個時間分離的階段：

**Ingestion phase:**
- Stage 1: Encoding Gate — 用 novelty ($n_t$)、salience ($s_t$)、prediction error ($\pi_t$) 三信號決定是否 admit 事件。Novelty 用 gzip compression cost 相對於 stored neighborhood 計算；salience 用 hybrid scorer（短訊息用 rule-based，長訊息用 L3 scorer）；prediction error 用 embedding pair-difference。Gate formula: $(\lambda_n \cdot n_t + \lambda_s \cdot s_t + \lambda_\pi \cdot \pi_t) / (\lambda_n + \lambda_s + \lambda_\pi) \geq \tau + \Delta_c$。權重 $(0.25, 0.20, 0.30, \tau=0.30)$ 是 production defaults。
- Stage 2: L1 Writer — admitted event 寫入 messages table，同步更新 FTS5 lexical index 和 sqlite-vec dense index。

**Post-ingestion phase (batch):**
- Stage 3: L4 Consolidator — 從 L1 event substrate 更新 consolidation artifacts（summaries、entity profiles）。
- Stage 4: L5 Predictive Coder — 更新 surprise index。
- Stage 5: L0 Personality Engram — 更新 speaker profile。

**Query-time:**
- Stage 6: L1 lexical retrieval (FTS5)
- Stage 7: L2 dense retrieval (sqlite-vec)
- Stage 8: Reciprocal Rank Fusion 融合 L1 + L2
- Stage 9: L3 salience reweighter（conditional on L0 speaker engram）
- Stage 10: Cross-encoder reranker → top-k → answer model

整個系統是單一 SQLite 檔案，不需要外部 database、vector index、graph store 或 GPU。

### 實驗設計

- **Benchmarks**: LoCoMo (1,540 questions, 10 multi-session conversations)、LongMemEval (500 questions)、BEAM-1M (700 questions at 1M token scale)
- **Baselines**: Mem0 (61.4%), Supermemory (65.4%), Zep (~71%), EverMemOS (94.5% on LoCoMo with GPU + Neo4j)
- **True Memory Pro**: LoCoMo 93.0%, LongMemEval 87.8%, BEAM-1M 76.6%
- **Ablation**: 56-configuration sweep，top-performing subfamily 只有 1.3pp spread
- **Diagnostic**: 357 LoCoMo errors → 92% recoverable with full conversation → bottleneck is retrieval, not storage
- **已讀來源**: arXiv HTML 全文已讀到 §4 pipeline stages 完整細節。§5–§6 實驗和 ablation 需要進一步確認。

### かに讀後判斷

True Memory 是 agent memory 架構方面的重要進展。核心論點「ingestion-time extraction 是錯誤的 primitive」非常有道理——你不知道未來的 query 是什麼，所以不應該在 ingestion 時做不可逆的 extraction。Encoding gate 的三信號設計（novelty 用 gzip、salience 用 hybrid scorer、prediction error 用 embedding pair-difference）在工程上很優雅，特別是 novelty signal 用 gzip 而不是 cosine，因為在對話資料中 cosine 是 anti-correlated with novelty（noise like "ok" 是語意遙遠的，重要更新是語意相近的）。

和前幾天收錄的 MemLineage（provenance enforcement）、MemGym（evaluation framework）比起來，True Memory 解決的是 architecture 層面的問題——怎麼設計 memory system 的 data flow。三篇剛好覆蓋三個不同面向：architecture（True Memory）、security（MemLineage）、evaluation（MemGym）。

值得深讀的部分：§4 pipeline stages 的完整十步設計、§5 encoding gate 的 120-variant 和 200-variant sweep 細節、§6 實驗結果的 per-category breakdown。如果你在設計 agent memory system，True Memory 的 encoding gate + verbatim preservation + multi-stage retrieval pipeline 是最值得參考的架構。

## 3. MemIR: Mitigating Provenance-Role Collapse in Long-Term Agents via Typed Memory Representation

- **arXiv**: 2605.25869
- **Link**: https://arxiv.org/abs/2605.25869
- **Authors**: Zhengda Jin, Bingbing Wang, Jing Li, Ruifeng Xu, Min Zhang (HIT Shenzhen, PolyU HK)

### 這篇在說什麼

現有的 agent memory 架構把歷史互動存成 unstructured flat text。這篇指出這種存法會導致 provenance-role collapse——agent 無法區分「觀察到的證據」和「推論出的結論」，無法追蹤資訊的來源和時間脈絡，也無法正確聚合分散在不同時間點的同一個實體的資訊。例如回答「Joanna 寫了幾個劇本？」需要把分散在不同對話中的三個劇本資訊聚合，但 flat text retrieval 缺乏 coreference links、source boundaries 和 epistemic typing，會把不同時間點的同一個 referent 當成不同的物件。

### 主要貢獻

1. **Provenance-role collapse 的形式化定義**：明確指出 flat text memory 導致的 source-monitoring errors，從認知科學的 source monitoring theory (Johnson et al., 1993) 出發。

2. **Typed Memory Intermediate Representation (MemIR)**：把 memory 寫成 grounded atoms，分離七種類型：page（上下文邊界）、span（verbatim evidence）、handle（referential access）、time（temporal anchoring）、pivot（semantic access）、claim（truth-bearing assertions）、retrieval views（cross-atom access relations）。其中只有 claim atoms 可以作為 truth-bearing，其他類型只能透過 associated claim 進入事實層。

3. **Multi-route atomic projection + provenance-scoped utilization**：sparse (BM25) + dense (BGE-M3) 雙路檢索，透過 type-constrained projection 把 heterogeneous hits 映射到 claim-centered candidate bundles，再用 cross-encoder reranker 和 LLM selector 組成 normalized fact interface。

### 方法 / pipeline

MemIR 三階段：

1. **Systematic Writing of Memory Atoms** ($\Phi: \mathcal{C} \to \mathcal{M}$)：把對話歷史編譯成 typed atoms。Support constraint: $\emptyset \neq \text{sup}(x) \subseteq \mathcal{S}, x \notin \mathcal{P}$，每個 extracted cue 或 generated claim 都必須有 span evidence 作為支撐。

2. **Multi-Route Atomic Projection**：BM25 over retrieval views + BGE-M3 dense retrieval → RRF fusion → type-constrained projection 把 heterogeneous hits 映射到 claim atoms → 形成 candidate bundles $\langle a, \rho_a, \mathcal{E}_a \rangle$。

3. **Provenance-Scoped Utilization**：cross-encoder reranker + LLM selector → normalized fact interface $F_q = \{f_1, \ldots, f_m\}$，每個 fact record 包含 claim text、provenance closure、temporal cues、functional role。如果 evidence 不足，model 被指示回傳 "insufficient evidence" 而非 hallucinate。

### 實驗設計

- **Benchmarks**: LoCoMo (1,540 questions, 4 answerable categories) 和 BEAM-100K (20 dialogues, 100K-token histories, 400 questions, 10 task categories)
- **Models**: GPT-4.1-mini 和 GPT-4.1 作為 backbone
- **Baselines**: LoCoMo baseline、ReadAgent、MemGPT、A-Mem、Mem0、Zep 等
- **已讀來源**: arXiv HTML 全文已讀到 §3 MemIR method。§4 實驗結果從 HTML 前段確認到 main results table 的部分數據，完整實驗細節和 ablation 需要進一步確認。

### かに讀後判斷

MemIR 和今天收錄的 True Memory 是同一個問題的兩個解法：都是在說「flat text memory 不夠」，但從不同角度切入。True Memory 從 retrieval pipeline 角度切入（保留 verbatim、multi-stage retrieval、encoding gate），MemIR 從 representation type 角度切入（typed atoms、provenance constraint、claim-centered bundles）。兩者互補而非競爭。

MemIR 的 provenance-role collapse 概念對 Morris 關注的 agent memory 安全性很重要——如果 agent 無法區分「觀察到的」和「推論出的」，那在 MCFA 類型的攻擊下更容易被 hijack。和 MemLineage 的 cryptographic provenance enforcement 比起來，MemIR 用的是 structural constraint 而非 cryptographic，更輕量但不保證 tamper-proof。

值得深讀的部分：§3 的 complete MemIR pipeline 定義、LoCoMo 和 BEAM-100K 上的 per-category breakdown、特別是 source tracking 和 temporal grounding 的實驗結果。
