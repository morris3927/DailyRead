# Agent Memory — 2026-06-02

## 1. AtomMem: Learnable Dynamic Agentic Memory with Atomic Memory Operation

- **arXiv**: 2601.08323
- **Authors**: Yupeng Huo, Yaxi Lu, Zhong Zhang, Haotian Chen, Yankai Lin (Renmin University of China, Tsinghua University)
- **Venue**: arXiv preprint (v3: March 2026)
- **Link**: https://arxiv.org/abs/2601.08323
- **Code**: https://github.com/RUCBM/AtomMem

### 這篇在說什麼

AtomMem 將 agent 的記憶管理從「固定的手工設計 workflow」重新框架為「可學習的決策問題」。核心觀察是：現有的 agent memory 系統（MemGPT、MemoryBank、A-MEM 等）都使用預定義的記憶管理流程——什麼時候存、什麼時候取、什麼時候刪——都是專家寫死的規則。這造成了一個隱含的 one-size-fits-all 問題：同一套 workflow 在某些任務上有效，在另一些任務上失敗。

AtomMem 的解法是把高層記憶操作分解為 CRUD（Create / Read / Update / Delete）四個原子操作，讓 agent 在每一步透過強化學習（GRPO）自己決定要執行哪些操作。這樣記憶管理就不再是固定的流程，而是一個 task-aligned 的策略——不同任務會學到不同的記憶使用模式。

### 主要貢獻

1. **POMDP 形式化記憶管理**：將 agent memory 明確建模為 POMDP（部分可觀察馬可夫決策過程），記憶是環境的一部分，記憶操作是動作空間的一部分。這讓記憶管理可以受益於 RL 的最佳化框架。

2. **CRUD 原子操作空間**：證明 CRUD 四個操作構成一個完備（completeness）、最小（atomic minimality）、任務無關（task-agnosticness）的操作集合。任何高層記憶工具都可以分解為 CRUD 組合，但 CRUD 不能再分解。

3. **學到 task-aligned 策略**：訓練後的 AtomMem 展現出系統性的操作頻率變化——Create/Update/Delete 頻率穩定上升，Read 頻率下降並穩定在較低水準。不同任務條件下操作頻率有完全不同的趨勢，證明策略是 task-aligned 而非固定的。

4. **穩定超越靜態 workflow baselines**：在 3 個長上下文 QA benchmark（HotpotQA, 2WikiMultihopQA, Musique）和 2 個 web benchmark（GAIA, WebWalkerQA）上，AtomMem-8B 穩定超越先前靜態 workflow 方法 3–8pp。

### 方法 / pipeline

AtomMem 的完整架構：

1. **POMDP 定義**：
   - 全域狀態 s_t = (s_t^env, s_t^mem)，包含外部環境和內部記憶。
   - 動作 a_t = (a_t^env, a_t^mem)，環境動作和記憶動作聯合決策。
   - 觀察 o_t = (o_t^env, m_t^scr, M̂_t)，包含環境觀察、scratchpad（確定性檢索）和選擇性檢索結果。

2. **CRUD 操作**：
   - **Create**：新增一筆記憶到動態集合 M_t。
   - **Read**：生成文字查詢 q_t，透過語意相似度做 Top-K 檢索。不修改記憶狀態。
   - **Update**：修改現有記憶條目。
   - **Delete**：移除記憶條目。

3. **混合檢索機制**：
   - 確定性檢索（Scratchpad）：每步都檢索的特殊記憶條目，保存全局任務狀態。
   - 選擇性檢索：agent 生成文字查詢，透過語意相似度做 Top-K 檢索。

4. **GRPO 訓練**：
   - 記憶操作是模型詞彙中的結構化 token，最佳化輸出序列的似然度隱式最佳化了記憶策略。
   - 使用 task-level success 作為 reward signal，無中間 reward。
   - Group Relative Policy Optimization (GRPO) 做策略梯度更新。

5. **Macro-action 機制**：每個決策步驟可以生成一系列 CRUD 操作（a_t = {a_t^1, ..., a_t^K_t}），形成組合性的 macro-action。

### 實驗設計

- **長上下文 QA**：
  - HotpotQA, 2WikiMultihopQA, Musique
  - 訓練：200 documents (~28K tokens)，測試：800 documents (~112K tokens)
  - Multi-question setting：1–10 個問題同時處理

- **Web 搜尋**：
  - 訓練：Asearcher 開源資料集
  - 測試：GAIA, WebWalkerQA
  - 最大 40 次 web tool calls

- **Baselines**：靜態 workflow 方法（MemoryBank, MemGPT, A-MEM 等）

- **核心結果**：AtomMem-8B 在所有 5 個 benchmark 上穩定超越靜態 workflow 方法 3–8pp（同一 Qwen3-8B 骨幹下）。

- **策略分析**：
  - Create/Update/Delete 頻率穩定上升，Read 頻率下降並穩定。
  - 不同任務條件下操作頻率有顯著差異。
  - 證明學到的策略是 task-aligned 的，不是固定模式。

### かに讀後判斷

AtomMem 是 agent memory 領域的重要進展，和 05-09 讀過的 AgeMem（2601.01885）以及 05-20 讀過的 SSGM（2603.11768）形成三足鼎立：

- **AgeMem**：把 LTM/STM 管理整合進 agent policy，用 tool-based actions 讓 agent 自主決定何時存取更新。和 AtomMem 的核心思路類似（記憶管理是可學習的決策），但 AgeMem 用的是三階段 RL（SFT → reward shaping → RL），AtomMem 用的是更簡潔的 GRPO + task-level reward。
- **SSGM**：提供治理層——即使 AtomMem 學到了有效的記憶策略，仍需要治理中間件防止 semantic drift、memory poisoning 等風險。AtomMem 是「怎麼管」的學習方案，SSGM 是「怎麼治理」的規範方案。
- **GEM**（2605.26252，06-01 推薦）：用四個 state-level operators 取代 CRUD 的 record-level 操作，和 AtomMem 的 CRUD 原子操作在抽象層次上有張力——GEM 認為 CRUD 太低階，AtomMem 認為 CRUD 是完備且最小的操作集合。

AtomMem 的 CRUD 形式化和 POMDP 框架很清晰，實驗也夠紮實（5 benchmarks + 策略分析）。值得深讀的部分：Section 3 的 POMDP 形式化、Table 1 的 benchmark 結果、以及策略分析中操作頻率變化的圖表——這些是理解「學到的記憶策略長什麼樣子」的關鍵。

## 2. Active Context Compression: Autonomous Memory Management in LLM Agents (Focus)

- **arXiv**: 2601.07190
- **Authors**: Nikhil Verma
- **Venue**: arXiv preprint (January 2026); IEEE conference format
- **Link**: https://arxiv.org/abs/2601.07190

### 這篇在說什麼

Focus 是一個受黏菌（Physarum polycephalum）探索策略啟發的 agent 記憶架構。核心問題是「Context Bloat」：隨著互動歷史增長，計算成本暴增、延遲增加、推理能力因為不相關的過去錯誤而退化。現有解法多是被動的外部摘要機制（agent 無法控制），Focus 讓 agent 自己決定何時壓縮——把關鍵學習摘要到一個持久的 Knowledge block，然後主動刪除原始互動歷史。

### 主要貢獻

1. **從 Append-Only 到 Sawtooth 模式**：把 agent 上下文從單調遞增的 log 轉為鋸齒狀（探索時增長，壓縮時收縮），用 slime mold 的類比——生物系統不保留每次肌肉運動的記錄，只保留學到的地圖。

2. **Focus Loop 架構**：start_focus → explore → complete_focus → withdraw 四個原語，agent 完全自主決定何時調用。

3. **SWE-bench Lite 上的實證**：在 N=5 context-intensive instances 上，Focus 達到 22.7% token 減少（14.9M → 11.5M），準確率不變（3/5 = 60%）。

### 方法 / pipeline

1. **start_focus**：agent 宣布正在調查什麼（如 "Debug the database connection"），標記一個 checkpoint。
2. **Explore**：使用標準工具（read, edit, run）做工作。
3. **complete_focus**：agent 自主生成摘要——嘗試了什麼、學到了什麼、結果是什麼。
4. **Withdraw**：系統把摘要追加到 context 頂部的 Knowledge block，刪除 checkpoint 之後的所有訊息。

關鍵：agent 完全自主決定何時壓縮。但實驗發現「被動提示」只產生 1-2 次壓縮，必須用「激進提示」（每 10-15 次 tool call 壓縮一次 + 系統提醒）才能達到有效壓縮。

### 實驗設計

- **模型**：Claude Haiku 4.5
- **Benchmark**：SWE-bench Lite，選 5 個 context-intensive instances
- **對比**：Baseline（無壓縮）vs Focus（自主壓縮）
- **Scaffold**：persistent bash + string-replacement editor（Anthropic 最佳實踐）
- **結果**：
  - 22.7% token 減少，準確率不變
  - 4/5 instances 節省 tokens（18%–57%）
  - 1/5 instances（pylint-7080）增加 110% tokens——因為壓縮丟失了有用的上下文，迫使重新探索
  - 平均 6.0 次壓縮/任務，每次丟棄 70.2 messages

- **核心洞察**：當前 LLM 不會自然最佳化上下文效率——需要外部 scaffolding 讓壓縮成為 workflow 的一部分。

### かに讀後判斷

Focus 和 AtomMem 形成有趣的對比：兩者都在解決「agent 應該如何管理記憶」，但路線完全不同。AtomMem 用 RL 學一個 task-aligned 的記憶策略，Focus 用 prompt engineering 讓 agent 自主壓縮。AtomMem 的記憶是外部資料庫，Focus 的記憶是 context window 內的 Knowledge block。AtomMem 有 5 benchmarks 的穩定結果，Focus 只有 N=5 的初步驗證。

Focus 的核心限制是實驗規模太小（5 instances）且高度依賴激進提示策略。但它的 slime mold 類比和 sawtooth 模式的直覺很有價值——問題不在於「要不要壓縮」，而在於「何時壓縮」和「壓縮多少」。這和 AtomMem 的 RL 學到的策略（Read 頻率下降、Create/Update/Delete 上升）有異曲同工之妙。

目前從 HTML 全文讀到了完整的方法和實驗，但實驗規模和激進提示策略的依賴性是重要限制。值得看未來工作是否能透過 fine-tuning 或 RL 內化壓縮啟發式。
