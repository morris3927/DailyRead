# Agent Memory — 2026-07-16

## 1. Shared Selective Persistent Memory for Agentic LLM Systems (2607.09493)

- **arXiv**: [2607.09493](https://arxiv.org/abs/2607.09493)
- **Authors**: Sanjana Pedada, Aditya Dhavala, Neelraj Patil (Apple Inc.)
- **Submitted**: 2026-07-10

### 這篇在說什麼

LLM agent 有一個根本問題：每次新 session 都從零開始，之前 session 累積的配置選擇、資料 schema、工具使用模式全丟了。直覺的解法是把整個對話歷史保留下來——但這不但浪費 token，還會害到生成品質（「lost in the middle」效應，加上過去的工具使用軌跡會 bias agent 重走舊路）。

Apple 的這篇論文提出 **shared selective persistent memory**：把 agentic session 的可重用知識分解成四個正交類別（task specifications, data schemas, tool configurations, output constraints），只保留這四類，丟掉 session-specific 的推理軌跡。而且這個記憶體是 **shared** 的——workspace 可以在不同使用者之間傳遞，搭配 role-based access control，讓團隊不需要重複規格。他們還設計了 **zero-token data refresh** 機制：把生成的程式和 runtime 資料分離，資料更新時不需要重新叫 LLM，直接替換資料就好。

在三個企業部署場景中，selective memory 達到 96% task completion（vs 79% 無記憶、71% 全歷史），zero-token refresh 減少 14× 任務時間、97× per-invocation token cost。

### 主要貢獻

1. **四類可重用 context 的分解**：不是什麼都留，也不是什麼都不留。Task specifications、data schemas、tool configurations、output constraints——這四類是跨 session 穩定、精簡、有益的；而 session trace、tool invocation logs、intermediate file states 是跨 session 有害的。這個分解是本文最核心的概念貢獻。
2. **Shared memory + role-based access**：workspace 不只是個人記憶，是可以跨團隊分享的「curated artifact store」。搭配 OIDC 身份管理和三種角色（owner / steward / viewer），讓記憶成為組織資產。
3. **Zero-token data refresh**：生成的 artifact 必須從 runtime injection point 消費資料，絕不 hardcode。這樣資料更新時，schema 相容就直接 refresh，零 LLM token。四個公開資料集上 12/12 成功。
4. **Naive full-history persistence 反而有害**：71% task completion vs 79% no memory vs 96% selective。這是一個重要反直覺結果——留越多不一定越好。

### 方法 / pipeline

- **Memory decomposition**：四類 context 各自獨立持久化：
  - `M_task`：自訂 system prompts，encode domain rules、output format、generation preferences
  - `M_data`：column names/types、統計摘要、關係，自動從 raw data 生成（pandas.describe() + 擴展）
  - `M_tools`：可用工具、參數 schema、invocation patterns、auth requirements
  - `M_output`：structural contracts between artifact and runtime environment

- **Session composition**：新 session 開始時，system prompt = `s_base ⊕ M_task ⊕ M_tools ⊕ M_output`，data schema 放在 user message 裡。

- **Discarding**：推理軌跡、工具調用 log、intermediate file states、error recovery paths——session 內有用，跨 session 有害。

- **Workspace**：`W = (M_task, M_data, M_tools, M_output, a, V)`，其中 `a` 是最新 artifact，`V` 是 version history。注意：workspace 存的是 structured configuration 和 generated code，不是聊天歷史。

- **Sharing workflow**：Load → Swap（接上自己的資料源，schema 相容就直接 render，零 token）→ Refine → Query。

- **Implementation**：FastAPI backend + React frontend，git-backed versioning，draft isolation，多 connector（CSV, SQL, REST, MCP）。

### 實驗設計

- **三個企業場景**：
  1. **Recurring refresh**：分析師每週生成供應鏈 dashboard，原本每次要重新指定 8–12 個格式約束（4–5 turns）。Selective memory 讓規格持續存在，zero-token swap 讓一鍵刷新成為可能。
  2. **Cross-team sharing**：主管發佈 revenue workspace 作為 versioned template，同事載入後接上自己區域的 SQL 資料，artifact 直接 render。
  3. **Iterative construction**：團隊跨 session 逐步建構 workspace，每個人加的規格自動帶入。Session time 從 ~20 min 降到 ~5 min。

- **量化結果**：
  - 96% task completion（selective memory）vs 79%（no memory）vs 71%（full history）
  - Zero-token data refresh：14× task time reduction, 97× per-invocation token cost reduction
  - 四個公開資料集 replication：zero-token refresh 12/12 成功
  - Summary-driven generation vs raw data injection：97× token cost reduction

- **已讀來源**：arXiv HTML 全文（Sections 1–4 完整，含方法論、架構細節、實驗設計）。Section 6 case study 和 Section 7 evaluation 的完整表格需要進一步確認。

### かに讀後判斷

這篇是 agent memory 領域的一個重要實務導向論文，來自 Apple，在 deployed enterprise platform 上驗證。

幾個關鍵判斷：

1. **「留什麼」比「留多少」更重要**：這篇的核心洞見不是「agent 需要記憶」（這大家都知道），而是「記憶的結構性分解」。四類 context 各自獨立管理，比把整個對話歷史丟進 context window 好得多。這和 MemGPT 的 OS 隱喻不同——MemGPT 是 hierarchy，這篇是 orthogonal decomposition。
2. **Naive full-history 比 no memory 還差**（71% vs 79%）這個結果很重要。它說明 LLM agent 的記憶管理不是「越多越好」，而是需要選擇性。這對所有在 agent 系統裡簡單加 long-term memory 的做法都是一個警示。
3. **和今天 harness 篇（E3）形成有趣的對照**：E3 是同一 session 內的 context 管理（判斷需要多少），這篇是跨 session 的 context 管理（判斷保留什麼）。兩者都在說：agent 的 context 需要精準管理，不是越多越好。
4. **Zero-token data refresh 是工程上的亮點**：把「程式和資料分離」這個軟體工程的 old idea 用在 LLM artifact 上，實現了資料更新不需要重新調用 LLM 的效果。
5. **值得深讀**：Section 6（case study 細節）、Table 1-4（量化比較）、以及 zero-token data refresh 的具體實作細節（schema compatibility check、additive schema evolution）。
