## 今日篩選判斷

今天 Harness Engineering 的主線是「把 harness 從隱形 glue code 變成可描述、可比較、可遷移、可驗證的工程物件」。昨天 AHE 強調 observability-driven evolution；今天的 OpenDev technical report 與 Natural-Language Agent Harnesses 則分別從兩個角度補上：一個展示 terminal-native coding agent 的實際 harness 架構，另一個嘗試把 harness control logic 外部化成自然語言 artifact。Addy Osmani 的文章則是 practitioner synthesis，很適合當工程 checklist。

## 1. Building Effective AI Coding Agents for the Terminal: Scaffolding, Harness, Context Engineering, and Lessons Learned

- URL: https://arxiv.org/abs/2603.05344
- HTML: https://arxiv.org/html/2603.05344v3
- Authors: Nghi D. Q. Bui et al.
- First version: 2026-03-05; v3: 2026-03-13
- Source type: arXiv technical report / open-source system report

### 這篇在說什麼

這篇介紹 OpenDev，一個用 Rust 寫的 terminal-native coding agent。它的核心不是提出新模型，而是把一個可長時間運作的 CLI coding agent 需要哪些 scaffolding / harness / context engineering 拆開講清楚。這對 Harness Engineering 很有價值，因為多數 production coding agents 的架構細節都藏在閉源產品裡；這篇至少把一套 open-source terminal agent 的取捨寫成 technical report。

作者的 framing 很直接：terminal-native agent 的挑戰不只是讓模型會寫 code，而是要讓它能在真實開發環境裡使用 git、build、test、deploy、shell，同時避免 context bloat、reasoning degradation 和 destructive actions。OpenDev 的設計把 scaffolding 定義為「第一次 prompt 前如何組裝 agent」，把 harness 定義為 runtime orchestration：tool dispatch、context management、safety enforcement、session persistence。

### 工程設計 / 架構重點

OpenDev 是 compound AI system，不是一個單一 LLM call。它把系統分成 session → agent → workflow → LLM 四層，讓不同 workflow 可以綁不同模型。這很像真正工程系統會做的 model routing：planning、execution、thinking、critique、vision 等角色不一定需要同一個模型。

它也採用 dual-agent / mode separation：Plan Mode 只能用 read-only tools，Normal Mode 才能 full read-write。這是很典型的 harness-level safety pattern：不是只在 prompt 裡叫 agent 小心，而是在 tool schema 與 runtime permission 層面限制能做什麼。

Context engineering 方面，它有 adaptive context compaction、event-driven system reminders、conditional prompt composition、lazy tool discovery、project memory。event-driven reminders 尤其值得注意：長任務裡 instruction fade-out 是真問題，OpenDev 不期待最初 system prompt 永遠有效，而是在決策點重新注入針對性提醒。

### 實驗 / 評估資訊

這篇比較像 system report，不是 benchmark paper。它沒有像 AHE 那樣主打 Terminal-Bench / SWE-bench 的量化提升，而是展示架構與 lessons learned。因此讀的時候不應把它當「OpenDev 贏過誰」的實證文，而應把它當「terminal coding agent 需要哪些 harness components」的工程藍圖。

### 對 agent harness / eval / workflow 的意義

OpenDev 把 harness 拆成多個可替換層：prompt composition、tool registry、MCP lazy discovery、approval manager、session persistence、operation log、memory、compaction。這種分層對 OpenClaw 類系統很有啟發，因為它把「agent 失敗」拆成可以定位的工程問題：是 tool menu 太大、context compaction 太粗、approval 太鬆、memory 太髒、還是 mode boundary 不清？

### かに讀後判斷

今天 Harness Engineering 最推薦先點這篇。它不像 AHE 那麼有實驗亮點，但更像一本 terminal-native coding agent 的架構筆記；如果 Morris 想思考 OpenClaw / Codex / Claude Code 這類系統的 harness surface，這篇很值得細看。

## 2. Natural-Language Agent Harnesses

- URL: https://arxiv.org/abs/2603.25723
- HTML: https://arxiv.org/html/2603.25723v1
- Authors: Linyue Pan, Lexiao Zou, Shuo Guo, Jingchen Ni, Hai-Tao Zheng
- Date: 2026-03-26
- Source type: arXiv preprint

### 這篇在說什麼

這篇問一個很有趣的問題：agent harness 的高層控制邏輯，能不能不要藏在 controller code 和 framework convention 裡，而是外部化成一個可編輯、可執行、可遷移的 natural-language artifact？作者提出 Natural-Language Agent Harnesses（NLAHs）和 Intelligent Harness Runtime（IHR）。NLAH 描述 harness behavior；IHR 則在 shared runtime assumptions 下解讀並執行這些 harness。

它的出發點和昨天的 AHE 很接近：harness 已經是決定 agent 表現的關鍵，但如果 harness 只散落在 prompt、tool adapters、controller code、verifier scripts 和 runtime defaults 裡，我們就很難做公平比較、模組 ablation 或跨 runtime migration。

### 工程設計 / 架構重點

NLAH 要明確暴露幾個元素：contracts、roles、stage structure、adapters/scripts、state semantics、failure taxonomy。這些其實就是成熟 agent workflow 裡最常被隱藏的部分：每個階段要產出什麼 artifact、誰負責驗證、什麼算完成、失敗時怎麼恢復、哪些 state 要跨步驟保留。

IHR 的 runtime 則包含 in-loop LLM、backend tool access / child-agent support，以及 runtime charter。這裡的分工是：runtime charter 提供共用語義與政策；NLAH 提供 task-family-specific harness logic。這讓研究者可以固定 runtime，只替換 harness pattern，做比較或 ablation。

### 實驗設計

作者在 coding 與 computer-use benchmarks 上做 controlled evaluations，包含 operational viability、module ablation、code-to-text harness migration。從可讀內容來看，它關心的不是單一最高分，而是三個研究問題：shared runtime charter 和 benchmark-specific harness 如何改變行為；明確化的 pattern modules 能否組合 / 消融；從原生 code harness 遷移到 natural-language harness 後還剩哪些差異。

這次我主要讀 abstract、introduction 和 methodology，還沒有逐表核對每個 benchmark 數字，因此具體效果先不展開。

### 對 agent harness / eval / workflow 的意義

這篇的價值在於把 harness 變成「可攜帶的研究物件」。如果這個方向成立，未來比較 agent 不應該只說 model + benchmark，而要附上 executable harness artifact。這也很符合 OpenClaw skill / AGENTS.md / automation prompt 的方向：自然語言不只是 prompt，而可以承載 role boundaries、artifact contracts、failure recovery、state semantics。

### かに讀後判斷

值得收藏。它可能還不如 OpenDev 立即可落地，但它提供了一個研究框架：harness 應該能被 versioned、ablated、ported，而不是每次都和 runtime code 綁死。

## 3. Agent Harness Engineering — Addy Osmani

- URL: https://addyosmani.com/blog/agent-harness-engineering/
- Author: Addy Osmani
- Date: 2026-04-19
- Source type: practitioner blog / synthesis

### 這篇在說什麼

這篇不是 paper，但今天仍值得放進 Harness Engineering，因為它把最近 practitioner discourse 整理得很清楚。核心句是：**coding agent = model + harness**；如果不是模型本身，那就是 harness。harness 包含 prompts、tools、skills、MCP servers、filesystem、sandbox、subagents、hooks、middleware、observability、feedback loops、recovery paths。

作者強調一個很實用的心智模型：每次 agent 犯錯，都應該變成 harness ratchet。不是笑一笑重跑，而是把失敗轉成 AGENTS.md 規則、pre-commit hook、reviewer subagent、test gate、permission block 或 context policy。

### 工程設計重點

文章把 harness primitives 拆得很工程化：filesystem / git 作為 durable state；bash 和 code execution 作為 general-purpose tool；sandbox 作為安全執行層；memory / search 作為 continual learning；compaction、tool-output offloading、progressive disclosure 對抗 context rot；hooks 作為 enforcement layer；planner / generator / evaluator split 支撐長任務。

這裡最值得記的是「success is silent, failures are verbose」。typecheck / lint / tests 通過時不要浪費 context；失敗時才把可行動的錯誤注入 agent loop。這是 harness feedback loop 的低成本設計原則。

### かに讀後判斷

適合當工程 checklist 收藏。若今天只讀 paper，先讀 OpenDev；若要快速整理「我自己的 coding-agent harness 缺什麼」，這篇更直接。
