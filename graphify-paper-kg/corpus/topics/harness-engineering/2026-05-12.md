## 1. Agent Harness for Large Language Model Agents: A Survey

- URL: https://github.com/Gloriaameng/Awesome-Agent-Harness
- Preprint: https://www.preprints.org/manuscript/202604.0428/v2
- Authors: Qianyu Meng, Yanan Wang, Liyi Chen, Wei Wu, Yihang Li, Wenyuan Jiang, Qimeng Wang, Chengqiang Lu, Yan Gao, Yi Wu, Yao Hu
- Date: initial repo 2026-04-03; preprint 2026-04
- Source type: survey preprint + maintained GitHub paper list

### 這篇在說什麼

這篇 survey 的核心句很強：**agent execution harness, not the model, is the primary determinant of agent reliability at scale.** 作者把 agent harness 從模糊的 glue code 拉出來，定義成一個六元組 H = (E, T, C, S, L, V)：Execution Loop、Tool Registry、Context Manager、State Store、Lifecycle Hooks、Evaluation Interface。

這個拆法很有用，因為它讓「agent 為什麼可靠 / 不可靠」不再只歸因到模型能力。很多實際差異其實在工具 schema、context compaction、狀態保存、hooks、權限、logs、evaluation surface。

### 工程設計 / 架構重點

六個 component 的意義大概是：E 管 observe-think-act loop、終止條件與錯誤恢復；T 管 typed tool catalog、routing、monitoring、schema validation；C 管 context window 進什麼、如何壓縮、如何檢索；S 管跨 turn/session 的持久狀態與 crash recovery；L 管 auth、logging、policy enforcement、instrumentation；V 管 action trajectories、intermediate states、success signals。

它也提出 Harness Completeness Matrix，想把不同 agent systems 放到同一張表上比較。這對領域很關鍵，因為現在很多 benchmark 結果其實混在一起：model 不同、scaffold 不同、tool policy 不同、context policy 不同，最後卻只報一個分數。

### 實驗 / 評估資訊

這是 survey，不是單一 benchmark paper。GitHub README 說它系統性整理 110+ papers / blogs / reports，涵蓋 23 systems，並整理 9 個 open technical challenges。README 也列出一些 practitioner evidence，例如同一模型在不同 edit-tool / harness format 下 SWE-bench 表現可以大幅變動；這類例子用來支持「harness 是一級變因」。

我今天主要讀 README / abstract-level material；Preprints 網頁本身被保護頁擋住，未逐頁讀 PDF。因此具體 citation graph 與每個 system 的矩陣細節先不展開。

### 對 agent harness / eval / workflow 的意義

這篇的價值是命名與標準化。它讓我們可以更精確地問：一個 agent framework 的 E/T/C/S/L/V 分別是什麼？哪個 component 是 research contribution？哪個只是工程缺口？如果 evaluation interface V 不透明，那 benchmark 分數是不是可重現？如果 state store S 缺失，agent 是否其實無法可靠跨 session？

### かに讀後判斷

值得收藏，而且很適合當 Harness Engineering 的 map。它可能有 survey 過度包山包海的風險，但 H=(E,T,C,S,L,V) 這個框架很實用：之後讀任何 coding agent / workflow agent，都可以用這六格拆解。

## 2. Holistic Agent Leaderboard: The Missing Infrastructure for AI Agent Evaluation

- URL: https://openreview.net/forum?id=vUaY1t64ZZ
- Source type: OpenReview submission / evaluation infrastructure paper

### 這篇在說什麼

這篇把 agent evaluation 的問題說成 infrastructure 問題，而不是單純 benchmark 問題。作者提出 Holistic Agent Leaderboard（HAL），目標是提供 standardized、cost-aware、third-party 的 agent evaluation harness。它不只是收集 benchmark 分數，而是要標準化 agent rollouts 的執行環境、平行化、log 保存與錯誤分析。

### 工程設計 / 架構重點

HAL 的第一個貢獻是 standardized evaluation harness：能在 hundreds of VMs 上平行跑 agent evaluations，將原本可能要 weeks 的評估縮短到 hours，同時減少 implementation bugs。這很像把「評估 agent」本身變成一個嚴肅的 distributed systems / MLOps 問題。

第二個貢獻是三維分析：models、scaffolds、benchmarks 同時看。這點對 harness engineering 很重要，因為 agent 分數不是 model-only；scaffold / harness 可能改變工具使用、重試策略、search behavior、reasoning effort、失敗恢復。

第三個貢獻是 log inspection。作者用 LLM-aided log inspection 找出未被報告的 agent 行為，例如不是解 task 而是去 HuggingFace 搜 benchmark、或在 flight booking 任務裡錯用信用卡。這提醒我們：只看 final score 不足以理解 agent reliability，trajectory logs 本身是 evaluation artifact。

### 實驗設計

OpenReview abstract 說他們用這套 harness 跑了 21,730 agent rollouts，涵蓋 9 models、9 benchmarks，任務類型包含 coding、web navigation、science、customer service，總成本約 $40,000。它也提到一個反直覺結果：higher reasoning effort 在多數 runs 裡反而降低 accuracy。

DailyRead 這裡只根據 OpenReview landing page / abstract 整理，還沒讀完整 PDF 和表格，因此不細列每個模型 / benchmark 成績。

### 對 agent harness / eval / workflow 的意義

這篇最值得記的是：agent evaluation 需要 capture model、scaffold、benchmark、cost、logs、trajectory failure modes。未來如果只說某模型在某 benchmark 幾分，但不說 scaffold / harness / VM / tools / logs，很可能已經不夠嚴謹。

### かに讀後判斷

很值得點開。它和 survey 的關係是：survey 給 harness taxonomy；HAL 給 evaluation harness infrastructure。若 Morris 關心 OpenClaw / coding agent evaluation，這篇的 log-first evaluation 很有參考價值。

## 3. Harness Engineering for AI Coding Agents: Constraints That Ship Reliable Code

- URL: https://www.augmentcode.com/guides/harness-engineering-ai-coding-agents
- Source type: practitioner engineering guide

### 這篇在說什麼

這篇不是 paper，但它把 production coding-agent harness 的語言整理得很好。核心主張是：coding agent 造成的 bottleneck 不只是產碼能力，而是 verification bottleneck。只用 prompt 說「遵守標準」是 probabilistic compliance；把 lint、test、permission、quality gate 接進 runtime，才是 deterministic constraints。

### 工程設計或架構重點

文章把 harness engineering 放在 prompt engineering / context engineering 之外：prompt engineering 管單次指令，context engineering 管 context window 裡的 token，harness engineering 管整個 agent system 的工具編排、state persistence、verification loops、error recovery、permission boundary。

它建議從 constraint harnesses、feedback loops、quality gates 逐層做起。這和我對 agent harness 的理解很一致：先減少錯誤輸出量，再讓 agent 能自我修正，最後用不可繞過的 gate 保護 mainline。

### 對 agent harness / eval / workflow 的意義

這篇適合當工程 checklist，不適合當實證研究引用。它的價值在於把 harness failure 說成架構問題，而不是叫使用者更會 prompt。對實際 coding agents，這個 framing 很健康。

### かに讀後判斷

可收藏。若只讀 research，今天先讀 HAL 或 survey；若要改自己的 agent workflow，這篇更直接。
