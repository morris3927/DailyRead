# Harness Engineering — 2026-05-13

## 1. How Much Heavy Lifting Can an Agent Harness Do? — Measuring the LLM's Residual Role in a Planning Agent

- **作者**: Seonil Son 等
- **arXiv**: [2604.07236](https://arxiv.org/abs/2604.07236) (v4: 2026-04-28)
- **領域定位**: Harness engineering 的定量分解論文

這篇問了一個 harness 領域最核心但最少被正式回答的問題：當 harness 可以把效能提升 6 倍時，LLM 本身到底還做了多少「重活」？

作者把一個 planning harness（noisy Collaborative Battleship）拆成四層：

1. **Posterior belief tracking** — 只靠觀測更新信念，不用 LLM
2. **Declarative planning** — 符號規劃，零 LLM calls，+24.1pp win rate
3. **Symbolic reflection** — 校準敏感，signed board-level effects ±0.140 F1，aggregate 上正負抵消
4. **LLM-backed revision gate** — 只在 4.3% 的 turns 啟動，效果有界且非單調

核心貢獻是方法論層面的：**把 harness layers 做成 external measurable 之後，LLM 的貢獻可以被量化為 residual，而不是被假設為中心。** Declarative planning（第二層）就 carry 了 heavy lifting，LLM 的角色反而有限。

實驗設計：54 場 game，primary metric 是 win rate，secondary 是 F1，heavy lifting 定義為單一最大正邊際效應。這種實驗設計很乾淨，但也有局限——Battleship 是相對簡單的規劃問題，LLM 在更開放的任務中可能扮演更大角色。

**閱讀判斷**: 這篇是 harness engineering 領域裡少見的定量分解實驗，直接回答了「harness 到底 carry 多少」這個關鍵問題。方法論清晰，值得細看。**今日推薦點開。**

## 2. The Last Harness You'll Ever Build

- **作者**: Haebin Seong 等
- **arXiv**: [2604.21003](https://arxiv.org/abs/2604.21003) (v3: 2026-05-01)

這篇提出一個兩層自動化框架，把 harness engineering 從手工打造變成自動演化：

- **第一層 Harness Evolution Loop**: Worker Agent W_H 執行任務 → Evaluator Agent V 對抗性診斷失敗並評分 → Evolution Agent E 根據歷史修改 harness。這是對單一任務優化 harness。
- **第二層 Meta-Evolution Loop**: 跨多樣化任務優化演化藍圖 Λ = (W_H, H^(0), V, E)，學到一個能在任何新任務上快速收斂的 Λ^(best)，讓新領域的 harness 適配不再需要人工工程。

對應到 meta-learning：第一層是 inner-loop learning，第二層是 outer-loop learning the learning algorithm。

這是一篇大膽的 paper——如果真的能 work，意味著 harness engineering 本身可以被自動化，甚至自動化的設計也可以被自動化。但目前只看到框架和算法描述，沒看到大規模實驗驗證。

**閱讀判斷**: 概念非常前瞻，但需要看實驗結果才有說服力。值得收藏追蹤，目前不推薦優先點開。

## 3. The Agent Harness: Why the LLM Is the Smallest Part of Your Agent System（MongoDB Blog）

- **來源**: [MongoDB Technical Blog](https://www.mongodb.com/company/blog/technical/agent-harness-why-llm-is-smallest-part-of-your-agent-system)（2026-04-30）
- **類型**: Engineering blog / industry perspective

這篇是 MongoDB 的 agent platform 系列文章之一，從工程實踐角度描述 harness 的六個組成元件：

1. **State and persistence** — checkpoint、intermediate outputs、resume-from-crash
2. **Security and governance** — identity propagation、permission scoping、audit trails
3. **Orchestration and tool use** — agent loop 驅動、tool calling
4. **Memory** — 不是向量庫就行，是 agent 的寫–管–讀迴路
5. **Observability** — logs、traces、metrics
6. **Evals** — 目前沒有標準 eval framework，測量問題 ahead of tooling

文章最有趣的論點是引用 Sculley 2015 的 MLOps diagram 來類比：ML code 在那張圖裡只是中心的小黑盒，周圍是龐大的基礎設施。Agent systems 正在重複同樣的錯誤——大家聚焦 LLM call 本身，但 harness 和 platform 才是工程重點。

另外給了具體數字：一個 governed agent platform 大約是每 token 50 行周邊代碼，而周末 chatbot 大約是 1 行。Claude Code 的源碼約 512K 行 TypeScript / 1900 files，其中 model interaction 只佔一小部分。

**閱讀判斷**: 這篇是很好的工程概覽，特別適合想快速理解 harness 範圍的讀者。不是 paper，但比大多數 paper 更接地氣。值得收藏。
