# 2026-05-08 - Harness Engineering

## 今日領域觀察

Harness engineering 和另外兩個 domain 不太一樣。它目前不一定會以 paper 為主，反而很多重要內容會出現在 framework README、engineering blog、benchmark docs 和實作 repo 裡。這也合理，因為 harness 本質上就是工程基礎設施：它關心的是怎麼把模型、任務、環境、工具、grader 和紀錄流程串成可重複執行的 evaluation pipeline。

今天看到的內容可以分成三種：成熟 LLM benchmark harness、agent eval 的工程方法論、以及具體 agent framework 的 evaluation docs。這個 domain 之後應該明確接受非 paper 來源，但每則要標清楚它是 paper、blog、docs 還是 framework。

## 1. EleutherAI lm-evaluation-harness

- Link: https://github.com/EleutherAI/lm-evaluation-harness
- Type: framework / GitHub repo

### 這個專案在說什麼

lm-evaluation-harness 是 LLM 評估領域很代表性的工具。它的核心目標是讓研究者或工程師可以用統一的方式，在大量 benchmark tasks 上測不同語言模型。它支援 few-shot evaluation、多種模型 backend、CLI 執行，以及 config-driven 的評估流程。

從 harness engineering 的角度看，它重要的地方不是「又多一個 benchmark」，而是它把模型評估變成一套可重複執行的工程流程。你可以定義 task、指定模型 backend、設定推論參數、跑評估、輸出結果。這種工具讓不同模型之間的比較比較不會變成每個人各寫各的 script。

### 主要貢獻 / 工程價值

- 提供標準化 LLM benchmark execution framework。
- 支援大量 academic benchmark tasks 和不同模型 backend。
- 近期更新走向 CLI subcommands、YAML config、backend dependency 分離。
- 對 API model、batched / async request、multimodal evaluation 等需求持續擴充。

### 方法 / 架構

它的基本架構可以理解成三層：第一層是 tasks，也就是要評估的資料集與任務格式；第二層是 model adapters，讓不同模型或 serving backend 可以用同樣介面被呼叫；第三層是 evaluation runner，負責 few-shot prompt 組裝、推論、metric 計算與結果輸出。

這種設計的重點是 abstraction：task 不應該綁死某個模型，model backend 也不應該綁死某個 benchmark。harness 的價值就在於把這些東西解耦。

### 評估設計

作為 framework，它本身不是單篇 paper 的實驗設計，而是承載很多 benchmark 的執行環境。它比較像 evaluation infrastructure：你可以透過它跑 MMLU、GSM8K、HumanEval、TruthfulQA 等任務，然後產生可比較的分數。

後續如果看 harness engineering，這類工具應該被當成基準樣本：一個成熟 harness 至少要處理 task registry、model adapter、config、metric、logging、reproducibility 和 output format。

### かに讀後判斷

這個不是今天要深讀的 paper，但非常值得收藏。它是理解「LLM evaluation harness」最好的工程入口之一。之後看 agent harness，可以拿它對比：傳統 LLM harness 多半評估單輪或資料集任務；agent harness 則還要處理工具、環境狀態、多步 trajectory 和失敗恢復。

## 2. Demystifying evals for AI agents

- Link: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Type: technical blog / engineering practice

### 這篇文章在說什麼

Anthropic 這篇文章在講 agent eval 為什麼比傳統 LLM eval 難。傳統單輪 LLM evaluation 通常是給 prompt、拿 response、用 grader 或 metric 評分。但 agent 會多輪行動、呼叫工具、修改環境狀態，還會根據中間結果調整策略。這讓錯誤不只出現在最後答案，也可能出現在任何一步。

文章把 agent eval 拆成幾個概念：task、trial、grader、assertion、transcript / trace / trajectory。這些詞很重要，因為它們把 agent evaluation 從「看答案對不對」變成「看整個行為過程是否合理」。

### 主要貢獻 / 工程價值

- 清楚定義 agent eval 的基本單位：task、trial、grader、assertion、trajectory。
- 強調 agent eval 需要保存完整 transcript，因為多步錯誤會傳遞與放大。
- 指出 frontier models 可能找到超出 static eval 預期的解法，因此 grader 設計不能太死。
- 把 eval 描述成 agent 開發生命週期的一部分，而不是上線前一次性測試。

### 方法 / 架構

文章中的 agent eval 流程大致是：先設計一個 task，給 agent 工具與環境，讓它執行多輪 agent loop；執行過程中保存完整 transcript，包括工具呼叫、中間輸出、狀態變化與最終結果；最後用一個或多個 graders 評分。

它特別強調 trial，因為模型輸出有隨機性，同一任務需要多次嘗試才能得到穩定估計。這對 agent evaluation 很重要，因為 agent 在某一步走錯，後面整個 trajectory 都會不同。

### 評估設計

這篇不是 academic experiment，而是工程評估方法論。它的評估設計重點是：agent task 應該有明確成功條件；grader 可以包含多個 assertions；完整 trajectory 應該被保存，方便分析 failure mode；對長任務或工具型任務，unit tests、state checks、policy checks 可能比單純 LLM judge 更可靠。

文章也提到 multi-turn eval 的複雜性：例如 coding agent 建 MCP server，不能只看最後文字，而要看環境中是否真的產生可工作的實作，並用測試驗證。

### かに讀後判斷

這篇很符合你說的 harness engineering：不是 paper，但非常值得追。它提供的是工程語言，幫我們理解 agent eval harness 應該記錄什麼、評什麼、怎麼避免只看最後答案。這篇我會列為 harness engineering 的高品質非 paper 來源。

## 3. OpenHands Evaluation Harness

- Link: https://docs.openhands.dev/openhands/usage/developers/evaluation-harness
- Type: framework docs / engineering guide

### 這份文件在說什麼

OpenHands 的 evaluation harness 文件展示的是一個具體 agent framework 如何把 benchmark 接進自己的系統。文件內容包含如何設定 LLM、如何用 command line 跑 OpenHands、如何指定 task description、agent class、LLM config 和最大迭代次數。

它的價值不是文筆或理論，而是可以看到一個 agent system 在工程上怎麼暴露 evaluation entrypoint。也就是說，如果你要評估一個 agent，不是只需要 prompt 和答案，還需要 runtime、controller、agent class、config、task，以及可能的 benchmark adapter。

### 主要貢獻 / 工程價值

- 展示 agent framework 如何支援自訂 benchmark integration。
- 把 evaluation 流程拆成 LLM config、agent class、task description、runtime 與 controller。
- 說明 agent eval 需要可配置的執行環境，而不是單一 API call。
- 作為 framework docs，可觀察 production-like agent harness 的基本形狀。

### 方法 / 架構

OpenHands 的流程大致是：command line 讀取參數與 config，建立 runtime environment，初始化指定 agent，然後由 controller 執行任務。這裡的重點是 runtime 和 controller，因為 agent 不是單純輸入輸出模型，而是在某個環境中執行行動。

這讓 evaluation harness 必須考慮環境重建、任務初始化、最大迭代數、模型設定、工具權限與結果驗證。這些都是傳統 benchmark harness 較少處理的東西。

### 評估設計

這份 docs 的評估設計偏 integration-oriented：它告訴你如何把 benchmark 接進 OpenHands，而不是提出一個新的 benchmark 指標。這類文件適合用來觀察 agent harness 的 operational details，例如如何配置多個 LLM、如何讓 agent 在 CLI 中跑任務、如何控制 iteration。

### かに讀後判斷

這份文件本身不一定要深讀，但它很適合當作 harness engineering 的樣本。它提醒我們：agent evaluation 的難點往往在「系統怎麼跑起來」，而不是只有分數怎麼算。之後如果要追這個領域，framework docs 和 benchmark repo 會跟 paper 一樣重要。
