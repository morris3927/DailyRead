## 今日篩選判斷

## 1. Demystifying evals for AI agents — Anthropic

- URL: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Source type: engineering article

### 這篇在說什麼

Anthropic 這篇是在講 agent eval 到底該怎麼做。它的核心主張很簡單但很重要：agent 不是單輪問答模型，所以 eval 不能只看最後輸出。agent 會用工具、改變環境狀態、跨很多 turns 累積錯誤，也可能用意想不到的方法完成任務。因此 evaluation harness 必須保存完整 transcript / trace / trajectory，並且同時評估最後環境 outcome。

這篇把術語整理得很清楚：task 是單一測試題；trial 是同一 task 的一次嘗試，因為模型輸出有隨機性，所以需要多 trials；grader 是評分邏輯；assertion 是 grader 裡的檢查；transcript / trace / trajectory 是完整過程紀錄；outcome 是環境的最終狀態；evaluation harness 是負責跑任務、提供 tools、記錄步驟、打分與彙總結果的基礎設施；agent harness / scaffold 則是讓 model 能夠行動的系統。

### 工程設計 / 架構重點

最有價值的設計點是「transcript 與 outcome 分離」。例如訂機票 agent 最後說「我已經訂好了」不代表 outcome 成功，真正要看的是 SQL database 裡是否存在 reservation。這個 framing 很適合所有 tool-using agent：自然語言回覆只是 surface，環境狀態才是 ground truth。

另一個重點是 grader 類型：code-based graders 快、便宜、可重現，適合 string match、unit test、static analysis、tool call verification、transcript analysis；model-based graders 彈性高，適合 rubric、natural language assertions、pairwise comparison，但要校準；human graders 慢而貴，但能當 gold standard 或校準模型 grader。對 harness engineering 來說，重點不是選一種 grader，而是把它們組合成能區分 capability eval 與 regression eval 的測試套件。

### 對 agent harness / eval / workflow 的意義

這篇把 evaluation harness 和 agent harness 的邊界講得很實用。當我們說「評估 agent」，其實是在評估 model + scaffold + tool interface + environment 的整體。這一點對 OpenClaw / Codex / Claude Code 這類系統很關鍵：改 tool schema、permission flow、context delivery、compaction 策略，都可能改變 eval 結果；不能把所有成功或失敗都歸因於 base model。

它也明確說 capability eval 和 regression eval 要分開：capability eval 可以從低 pass rate 開始，找模型還不會的能力；regression eval 則應該接近 100% pass rate，用來防止已經會的事情退化。這就是 production agent 的 harness 思維：不只是展示能力，而是持續防止退步。

### 小龍蝦讀後判斷

這篇今天 Harness Engineering 最值得點開。它不是泛泛說「eval 很重要」，而是把 agent eval 的資料結構和運作單元拆出來。若 Morris 要整理 agent harness 的核心詞彙，這篇可以當基礎引用。

## 2. Ready For General Agents? Let’s Test It. — ICLR Blogposts 2026

- URL: https://iclr-blogposts.github.io/2026/blog/2026/general-agent-evaluation/
- Source type: research blog / evaluation taxonomy
- Date surfaced by SearXNG: 2026-04-27

### 這篇在說什麼

這篇關注的是 general-purpose agents 的評估問題。作者認為 agent field 正從 domain-specific agents 走向更 general 的 agents：一個 agent 不只會寫程式、只會 web browsing、或只會特定 research workflow，而是要能進入不同環境、吸收 domain knowledge、透過互動完成任務。

問題是現有 benchmark 多半是 domain-specific：SWE agent 有 SWE 類 benchmark，web agent 有 web benchmark，science agent 有 science benchmark。這些可以評估特定能力，但很難評估「general agent 能不能適應新環境」。因此作者提出五層 evaluation taxonomy，並討論標準化 agent interface、environment interface、researcher interface 的缺口。

### 工程設計 / 架構重點

這篇最接近 harness engineering 的部分，是它把 evaluation 視為 protocol 問題。agent 要和 environment 溝通，就需要 interface / protocol：web browsing、terminal、MCP、tool schemas 都是不同的 agent-to-environment communication protocol。若 protocol 不標準，benchmark 很難重現，也很難比較不同 agent architectures。

文章提出的五層 taxonomy 從比較局部的 agentic skills evaluation，一路到 protocol-centric agent evaluation 與 general agent evaluation。這對 harness builders 的提醒是：benchmark 不只是 task set，也包含 environment setup、tool surface、observation/action format、metrics、以及 researcher 如何接入與比較結果。

### 對 agent harness / eval / workflow 的意義

如果 Anthropic 那篇是在講「一個 eval harness 內部應該怎麼拆」，這篇則是在講「跨 domain / 跨 environment 的 eval harness 為什麼需要 protocol」。對 long-running agents 或 OpenClaw 這種多工具環境來說，這很有參考價值：agent 能力不只在模型，也在它能不能快速理解並穩定使用新的 environment interface。

這篇也提醒我們，越 general 的 agent 越不能只靠單一 leaderboard。真正重要的是 agent 是否能在以前沒見過的工具、檔案系統、網頁、MCP server、API schema 中建立穩定工作循環。

### 小龍蝦讀後判斷

值得收藏，尤其適合作為「general agent eval / protocol」方向的背景讀物。不過它是 blogpost，不是完整實驗 paper；如果要找可直接採用的 eval implementation，還是要搭配實際 benchmark repo 或 eval harness。

## 3. awesome-harness-engineering — ai-boost

- URL: https://github.com/ai-boost/awesome-harness-engineering
- Source type: curated repository

### 這篇 / repo 在解決什麼工程問題

這個 repo 把 harness engineering 定義成 agent 周圍的 scaffolding：context delivery、tool interfaces、planning artifacts、verification loops、memory systems、sandboxes、permissions、observability、orchestration。它不是一篇研究文章，而是一個整理地圖，適合用來追蹤這個領域哪些 component 正在被工程化。

### 工程設計或架構重點

README 的分類本身就是一張 harness checklist：agent loop、planning / task decomposition、context delivery / compaction、tool design、skills / MCP、permissions / authorization、memory / state、task runners / orchestration、verification / CI、observability / tracing、debugging / DX、human-in-the-loop、security / sandbox、evals / verification 等。

這種分類有用，因為它把「agent 做得好不好」拆成多個可維護的系統部件。模型變強後，有些 harness component 可能會變薄，但在 production 環境裡，permissions、observability、verification、sandbox 很難完全消失。

### 小龍蝦讀後判斷

適合收藏，不一定要今天深讀。它的價值是作為 index：當 Morris 想找某個 harness component 的代表文章或 repo，可以先從這裡往外展開。
