# Harness Engineering — 2026-05-10

## 今日篩選判斷

今天 Harness Engineering 的主線很清楚：harness 不只是手寫 scaffold，而正在被當成可以觀測、評估、演化的工程物件。昨天的重點是 agent eval harness 的資料結構；今天更往前一步，看到兩篇都在問「能不能自動改善 harness 本身」。這對 coding agents 特別關鍵，因為模型、工具、middleware、memory、context policy 的交互作用太複雜，單靠人類 prompt tuning 很難穩定推進。

## 1. Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses

- URL: https://arxiv.org/abs/2604.25850
- HTML: https://arxiv.org/html/2604.25850v3
- Authors: Shichun Liu et al.
- First version: 2026-04-28; v3: 2026-04-30
- Source type: arXiv preprint

### 這篇在說什麼

這篇把「harness engineering」講得非常具體：coding agent 的表現不只取決於 base model，而取決於它周圍的 harness，也就是 tools、middleware、memory、context handling、execution environment、system prompts、觀測與驗證流程。問題是，現在 harness 大多靠人手調，調一次看一次結果，很像高成本 trial-and-error。

作者提出 Agentic Harness Engineering（AHE）：讓一個 evolving agent 根據前一輪任務軌跡、失敗證據與 outcome，自動修改 coding-agent harness。它最重要的設計不是「叫 LLM 改 prompt」，而是把 harness components、trajectory evidence、edit decisions 都變成可觀測、可回溯、可驗證的資料結構。

### 工程設計 / 架構重點

AHE 有三個 observability pillars。

第一是 component observability：每個可編輯的 harness component 都要有 file-level representation，讓 action space 明確、可 diff、可 revert。這很重要，因為 harness 不是一段 prompt，而是一堆工具、middleware、memory policy 與 runtime glue。

第二是 experience observability：coding agent 的 trajectory 可能有數百萬 tokens，不能直接塞給下一個 agent 看。AHE 把 raw trajectories 壓成 layered、可 drill-down 的 evidence corpus，讓 evolving agent 能先看摘要，再往下追具體證據。

第三是 decision observability：每次 edit 都要附上一個 self-declared prediction，也就是「我改這裡預期會讓哪些任務變好、為什麼」。下一輪結果出來後再驗證這個 prediction。這讓 harness evolution 不只是盲目搜尋，而是每個改動都有可被 falsify 的合約。

### 實驗設計

摘要給的實驗很強：10 次 AHE iterations 讓 Terminal-Bench 2 pass@1 從 69.7% 提升到 77.0%，超過 human-designed Codex-CLI harness 的 71.9%，也超過 ACE 和 TF-GRPO 這類 self-evolving baselines。更有意思的是 frozen harness 不重新演化也能 transfer：在 SWE-bench-verified 上用更少 tokens 拿到更好的 aggregate success；在 Terminal-Bench 2 上跨三個 model families 有 +5.1 到 +10.1 percentage points 的增益。

Ablation 也值得注意：提升主要來自 tools、middleware、long-term memory，而不是 system prompt。這和 harness engineering 的直覺一致：真正可轉移的是結構與工具行為，不是幾句策略性 prose。

### 對 agent harness / eval / workflow 的意義

這篇非常適合放進 harness engineering 核心閱讀。它把「observability」從 logging 層級提升到 evolution substrate：如果你想讓 agent 自動改善系統，必須讓它看得懂元件、看得懂經驗、看得懂自己上次改動的預測是否成立。

對 OpenClaw / coding-agent 系統來說，這篇的啟發是：若要讓 harness 持續進化，不應只保存 transcript，而要保存可壓縮、可索引、可回放、可歸因的失敗證據，並把每個改動和預期效果綁在一起。

### かに讀後判斷

今天 Harness Engineering 最推薦點開這篇。它是目前看到最貼近「harness 本身如何被工程化與自動演化」的 paper，而且有 Terminal-Bench / SWE-bench 量化結果，不只是概念文。

## 2. The Last Harness You'll Ever Build

- URL: https://arxiv.org/abs/2604.21003
- HTML: https://arxiv.org/html/2604.21003v3
- Authors: Haebin Seong et al.
- First version: 2026-04-22; v3: 2026-05-01
- Source type: arXiv preprint / framework proposal

### 這篇在說什麼

這篇也在談自動化 harness engineering，但更像是一個高層框架與 meta-learning formulation。作者說現在每個新 task domain 都需要專家手動設計 prompt、tools、orchestration logic、evaluation criteria。這種 domain-by-domain harness engineering 會成為 agent deployment 的瓶頸。

它提出兩層 loop。第一層是 Harness Evolution Loop：Worker Agent 用某個 harness 執行任務，Evaluator Agent 診斷失敗與評分，Evolution Agent 根據歷史嘗試修改 harness。第二層是 Meta-Evolution Loop：不只優化某個 harness，而是優化「如何演化 harness」的 blueprint，讓系統在新 domain 上更快收斂。

### 工程設計 / 架構重點

這篇的關鍵詞是 blueprint。它把 worker、初始 harness、evaluator、evolution agent 組成一個可被 meta-optimized 的物件。這比單純讓 agent 改自己的 prompt更抽象：系統想學會的是一套跨任務的 adaptation procedure。

它和 AHE 的差別在於，AHE 很重 observability 與 empirical harness components；這篇更重 formal framing，把 harness evolution 類比成 meta-learning。若要實作，還需要回答很多工程問題：失敗 evidence 怎麼壓縮、edit space 怎麼限制、evaluator 怎麼校準、如何避免 overfitting 某個 task family。

### 對 agent harness / eval / workflow 的意義

這篇適合當作自動 harness engineering 的概念邊界：第一步是自動改某個 domain 的 harness；下一步是自動改「改 harness 的方法」。對長期維護 agent 平台的人來說，這個問題會很現實，因為不同 domain 的工具、資料格式、成功條件都不一樣，不可能每次靠人工從零設計。

### かに讀後判斷

值得收藏，但今日推薦順位在 AHE 之後。這篇的想法很大，適合拿來思考 meta-harness / harness evolution 的長線方向；如果 Morris 想看立即可落地的設計與結果，先讀 AHE。
