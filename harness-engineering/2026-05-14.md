# Harness Engineering — 2026-05-14

## 1. HarnessBench: A Benchmark for Coding Agent Harnesses

- **類型**: Blog + GitHub repo
- **Link**: https://nyosegawa.com/en/posts/harness-bench/
- **GitHub**: https://github.com/nyosegawa/harness-bench

**📌 今日推薦點開**

Sakasegawa（@gyakuse）做了一件 harness engineering 領域一直缺的事：直接比較不同 coding agent harness 的表現，而不是只比模型。

HarnessBench 的設計：
- 9 個真實 OSS repo，每個 repo 3 個 issue（low/mid/high difficulty），共 27 個 task
- 14 種條件組合（Codex / Claude Code / Cursor Agent，不同模型 + 不同 harness）
- 378 次執行，用 hidden deterministic test 评分（不是 LLM-as-judge）
- 特別處理了 benchmaxxing 問題：用近期 PR、記錄 base/fixed commit、清洗 repo-local steering files

核心洞察：同一個模型（例如 GPT-5.5 或 Opus 4.7）在不同 harness 下的表現差異顯著。這直接證明了 harness 不是「包裝層」，而是性能的決定因素之一。

**工程意義**：這是目前少數直接把 Codex CLI / Claude Code / Cursor Agent 放在同一基準上比較的公開基準。對於在評估或選擇 coding agent harness 的團隊來說，這是一個實用的參考基準。

**閱讀判斷**：值得收藏和細看。如果你在做 agent eval 或 harness 設計，這個 benchmark 的方法論（hidden test、避免 LLM-as-judge、明確記錄 harness 版本）可以直接參考。

## 2. Workspace-Bench: Benchmarking AI Agents on Workspace Tasks with Large-Scale File Dependencies

- **arXiv**: 2605.03596
- **Link**: https://arxiv.org/abs/2605.03596

這篇提出 Workspace-Bench，評估 AI agent 在有大量檔案依賴的工作區中的表現。

**設計**：
- 5 個 worker profile、74 種檔案類型、20,476 個檔案（最大 20GB）
- 388 個 task，每個有自己的檔案依賴圖
- 7,399 個評分 rubric，要求 cross-file retrieval、contextual reasoning、adaptive editing

這個 benchmark 關注的不是單一任務的正確性，而是 agent 在真實工作區中的 workspace learning 能力——能不能識別、推理、利用、更新異質檔案之間的顯式和隱式依賴。

**閱讀判斷**：和 HarnessBench 互補——HarnessBench 比 harness，Workspace-Bench 比 workspace-level 的 agent 能力。如果你在做 multi-file agent，這篇的 task 設計和依賴圖建模值得參考。

## 3. Externalization in LLM Agents: A Unified Review of Memory, Skills, Protocols and Harness Engineering

- **arXiv**: 2604.08224
- **Link**: https://arxiv.org/abs/2604.08224
- **Authors**: Chenyu Zhou, Huacan Chai, Wenteng Chen, et al. (Shanghai Jiao Tong University, CMU, OPPO)
- **Type**: 54 pages tech report

**📌 今日推薦點開**

這篇是今年 harness engineering 領域最重要的一篇統一框架論文。核心論點很清晰：LLM agent 的進步越來越不是靠改模型權重，而是靠「外化」（externalization）——把認知負擔從模型內部搬到外部基礎設施。借鏡 Norman 的 cognitive artifacts 理論，作者論證外化的力量不在於加輔助元件，而在於它把難題做了「表徵轉換」（representational transformation），讓模型用已有的能力就能更可靠地解決問題。

三種外化形式：
1. **Memory 外化狀態**：解決「連續性問題」——LLM 的 context window 有限、session memory 幽靈般消失。Memory 讓積累的知識跨 session 持久化，核心轉換是「回憶變成辨識」。
2. **Skills 外化程序性專業**：解決「方差問題」——LLM 重複推導多步驟流程而非穩定執行。Skills 讓複雜工作流變成可重複載入的元件，核心轉換是「即興生成變成組合執行」。
3. **Protocols 外化互動結構**：解決「協調問題」——工具、服務、其他 agent 之間的互動如果只靠 free-form prompting 很脆弱。Protocols 讓互動遵循明確的契約而非臨時提示，核心轉換是「隨意協調變成結構化契約」。

Harness 是統一這三種外化的基礎設施層：
- Execution loop & control flow（執行迴圈）
- Sandboxing & execution isolation（沙箱與隔離）
- Human oversight & approval gates（人類監督與審批閘門）
- Observability & structured feedback（可觀測性）
- Configuration, permissions, policy encoding（組態與政策編碼）
- Context budget management（上下文預算管理）

論文用了一個很漂亮的認知神器類比：人類文明的發展本身就是一部認知外化史（語言→文字→印刷→數位計算），LLM agent 的外化弧線也在重演同樣的邏輯。

和今天早上看的 HarnessBench 比起來，這篇不比數字，而是給了一個理論框架來理解為什麼 harness engineering 重要、以及 harness 到底在解決什麼問題。兩篇互補——HarnessBench 是實證，Externalization 是理論。

**閱讀判斷**：如果你在思考 agent 架構的全局圖，或需要向別人解釋「為什麼 harness engineering 重要」，這篇是目前最完整的理論框架。54 頁的篇幅很厚，但 §1-2 和 §6 是核心，可以直接讀這兩章。對於已經在實做 harness 的人，§6.2 的六個分析維度和 §7.3 的 parametric vs. externalized trade-off 空間尤其值得細看。

## 4. ProgramBench: Can Language Models Rebuild Programs From Scratch?

- **arXiv**: 2605.03546
- **Link**: https://arxiv.org/abs/2605.03546
- **Authors**: John Yang, Kilian Lieret, Jeffrey Ma, et al. (Meta FAIR, Stanford, Harvard)

ProgramBench 是一個測試軟體工程 agent「從零建構完整程式」能力的基準——不是修 bug 或加功能，而是給定一個程式和文件，agent 要自己架構並實作出匹配原始行為的 codebase。

**設計**：
- 200 個 task，從小型 CLI 工具到 FFmpeg、SQLite、PHP interpreter 等大型軟體
- 給定 gold executable + 文件，agent 必須從零寫出 source code + build script
- 測試用 agent-driven fuzzing 自動生成行為測試，不規定實作結構
- 評估完全實作無關——不同演算法、不同語言都算過關，只要 input-output 行為匹配

**結果**：9 個 LLM 用 mini-SWE-agent 測試，沒有任何一個完全解決任何 task。最好的 Opus 4.7 只有 3% 的 task 能通過 95% 的測試。模型傾向寫 monolithic、單檔案的實作，和人類寫的模組化代碼差異顯著。

**和 harness engineering 的關係**：ProgramBench 測的是 agent 在「完全自主架構決策」場景下的能力極限，這和 harness 的關係很直接——harness 需要提供足夠的 scaffolding 來幫助 agent 做好架構決策，而不是讓 agent 在 vacuum 裡自己掙扎。這也說明了為什麼 ProgramBench 的結果這麼差——沒有 harness 支援的純 LLM 做架構決策還不夠好。

**閱讀判斷**：ProgramBench 的結果本身不意外（agent 做架構決策還很差），但 benchmark 設計值得關注——用 fuzzing 生成行為測試、實作無關的評估方式、以及從 CLI 到 interpreter 的廣度。對於做 coding agent harness 的人來說，這是一個很好的「上限測試」：如果你的 harness 讓 agent 在 SWE-bench 上表現很好但 ProgramBench 上很差，那可能是 harness 在幫 agent 處理局部問題，但沒有幫它做架構規劃。
