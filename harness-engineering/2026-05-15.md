## 1. Harness Engineering for AI Coding Agents: Constraints That Ship Reliable Code

- **來源**: Augment Code (augmentcode.com)
- **類型**: Engineering guide / blog article
- **Link**: https://www.augmentcode.com/guides/harness-engineering-ai-coding-agents

### 這篇在說什麼

Harness engineering 作為一個正式術語，最早的公開定義來自 2026 年 2 月：Mitchell Hashimoto（HashiCorp 共同創辦人、Terraform 作者）提出核心原則——「每當 agent 犯錯，工程師應該建一個確保它不再犯同樣錯誤的解決方案」；OpenAI 的 Ryan Lopopolo 隨後在官方部落格給出正式定義：「Humans steer. Agents execute.」LangChain 則濃縮為「Agent = Model + Harness」。

這篇 Augment Code 指南是目前為止最系統性的 harness engineering 實戰文件。它不是在定義一個模糊概念，而是在告訴你：如果你想讓 AI coding agent 在生產環境可靠運作，你需要建哪幾層控制、每層的具體實作長什麼樣子、以及最常見的坑在哪裡。

### 主要貢獻

1. **三層架構的完整定義**：Constraint Harnesses（feedforward）→ Feedback Loops（corrective）→ Quality Gates（enforcement）。每層有明確的定義、實作方式、和常見失敗模式。這比之前 DailyRead 看過的 OpenAI 原文更具體。
2. **Constraint Harness 細節**：不只是「寫 rules files」，而是明確說明 rules files 是 repository-scoped 的 instruction sets，在 session 開始時注入 agent context。OpenAI 的 production system 用「taste invariants」——一組小的、硬編碼的工程標準規則，全部設為 CI failure 而非 warning。
3. **Feedback Loop 的關鍵實作細節**：最容易被忽視的是 inline-disable rules（如 `// eslint-disable-next-line`）應該被禁用，因為 agent 會傾向 suppress violations 而不是 fix them。而 lint message 本身應該成為 prompt——不是「violation detected」，而是「use `logger.info({event: 'name', ...data})` instead of `console.log`」。
4. **Quality Gates 的 AI-specific 差異**：標準 CI pipeline 對 AI 生成的程式碼不夠，因為 agent 會引入傳統檢查抓不到的問題。一些團隊加 staleness gates 來抓依賴選擇不符合當前策略的程式碼。
5. **和 Prompt Engineering / Context Engineering 的清晰區分**：Prompt engineering 管單次互動、context engineering 管一個 context window 內的 token 組織、harness engineering 管整個 agent 系統——跨多個 context window、跨整個任務生命週期。

### 方法 / pipeline

文章描述的 harness 架構是一個分層系統：

**Layer 1: Constraint Harnesses (Feedforward)**
- Rules files：repository-scoped instruction sets，在 session 開始時注入 agent context
- Architecture lint configurations：編碼什麼是正確的程式碼
- Type systems：作為 feedforward controls
- 關鍵原則：所有規則設為 error 而非 warning，所以它們是 hard gates 而非 advisory signals

**Layer 2: Feedback Loops (Corrective)**
- Structured error signals 返回給 agent，使 autonomous self-correction 成為可能
- Lint messages 成為 prompts：錯誤訊息本身應該包含足夠資訊讓 agent 自行修復
- 禁用 inline-disable rules：防止 agent 繞過規則
- Spotify 的 Honk 系統作為 production 案例

**Layer 3: Quality Gates (Enforcement)**
- Standard CI + AI-specific checks
- Staleness gates：抓不符合當前策略的依賴選擇
- 所有規則設為 error，不是 warning

**Trade-off**: Over-constraining 是一個真實的失敗模式。Complexity limits 設太低會 flag 合法的重構；lint rules 拒絕合法 patterns 會拖慢 agent 而不改善品質。建議：start narrow, measure, then expand.
