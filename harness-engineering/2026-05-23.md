### 這篇在說什麼

這篇論文的核心問題非常具體且實際：兩篇論文用「同一個」模型跑「同一個」benchmark，報出來的數字卻差了十幾分，而且你無法從已發表的資料判斷差異來自哪裡——是 scaffold 不同？sampling 設定不同？用了不同 subset？evaluator 版本不同？作者把這個問題系統化：設計了一個 audit schema，然後拿 12 篇知名 benchmark 論文來打分，看它們到底揭露了多少讓讀者重現實驗所需的資訊。結果是 agent benchmark 平均只有 0.38/1.0 的揭露度。

這直接回應了 harness engineering 領域最根本的問題：如果連 harness specification 都不揭露，怎麼談 harness engineering 的最佳實踐？這篇不是提出新 harness 架構，而是揭露現有 harness 資訊的嚴重缺失——這是讓整個領域往前走的前提工作。

### 主要貢獻

1. **五欄位 audit schema**：Benchmark identity（版本、subset、grader）、Harness specification（scaffold、tools、stopping rule、environment image）、Inference settings（model、engine、sampling、seed、date）、Cost reporting（tokens、time、dollar cost）、Failure breakdown（結構化錯誤分類與計數）。這不是從理論推導，而是從 pilot scoring 的實際摩擦中迭代出來的。

2. **Codebook with boundary rules**：記錄了 scoring 過程中遇到的模糊地帶與裁決，例如「greedy decoding alone 不算 fully disclosed inference settings」、「repository tag ≠ container digest」、「qualitative error analysis ≠ failure breakdown」。這些邊界規則讓 audit 可重現，也讓未來的 auditor 可以具體不同意。

3. **12 篇論文的實證 audit**：Agent benchmark 均分 0.38、classical static benchmark 均分 0.66。最大缺口在 cost（0 篇揭露 inference cost）和 harness specification（0 篇揭露 content-addressed container image）。

4. **五個反覆出現的 failure modes**：Harness drift、Silent subsetting、Decoding underspecification、Cost invisibility、Grader opacity——命名了這些問題讓後續討論可以具體化。

### 方法 / pipeline

Audit 流程：每篇論文用兩個來源（ar5iv HTML + GitHub repo README/config），由一位 auditor 一次 pass 打分，每個欄位給 0/0.5/1 並附一句 justification。五欄位的 unweighted mean 即為 aggregate score。

Schema 設計原則：只從 paper + public repo 就能回答（不需要跑模型）；一小時內可完成一篇；1.0 分代表「有能力的讀者可以嘗試 faithful re-execution」，不是「實驗設計正確」。

Codebook 的演進很有意思：作者最初沒有 codebook，打到第四篇就必須加。很多邊界規則是「作者自己跟自己意見不一致」時才浮現的——這正是 codebook 的價值所在。

### 實驗設計

- **Corpus**：12 篇 benchmark 論文，8 篇 agent（SWE-bench、WebArena、VisualWebArena、OSWorld、GAIA、AgentBench、AgentBoard、MLE-bench）、4 篇 classical static（HumanEval、MBPP、GSM8K、MMLU）。原計畫 15 篇，因為 ar5iv 渲染失敗、HTTP 403 等技術問題降到 12 篇。
- **Scoring**：單一 auditor、單次 pass，這是明確承認的限制。
- **主要數字**：Agent benchmark mean = 0.38，Classical static mean = 0.66。最弱維度是 cost（8 篇 agent paper 全部 0 分）和 harness specification（environment image 全部 0 分或 0.5 分，沒有任何一篇用 Docker digest）。
- **有趣細節**：兩篇論文的 ar5iv HTML 渲染失敗；一篇被排除因為無法取得足夠文本；vendor blog 回 HTTP 403。這些「取用困難」本身就是一種 disclosure 問題的側面。
- **已讀來源限制**：Section V 的 walkthrough 和 per-paper scores 已完整讀過，Section VI–VII（adoption discussion）快速掃過。Appendix 的 per-paper scoring details 尚未逐篇核對。

### かに讀後判斷

這篇對 harness engineering 的價值不在提出新 harness，而在揭露現有 harness 資訊的嚴重不足。五個 failure modes 的命名（尤其是 harness drift 和 cost invisibility）是對前幾天 DailyRead 討論過的 AHE（2604.25850）和 "Code as Agent Harness"（2605.18747）的直接補充——AHE 討論怎麼自動演化 harness，這篇提醒我們連最基本的 harness 資訊都沒揭露。

值得點開深讀。優先看：Section V 的兩個 walkthrough（具體展示怎麼打分、哪些地方難判斷）；Table III–IV 的 per-dimension 分數（直接看 SWE-bench 相關論文在 harness specification 欄位的得分）；Codebook（附錄或 supplementary），因為 boundary rules 是這篇最可持續的貢獻。如果 Morris 關心 agent benchmark 的 reproducibility，Table III 的 harness specification 欄是必看。

跟前幾天 DailyRead 的關係：AHE（2604.25850）證明了 harness 可以自動演化、帶來效能提升；"Harness Engineering as Categorical Architecture"（2605.12239）試圖形式化 harness 的組合性質；這篇則從相反方向出發——你連 harness 是什麼都不告訴我，怎麼談工程？三者形成一個完整的問題空間：specify → formalize → evolve。
