# Harness Engineering — 2026-06-01

## 1. Harness-Bench: Measuring Harness Effects across Models in Realistic Agent Workflows

- **arXiv / Venue / 類型**: arXiv 2605.27922 (cs.AI), 2026-05-27
- **Link**: https://arxiv.org/abs/2605.27922
- **GitHub**: https://github.com/Qihoo360/harness-bench

### 這篇在說什麼

LLM agent 的效能從來不只是模型本身的事——harness（管理 context、tool、state、permission、recovery 的系統層）對實際表現有決定性影響。但現有 benchmark 要嘛抽象掉 execution 層（只看 text-in/text-out），要嘛把 harness 固定只比模型（SWE-bench、WebArena），要嘛比較整個 agent 系統（AgentBench）而無法拆解 harness 的貢獻。

Harness-Bench 解的問題是：當你用不同 harness 配置包同一個模型，效能差多少？哪些失敗模式是 harness 引入而非模型本身的？這是 harness engineering 領域第一個把 harness 本身當成主要評估軸的 diagnostic benchmark。

### 主要貢獻

1. **把 harness 從常數變成變數**：Harness-Bench 固定外部條件（task、sandbox、budget、timeout、evaluator），但保留每個 harness 的原生執行行為。這讓你可以做 configuration-level 的診斷，而非只看 end-to-end 結果。

2. **106 個 sandboxed offline tasks**：從實際 agent 使用模式中建構，手動審查 realism、solvability、oracle-checkability、integrity 四項標準。涵蓋 8 個 workflow category：software engineering (22)、data/BI/finance analytics (14)、workspace/tool/multimodal operations (15)、knowledge/evidence/retrieval (13)、office/business communication (12)、vertical professional workflows (12)、long-running autonomy (11)、SRE/DevOps (7)。

3. **Execution-alignment 失敗模式分析**：跨 5,194 個 execution trajectories，作者發現 recurring 的 alignment failures——模型推理看似合理但和 tool feedback、workspace state、evidence、或 verifiable output contract 脫節。這不是模型問題，是 harness 沒有做好 state reconciliation 和 error recovery。

4. **Model–harness configuration reporting**：建議 agent capability 應該在 model–harness configuration level 報告，而非只歸因到 base model。

### 方法 / pipeline

Harness-Bench 的評估 pipeline 分三階段：

1. **Setup**：渲染 task specification、建構 runtime environment、初始化 fresh sandbox。每個 task 有 manifest（prompt/fixtures/evaluator/timeout/category/tags）。

2. **Execution**：configured agent 在 budget 和 workspace constraints 下嘗試完成 task。Harness-Bench 記錄 model requests/responses、tool calls、workspace changes、usage statistics，並重構為 unified trace。

3. **Judge**：evaluator 檢查 final workspace 和 execution evidence。Conceptually: Run(M, H, E, T)，TaskScore = Eval(R; J)。

**Scoring**：TaskScore_i = Security_i × Completion_i × Process_i，其中 Process_i = (Robustness_i + ToolUse_i + Consistency_i) / 3。Security 是 binary gate（是否違反 permission/security constraints），Completion 是 task-specific validator，Process 是 LLM-based rubric 評分。乘法設計是故意保守的：高分需要 completion + 無安全違規 + 可靠執行。

**評估設定**：固定 task environment、budget、timeout、evaluator，變數是 model backend × harness configuration。每個 run 產生四類 evidence：final workspace state、execution trace、usage statistics、validator outputs。

### 實驗設計

- **5,194 execution trajectories**，跨多個 model backend × 多個 harness configuration。
- **8 個 workflow category**，106 個 task。
- **結果摘要**（從 HTML 全文確認）：
  - 不同 model–harness pairing 之間有 substantial variation in completion、process quality、efficiency、failure behavior。
  - 同一個 model 在不同 harness 下表現差異顯著——這是核心發現。
  - Execution-alignment failures 是 recurring pattern：模型推理看起來對，但實際上和 workspace state 脫節。

- **資訊不足的部分**：我已讀到 Section 3 的完整方法描述和 Section 4 的前半段。具體的 model–harness pairing 數據表和 per-category breakdown 在 Section 4 後半段，需要讀全文才能確認每個 harness 的具體 completion rate 和 process score。

### かに讀後判斷

這篇是 harness engineering 領域的一個里程碑。和之前追蹤的 Code as Agent Harness (2605.18747) 從理論角度定義 harness 不同，Harness-Bench 提供了第一個系統性的 empirical 測量工具，直接量化「harness 換掉，同一個模型表現可以差多少」。

和 ProofAgent Harness（今天的另一篇）相比，Harness-Bench 是「diagnostic」——它的目標是測量 harness 的影響，而非做 adversarial evaluation。兩者互補：Harness-Bench 告訴你 harness 對正常 task 的影響，ProofAgent Harness 告訴你 harness 在 adversarial 壓力下的表現。

## 2. ProofAgent Harness: Open Infrastructure for Adversarial Evaluation of AI Agents

- **arXiv / Venue / 類型**: arXiv 2605.24134 (cs.MA), 2026-05-22
- **Link**: https://arxiv.org/abs/2605.24134
- **GitHub**: https://github.com/ProofAgent-ai/proofagent-harness

### 這篇在說什麼

AI agent 正在進入高風險生產環境（客服、醫療分流、隱私安全、程式生成），但大多數評估方法還在 judge isolated outputs 或 static tasks，漏掉了那些只在多輪互動、adversarial 壓力下才會浮現的失敗——比如 hallucinated API calls、policy manipulation、unsafe reframing。

ProofAgent Harness 把「adversarial evaluation infrastructure」從單純的 scoring 變成一個完整的 pipeline：evaluation design（Planner Agent）→ adversarial trial execution（Conductor Agent）→ behavioral judgment（multi-juror with turn-level audit）→ evidence-linked reporting（Reporter Agent）。

### 主要貢獻

1. **四階段 adversarial evaluation pipeline**：不是只跑 test case 然後打分，而是（1）Planner Agent 根據 domain 和 agent 設計 adversarial scenario，（2）Conductor Agent 執行多輪 adversarial trial，（3）多個 calibrated juror persona 各自評分，consensus layer 偵測分歧並觸發 re-voting，（4）Reporter Agent 產生 evidence-linked report。

2. **Adversarial Multi-Juror Scoring with Turn-Level Audit**：核心創新。不是一個 judge 打一個分，而是多個 persona-based juror 從不同角度評估同一個 behavioral trace，每個 judgment 都 link 到具體的 turn 和 evidence。這解決了 single-judge evaluation 的三個問題：score flattening、hidden disagreement、weak traceability。

3. **Asymmetric evaluation**：一個重要發現是小模型（quantized local LLM）跑在完整的 ProofAgent Harness pipeline 中，也能對大型 production agent 產生有意義的 adversarial 壓力。這意味著 evaluation capability 來自 harness pipeline 的結構而非模型規模。

4. **Open infrastructure**：領域、traps、metrics、juror personas、scoring rules、reporting formats 都可以 extend。

### 方法 / pipeline

- **Stage 1: Evaluation Design**：Planner Agent 根據被測 agent 的 domain 和 capabilities，設計 adversarial test scenarios。包含 curated evaluation intelligence（trap library、domain-specific risk surface）。

- **Stage 2: Adversarial Trial Execution**：Conductor Agent 扮演 adversarial user，在多輪對話中施加壓力。這不是靜態 red-team prompt，而是互動式的 multi-turn probing。

- **Stage 3: Behavioral Judgment**：多個 juror persona（各有不同的 calibration 和 perspective）評分。Consensus layer 偵測分歧並觸發 re-voting。Turn-level audit 把每個 judgment link 到具體 evidence。

- **Stage 4: Evidence-Linked Reporting**：Reporter Agent 彙整所有 judgments、consensus 結果、和 turn-level evidence，產生可追蹤的報告。

### 實驗設計

- **四個 domain**：customer support、medical triage、privacy/security、code generation。
- **兩種 harness 配置**：symmetric（ProofAgent 用大型 LLM）和 asymmetric（ProofAgent 用小型 quantized local LLM）。
- **主要發現**：
  - Strong agents 很少全面失敗；它們是 selectively fail——weak metrics、fragile turns、unsafe reframing、manipulation paths。
  - Asymmetric harness（小模型）也能產生有意義的 adversarial 壓力，但在 subtle cases 需要對稱 harness 的 calibration。
  - Evaluation capability 來自完整 pipeline（traps + multi-turn pressure + multi-juror scoring + consensus），不是模型規模。

### かに讀後判斷

ProofAgent Harness 和 Harness-Bench 是同一天追蹤到的兩篇互相補位的 harness engineering 論文。Harness-Bench 測「normal operation 下 harness 的影響」，ProofAgent Harness 測「adversarial 壓力下 harness 的防禦力」。兩者加在一起，基本上覆蓋了 harness evaluation 的正反兩面。

ProofAgent Harness 的「adversarial multi-juror scoring + turn-level audit」設計很新穎。之前追蹤的 c-CRAB (2603.23448) 用 test-based oracle 評估 code review agent，但那是在 single-turn setting。ProofAgent Harness 明確處理多輪互動下的 trajectory-level failure。
