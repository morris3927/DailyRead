# Harness Engineering — 2026-06-15

## 1. How AI Agents Are Restructuring the Software Paradigm (Agentic Engineering)

- **arXiv**: 2606.05608
- **Link**: https://arxiv.org/abs/2606.05608
- **Authors**: (LangChain collaborative)
- **類型**: arXiv preprint (position paper), 引用 LangChain 2026 年 4 月的 Agentic Engineering 定義

### 這篇在說什麼

這篇不是 incremental tool paper，而是一篇立場論文（position paper），論證 AI agents 不只是軟體工程的「新工具」，而是從根本上重新定義了「軟體是什麼」。核心論點：在傳統軟體中，code 是決策邏輯的載體——工程師把每個決定都寫死在 code 裡；在 agentic software 中，agent 本身就是軟體，code 只是 agent 推理過程中的臨時工具，用完即丟。

作者提出三個主張：（1）第一性原理必然性——傳統軟體的複雜度縮放定律要求人類工程師窮舉所有決策，而 LLM 的推理能力隨訓練計算量增長；（2）軟體被重新定義而非取代——從「AI → Software → Result」收縮為「Agent → Result」，但 agent 本身還是軟體；（3）Agentic Engineering 作為新興學科——它的核心研究對象是 agent systems 而非靜態 source code，控制模型是 LLM-driven 而非 human-predefined，人類角色是意圖架構師而非代碼作者。

### 主要貢獻

1. **形式化區分**：傳統軟體 S=(C,D,E)（計算資源、靜態決策規則、執行環境）vs. Agentic 系統 A=(M,T,M,Π)（LLM 推理引擎、工具集、記憶子系統、規劃機制）。核心區別：D 是靜態的（人類預寫），而 M 的決策邏輯在運行時生成。

2. **三階段軟體交付範式**：Licensed Software → SaaS → Agent-as-a-Service (AaaS)。每次轉移都是把更多複雜度從用戶端移到供應端，AaaS 把決策複雜度也移過去了——用戶只需說「我要什麼結果」。

3. **複雜度縮放論證**：對 n 個組件的系統，可能的互動拓撲數量是 2^(n choose 2)，超指數增長。人類認知容量基本固定，LLM 的有效容量 C_M 隨模型規模和訓練計算量增長——這是一個質的變化。

4. **四階段演化路線圖**：（1）Augmented Engineering（當前）→（2）Agentic Workflows（agent 處理明確任務）→（3）Autonomous Agent Systems（agent 系統自我演化）→（4）Self-Evolving Ecosystems（agent 生態系自主演化）。

5. **實證分析**：引用 SWE-bench Verified、EvoClaw、LangChain 多 agent 協作研究的數據，展示 agentic paradigm 的潛力和當前限制。

### 方法 / pipeline

這篇是 position paper，沒有實驗 pipeline。但它的論證結構清晰：

1. **第一性原理分析**（§2）：形式化定義傳統軟體和 agentic 系統，推導複雜度縮放論證
2. **歷史範式分析**（§3）：Licensed Software → SaaS → AaaS 的演化邏輯
3. **學科定義**（§4）：Agentic Engineering 的核心概念、工具、度量
4. **實證回顧**（§5）：SWE-bench Verified、EvoClaw 等基準的結果分析
5. **路線圖**（§6）：四階段演化路線
6. **實踐建議**（§7）：給從業者的建議

### かに讀後判斷

這篇 position paper 對 harness engineering 的意義很直接——如果 Agentic Engineering 是一個新學科，那 harness 就是這個學科的核心工程實踐。論文的核心論點「Agent = Model + Harness」和 Addy Osmani 的 harness engineering 文章完全一致，但這篇從第一性原理出發做了更系統的論證。

值得注意的幾個點：
- **複雜度縮放論證**很有力——人類認知容量固定 vs. LLM 容量隨計算量增長，這是 agentic paradigm 的根本動力，不只是市場偏好
- **「AI → Software → Result」vs.「Agent → Result」**的區分很重要——中間的 Software 層消失，code 變成臨時工具
- 但論文對 Agentic Engineering 的「當前限制」討論偏樂觀——SWE-bench 的數據也顯示 agent 的可靠性還遠不夠生產部署

和昨天看的 Agent Reliability Science（2602.16666）形成強烈對話：那邊說「可靠性提升滯後」，這邊說「範式轉移正在發生」。真實情況可能是兩者並存——範式確實在轉移，但可靠性問題讓轉移速度比樂觀者預期的慢。

## 2. Towards More Standardized AI Evaluation: From Models to Agents

- **arXiv**: 2602.18029
- **Link**: https://arxiv.org/abs/2602.18029
- **Authors**: (multi-institution)
- **類型**: arXiv preprint (survey/position paper)

### 這篇在說什麼

AI 評測有一個根本性的問題：我們還在用模型時代的評測方法來評估 agent 系統。模型評測問的是「這個輸出對不對」，agent 評測需要問的是「這個系統在時間推移中、在不確定性下、在約束條件下行為是否正確」——這是完全不同的問題。

作者論證，當前的評測實踐有三個系統性問題：（1）靜態基準和聚合分數掩蓋了系統行為的關鍵面向；（2）高基準分數常常誤導團隊；（3）agentic 系統從根本上改變了「效能測量」的意義。這篇不是提出新指標或更難的基準，而是澄清評測在 AI 時代的角色——不是表演秀，而是一門測量學科，為非確定性系統提供信任、迭代和治理的基礎。

### 主要貢獻

1. **評測角色的重新定義**：評測不是最後的 checkpoint，而是核心系統功能——控制功能。從「這個模型多好」到「我們能不能信任這個系統在變化中、在規模上按預期行為」。

2. **模型 vs. Agent 評測的系統性區分**：模型評測問「輸出正確嗎？」，agent 評測問「系統在時間中、在不確定下、在約束下行為正確嗎？」變異性是信號而非噪音，失敗可能反映 harness 問題而非能力問題。

3. **評測作為治理機制**：評測結果直接影響部署、回滾、擴展的組織決策。評測的產出必須可審計——基準套件、閾值、評分邏輯構成合規證據。

4. **8 步評測生命週期**：從早期小規模開始，隨系統成長逐步硬化為結構化套件、可靠性檢查和回歸防護。

5. **監管分析**：EU AI Act 和 NIST AI RMF 都要求評測，但都沒有定義具體怎麼做——評測成了法律義務但沒有穩定的技術含義。

### 方法 / pipeline

這是 survey/position paper，沒有實驗 pipeline。論證結構：

1. **§1 從輸出檢查到行為測量**：為什麼傳統評測方法不適用於 agent
2. **§2 評測作為核心系統功能**：8 步生命週期、治理角色、監管要求
3. **§3 評測管線的隱性失敗模式**：靜態基準、聚合分數、一次性成功標準的問題
4. **附錄**：8 步評測生命週期細節、從早期到信任系統的路線圖

### かに讀後判斷

這篇和昨天的 Agent Reliability Science（2602.16666）形成互補：那邊從安全關鍵工程借用 4 維度 12 指標做量化評測，這邊從測量學和治理角度做概念框架。兩篇的核心信息一致——評測需要從「看結果」轉向「看行為」，從一次性評分轉向持續監控。

## 3. Agentic CLEAR: Automating Multi-Level Evaluation of LLM Agents

- **arXiv**: 2605.22608
- **Link**: https://arxiv.org/abs/2605.22608
- **Authors**: Asaf Yehudai, Lilach Eden, Michal Shmueli-Scheuer (IBM Research)
- **類型**: arXiv preprint, 有開源代碼（https://ibm.biz/ACLEAR-Code），PyPI 包

### 這篇在說什麼

Agent 系統越來越強大，但也越來越脆弱——微妙的失敗模式、重複循環、子 agent 行為不對齊、跨步驟的錯誤傳播。現有的可觀測性平台（LangSmith、LangFuse）主要做日誌記錄，評測能力只限於基本指標聚合或單次 LLM-as-judge 評估。研究社群專注於錯誤分類法（靜態、手工設計）或高保真基準（需要大量工程）。

Agentic CLEAR 填補了一個缺口：自動化、動態、多層級的 agent 評測。它不只是看最終結果是否正確，而是在三個層級（system、trace、node）產生文字洞察，告訴你「什麼失敗了、為什麼、在哪裡重複出現」。

### 主要貢獻

1. **三層級評測方法**：Node 層級（每個 LLM call 的品質評分和批評）、Trace 層級（整個執行軌跡的品質評估）、System 層級（跨所有軌跡的模式聚合）。這三個層級對應不同粒度的診斷需求。

2. **Rubric 評測**：不是用預定義的錯誤分類，而是讓 LLM judge 為每個任務自動生成任務特定的評測標準，然後判斷軌跡是否滿足這些標準。這解決了「靜態分類法無法適應新領域」的問題。

3. **CLEAR 聚合**：把實例層級的回饋聚合成高層級洞察——node-specific patterns 和 system-wide patterns。每個洞察都連結到觸發它的具體步驟或軌跡。

4. **開源工具鏈**：PyPI 包、OpenTelemetry 相容格式、互動式 UI 儀表板。一個 CLI 命令就能跑完整評測。

### 方法 / pipeline

Agentic CLEAR 的兩階段流程：

**階段一：Trace 評測**（Algorithm 1）
- 對每條軌跡 t_n，LLM judge J 執行三種評估：
  1. **Node-wise Evaluation (J_s)**：對每個 (input, output) 對打分和批評
  2. **Trace-wise Evaluation (J_t)**：評估整條軌跡的品質
  3. **Rubric Evaluation**：J_r 生成任務特定標準 → J_v 判斷軌跡是否滿足

**階段二：Insight 聚合**（CLEAR）
- 把 node-wise 批評按 node 分組聚合 → node-specific patterns
- 把 trace-wise 和 rubric 評估聚合 → system-wide patterns
- 每個 pattern 連結到觸發它的具體實例

### 實驗設計

- **基準**：4 個基準（包括 SWE-bench 等），7 種 agentic 設定，數千次 LLM 調用
- **核心結果**：
  - Agentic CLEAR 產生的文字洞察與人工標注的錯誤高度對齊
  - 洞察能預測任務成功率
  - 自動生成的 rubric 比靜態分類法更能適應不同任務類型

### かに讀後判斷

Agentic CLEAR 和昨天的 Agent Reliability Science 以及今天的 Standardized AI Evaluation 形成了一個完整的評測光譜：

- **Agent Reliability Science**：4 維度 12 指標的量化評測，回答「agent 可靠嗎？」
- **Standardized AI Evaluation**：概念框架，回答「我們到底在測什麼、為什麼測？」
- **Agentic CLEAR**：自動化工具，回答「agent 哪裡失敗了、為什麼、怎麼修？」

三篇一起看，就是 harness engineering 的評測層：概念（為什麼測）→ 指標（測什麼）→ 工具（怎麼測）。

Agentic CLEAR 的 rubric 自動生成是個好設計——靜態分類法確實無法適應新領域，讓 LLM judge 為每個任務動態生成評測標準，既靈活又可解釋。但潛在問題是：LLM judge 本身的偏誤如何校正？如果 judge 和被評測的 agent 用同一個模型，系統性偏誤可能被掩蓋。
