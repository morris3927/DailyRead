# Harness Engineering — 2026-06-17

## 1. Gating the Deterministic Scaffold of a Production LLM Agent with a No-LLM, Regression-Locked Test Harness

- **arXiv**: 2606.11686
- **Link**: https://arxiv.org/abs/2606.11686
- **Authors**: Sawyer Zhang, Alexander Wang, Sophie Lei (Lumivate / Lumi)

### 這篇在說什麼

End-to-end task-success 是目前評估 LLM agent 的主流方式，但它只告訴你 agent 是否退步了，不告訴你哪裡退步了。當一個 multi-turn ordering agent 的成功率從 85% 掉到 80%，你不知道是 intent resolution、routing、escalation、safety validator 還是 memory 出了問題。要找出原因，你得重新跑整個 stochastic、每次幾分鐘的 agent episode，然後 bisect——慢、貴、噪音大。

這篇提出的解法是 layer-isolated evaluation：把一個已部署的 ordering agent 分解成固定分類的架構層（ontology pre-resolution、intent signals、routing、decomposition、escalation、safety、memory 等），每一層有自己的 assertion slice 在確定性的 no-LLM "pure" 模式下跑。整個 pure suite（238 baseline cases，23 slices）在 CI 裡 2.39 秒跑完，每次 PR 都對鎖定的 per-slice baseline 做回歸測試。

最核心的實驗結果是 **masking**：作者對七個非安全層逐一注入退步，結果 aggregate pass-rate 幾乎不動（−1.7 到 −5.9 pp），但對應的 slice 直接崩潰（−25 到 −91 pp）。也就是說，如果你只看整體指標，你根本發現不了問題。

### 主要貢獻

1. **Layer-isolated pure-mode harness**：把生產 agent 分解成 23 個 slice，每個 slice 有自己的確定性斷言，不需要任何 LLM call。整個 suite 在 2.39 秒內跑完，每個 PR 都鎖定 baseline 做回歸測試。

2. **Regression-injection 驗證**：對七個層逐一注入退步，證明 per-slice gate 能定位 aggregate metric 會遮蔽的回歸。注入層的 slice 在 5/7 案例中是受創最嚴重的，7/7 都是 top-3，平均排名 1.29（滿分 19 個 slice）。Off-diagonal 幾乎是平的——退步集中在對應的 slice。

3. **Cross-tenant 複製**：在第二個結構不同的租戶（Starbucks SG）上重複了所有七次注入，結果一致——不是單一目錄的 artifact。

4. **Coverage-honest baseline**：零 case 的 slice 報告 rate: null（未覆蓋），永遠不報 100%。一個綠色的 aggregate 無法隱藏未測試的層。這是一個 test-adequacy criterion——未覆蓋的 slice 數量本身是測試套件的品質信號。

5. **Honest positioning**：作者明確承認這是 evaluation-driven agent operations（Xia et al. 2024）的具體實現，方法論祖先來自 CheckList（Ribeiro et al. 2020），和 whole-workflow stochastic mutation testing（Bhardwaj 2026）互補而非競爭。

### 方法 / pipeline

- **Layer taxonomy**：agent 被分解為固定分類——L0 ontology pre-resolution、intent signals、speech-act；L2 tool routing；L3 sub-goal decomposition、constraint handling、tier escalation；L4 safety（price/SKU/allergen）、knowledge、memory；加上 cross-cutting envelope、defense、OOD-reject、reformulator、locale-fidelity、session-init。

- **Pure mode**：每個 slice 斷言一個層的 contract，基於確定性輸出，不呼叫任何 LLM。例如：ontology resolver 的 canonical ID、rule-based escalation 決策、reformulator 的字典替換、OOD 短路謂詞、server-side reprice、prompt envelope 的渲染區塊。每個 case ≈1ms 計算，完全可複製。

- **Locked baseline**：凍結的 baseline 記錄每個 slice 的 (total, passed, rate, failed_ids)。當前 baseline 是 238 cases × 23 slices @ 100%。零 case 的 slice 報告 null，不報 1.0。

- **Per-PR gate**：每次 PR 比較當前結果和鎖定 baseline，任何 per-slice rate 下降都 block merge。

- **Regression injection**：對七個非安全層逐一 monkeypatch 退化實現，重跑 pure suite，記錄 aggregate 和 per-slice 的 delta。每次注入都在全新構建的 runtime 上跑，避免狀態洩漏。

### 實驗設計

- **主體**：Lumivate 的生產 ordering agent（per-tenant, multi-turn, food-and-beverage）。
- **Pure suite 規模**：238 baseline cases（225 pure + 13 legacy），23 slices。225 cases 在 2.39 秒內完成。
- **Regression injection**：七個非安全層逐一退化。結果：
  - Aggregate delta: −1.7 到 −5.9 pp（六個 local regression），−95 pp（一個 foundational ontology case）
  - Matching slice delta: −25 到 −91 pp
  - 注入層的 slice 在 5/7 是 worst-hit，7/7 是 top-3，平均排名 1.29/19
  - Off-diagonal 近乎平坦——退步精確定位
- **Cross-tenant**：Starbucks SG 上七次注入全部複製。
- **目前能確認的**：layer taxonomy、pure mode 設計、regression injection 方法論和主要結果表格從 HTML 全文確認。Appendix 中的 sensitivity analysis 和 per-case 詳細結果需看 PDF。

### かに讀後判斷

這篇是 harness engineering 領域近期最紮實的工程論文。它解決的問題非常具體——生產環境中的 agent 回歸定位——而且解法優雅：不需要跑 stochastic agent，不需要 LLM call，2.4 秒就能告訴你哪一層出了問題。

和之前看過的 Self-Harness（2606.09498, 2026-06-16）形成有趣的對比：Self-Harness 讓 agent 自己改自己的 harness（feedforward 改進），這篇則是用 per-layer 回歸測試來定位退步（feedback 定位）。兩者互補——Self-Harness 改 harness，layer-isolated harness 驗證 harness 改動沒有引入回歸。

和 Martin Fowler 今天的那篇文章也直接呼應：Fowler 說「computational sensors」是便宜、快速、確定性的 feedback control，這篇的 pure-mode per-layer assertions 就是 computational sensors 的極致版本——連 LLM 都不需要呼叫。

值得 Morris 點開深讀，特別是：Table 2 的完整 slice taxonomy、Table 3 的 regression injection 結果、Listing 1 的 per-PR gate 演算法、以及 cross-tenant 複製的細節。這篇對任何在生產環境跑 LLM agent 的團隊都有直接參考價值。

## 2. Harness Engineering for Coding Agent Users

- **類型**: Blog article (martinfowler.com)
- **Link**: https://martinfowler.com/articles/harness-engineering.html
- **Author**: Martin Fowler (Thoughtworks)

### 這篇在說什麼

harness 這個詞現在已經變成「agent 中除了模型以外的所有東西」的簡稱——Agent = Model + Harness。但這個定義太寬了。Fowler 把它收斂到 coding agent 的 bounded context：harness 分為內建部分（system prompt、code retrieval、orchestration）和用戶可建構的外部部分（outer harness）。一個好的 outer harness 有兩個目標：提高 agent 第一次就做對的概率，和提供 feedback loop 讓 agent 在人類看到之前自我修正。

Fowler 提出的核心分析框架是兩個維度的矩陣：方向（feedforward vs. feedback）× 執行類型（computational vs. inferential）。這個框架把之前散落在各處的 harness 技術（AGENTS.md、Skills、linters、ArchUnit、mutation testing、AI code review）統一在一個語言下。

### 主要貢獻

1. **Feedforward / Feedback × Computational / Inferential 框架**：把 harness 技術組織成一個清晰的 2×2 矩陣，給了 harness engineering 一個統一的討論語言。之前大家各說各話（有人在說 AGENTS.md、有人在說 linter、有人在說 AI review），現在可以精確定位每個技術在 harness 中的角色。

2. **三個調節類別**：Maintainability harness（最容易，工具最成熟）、Architecture fitness harness（fitness functions）、Behaviour harness（最難、最關鍵但目前最薄弱）。這三個類別揭示了 harness engineering 的成熟度梯度。

3. **Steering loop 概念**：人類的 job 不是一次建好 harness 然後放手，而是持續觀察 agent 的失敗模式，迭代改進 feedforward 和 feedback controls。而且 AI 本身也可以幫忙改進 harness——寫 structural tests、從觀察到的 pattern 生成 draft rules、scaffold custom linters。

4. **Harnessability 概念**：不是每個 codebase 都一樣好 harness。強型別語言自帶 type-checking sensor、清晰模組邊界可以寫 architectural constraint rules、框架抽象掉了 agent 不需要操心的細節。Greenfield 可以從第一天 bake in harnessability，legacy 在最需要 harness 的地方最難建。

5. **Harness templates 的前瞻性提案**：企業的常見服務 topology（API 業務服務、事件處理服務、數據儀表板）可能演變成 harness templates——一組 guides + sensors 的捆綁包。未來團隊可能根據哪些 harness 已經可用來選擇 tech stack。

### 方法 / pipeline

這篇文章是概念框架文章，不是系統論文。它的「方法」是一個分析框架：

- **Feedforward controls (guides)**：在 agent 行動前預期問題，嘗試引導。例如 AGENTS.md、Skills、code mods、bootstrap scripts。
- **Feedback controls (sensors)**：在 agent 行動後觀察結果，幫助自我修正。例如 linters、structural tests、AI code review、mutation testing。
- **Computational 執行**：確定性、快速、CPU 運行。毫秒到秒級。
- **Inferential 執行**：語義分析、GPU/NPU 運行。慢、貴、非確定性。

Timing 原則：quality left——檢查盡早、盡快、盡便宜。從 commit 前（linters、fast tests）到 post-integration（mutation testing、broad code review）到 continuous monitoring（dead code、coverage quality、dependency scanning）到 runtime（SLO degradation、response quality sampling）。

### 實驗設計

這是一篇概念文章，沒有正式實驗。但 Fowler 提供了三個實證來源：

1. **Failure mode mapping**：把之前 catalogued 的 coding agent 失敗模式對應到 maintainability harness 的覆蓋範圍，發現 computational sensors 可以可靠地捕捉結構性問題，但無法可靠地捕捉高影響問題（misdiagnosis、overengineering、misunderstood instructions）。

2. **OpenAI 團隊的 harness 實踐**：layered architecture + custom linters + structural tests + recurring drift GC。

3. **Stripe 的 minions 實踐**：pre-push hooks + heuristic-based linter selection + blueprints 整合 feedback sensors。

缺少的證據：沒有系統性的量化實驗，沒有 A/B 測試，沒有 harness 有效性的嚴格衡量。文章明確承認行為 harness（behaviour harness）目前是最薄弱的一環——AI-generated tests 的品質還不夠好，approved fixtures 只在部分場景適用。

### かに讀後判斷

Fowler 的這篇文章是 harness engineering 領域目前最好的概念框架文章。它沒有提出新系統或新演算法，但它做了一件更重要的事：給了這個快速發展的領域一個統一的討論語言。

和今天第一篇 layer-isolated harness（2606.11686）的關係特別直接：Fowler 的「computational feedback sensors」概念在 layer-isolated harness 中被推到極致——連 LLM 都不需要的 pure-mode per-layer assertions。Fowler 的「coverage-honest baseline」概念（不讓綠色 aggregate 隱藏未測試層）也在 layer-isolated harness 中被具體實現。

和之前看過的 Self-Harness（2606.09498, 2026-06-16）的關係：Self-Harness 在 Fowler 的框架中屬於「inferential feedforward + inferential feedback」——agent 分析自己的失敗模式（inferential feedback），提出 harness 修改（inferential feedforward），然後用 regression test（computational feedback）驗證。

值得收藏但不需要今天深讀。這篇文章更適合當作 harness engineering 領域的「字典」和「地圖」，在讀其他論文時回來對照。特別有價值的是 Figure 1（bounded context）、feedforward/feedback × computational/inferential 的 examples 表、和三個 regulation categories 的討論。
