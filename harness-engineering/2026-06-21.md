# Harness Engineering — 2026-06-21

## 1. Human-on-the-Bridge: Scalable Evaluation for AI Agents

- **arXiv**: 2606.16871
- **Link**: https://arxiv.org/abs/2606.16871
- **Authors**: Fouad Bousetouane et al.

### 這篇在說什麼

現有的 AI agent 評估方法各自有用但零碎：benchmark 測固定能力、Human-in-the-Loop 保留專家判斷但不規模化、LLM-as-judge 依賴評估者設計、red teaming 往往是一次性的、trace auditing 需要明確規則。這篇提出 Human-on-the-Bridge（HOB），一個把人類專業知識放到「上游」而非「迴圈中」的 scalable evaluation paradigm。核心觀點是：人的角色不是每 run 都進來看，而是在測試開始前把 domain context、Red-Team Traps、Juror Personas、scoring guidelines、audit rules、fallback policies 一次 curate 好，然後讓 ProofAgent Harness 反覆執行這些 curated evaluation intelligence。

這個定位很清楚：HOB 不是「取代人類判斷」，而是「把人類判斷做成可重複使用的 infrastructure」——你 curate 一次，跑很多次，跨 agent 版本、跨 domain、跨模型。這跟 HITL 的差別不是有沒有人，而是人在哪裡、什麼時候介入。

### 主要貢獻

1. **Human-on-the-Bridge paradigm**：把 human expertise 從 per-run bottleneck 變成 reusable evaluation infrastructure。四個 pillar：Red-Team Traps（adversarial test scenarios）、Juror Personas（multi-juror scoring with different domain perspectives）、Scoring Guidelines + Audit Rules（trace-verifiable + subjective scoring 的分離）、Fallback Policies（當 agent 做了不可接受的事時的 escalation 和 recovery）。

2. **Objective vs. Subjective 分離**：論文明確區分「trace-verifiable detections」（可以從 execution trace 獨立驗證的，例如 phantom tool call、missing mandatory tool call、policy drift）和「subjective juror scores」（需要 domain perspective 的判斷）。這個區分很重要：前者一旦被 surface，驗證不依賴 evaluator model 大小；後者的品質隨 evaluator tier 變化。

3. **Asymmetric evaluation**：小模型 Harness LLM 可以挑戰 frontier LLM agent。在 23,500 agent turns 的實驗中，HOB 用較小的 Harness LLM 就能 surface 出 frontier agent 的行為和程序失敗。

4. **ProofAgent Harness 開源實作**：https://github.com/ProofAgent-ai/proofagent-harness

### 方法 / pipeline

HOB 的執行流程：

1. **Upstream curation**：專家在測試前準備 evaluation intelligence——domain context、adversarial scenarios（Red-Team Traps）、多個 Juror Personas（不同視角的 scoring viewpoints）、scoring guidelines、audit rules、fallback policies。這一步是人做的，但只做一次。

2. **ProofAgent Harness 執行**：
   - 多回合 adversarial evaluation：用 curated traps 觸發 agent
   - Trace capture：記錄 agent 的完整行為軌跡（tool calls、policy adherence、memory state）
   - Multi-juror scoring：多個 Juror Persona 獨立打分，每個有不同 domain perspective
   - Evidence-linked reporting：每個判斷都連到 trace 中的具體證據

3. **Asymmetric 設計**：Harness LLM 可以比被測的 agent LLM 小很多。因為 trace-verifiable detections 不需要大模型來驗證，而 Juror scoring 可以用 domain-specific personas 來補償模型能力的差距。

4. **四個 failure 類型**：論文特別強調四種 static benchmark 和 single-evaluator 容易 miss 的 failure：(a) phantom tool-call claims（agent 宣稱用了工具但沒真的 call）、(b) missing mandatory tool calls、(c) policy drift（多回合後偏離 policy）、(d) safe but non-resolving refusals（安全但不解決問題的拒絕）。

### 實驗設計

- **規模**：23,500 agent turns、47 evaluation configurations、470 run-level trials（每個 config 跑 10 次 50-turn runs 取中位數）。
- **Domains**：finance、healthcare、code generation。
- **Agent backbones**：frontier LLM-based agents。
- **Harness LLM tiers**：5 個不同大小的 Harness LLM tier（從小到大）。
- **主要發現**：
  - HOB 可以用較小的 Harness LLM surface 出 frontier agent 的行為失敗。
  - Trace-verifiable detections（phantom calls、missing calls、policy drift）不需要大模型來驗證。
  - Safe but non-resolving refusals 是一個重要但常被忽略的 failure mode。
  - Multi-juror scoring 比 single-evaluator 更穩定，且不同 juror perspective 會 catch 不同的問題。
- **Asymmetric 效果**：小 Harness LLM + curated traps 和 guidelines 可以達到比大 Harness LLM + naive prompting 更好的 evaluation 品質，說明 human-curated evaluation intelligence 的 ROI 比 brute-force 用大模型當 judge 高。

### かに讀後判斷

這篇跟 HarnessFix（2606.06324，已於 06-07 收錄）形成有趣的對照：HarnessFix 是修 harness，HOB 是用 harness 來評估。但兩者都把 harness 當成核心 abstration level——不是評估模型本身，而是評估模型+harness 的行為系統。HOB 的核心 insight 是「把人放到上游而不是迴圈中」，這跟 harness engineering 領域的趨勢一致：評估應該是可重複、可擴展的 infrastructure，不是每 run 的人力 bottleneck。

特別值得深讀的部分：(1) Section 3 的四個 pillar 設計（Red-Team Traps、Juror Personas、Scoring Guidelines + Audit Rules、Fallback Policies），(2) Section 4.7 的四種 failure 類型的具體案例分析，(3) Section 4.3 的 asymmetric evaluation 設計和結果——小模型 Harness 怎麼挑戰大模型 Agent 這個結果對實際部署很有意義。

## 2. SEAGym: An Evaluation Environment for Self-Evolving LLM Agents

- **arXiv**: 2606.17546
- **Link**: https://arxiv.org/abs/2606.17546
- **Authors**: Congjie Zheng, Chuanyi Xue, Bin Liang, Jun Yang, Changshui Zhang (Tsinghua University)

### 這篇在說什麼

Self-evolving agent（會自己更新 harness 的 agent）的評估問題不只是「最終 agent 分數高不高」，而是「更新過程本身健不健康」：更新是否帶來可複用的改進？是否 overfit 到最近任務？是否損害了舊能力？成本是否可控？中間 snapshot 是否可靠？現有的 agent benchmark 是靜態的——每個 task 是獨立 episode、agent state 被 reset、分數測的是一個固定 agent。這完全移除了 self-evolving agent 賴以運作的 state persistence。SEAGym 解決的正是這個 gap：把現有 benchmark（Harbor-compatible）轉成動態的 self-evolution 評估環境，支援 training batch、frozen update-validation、held-out ID/OOD transfer、replay diagnostics、snapshot 和 metric 記錄。

### 主要貢獻

1. **RL-style 環境建模**：把 self-evolution 建模為 MDP-style evaluation process，agent snapshot 是 (M, H_t) 其中 M 是固定 base model、H_t 是可變 harness state。環境控制 task sampling、feedback、schedule、evaluation views；agent 提供 policy 和 update rule。

2. **Evaluation views 分離**：把 dataset split 和 evaluation view 解耦。Train batches 提供 update evidence，validation views 和 test views 保留做 frozen assessment。四種 view：update-validation（追蹤中間 snapshot）、ID transfer（同分布 held-out）、OOD transfer（跨分布）、replay（測 retention 和 forgetting）。

3. **Schedule 參數化**：用 schedule 參數（state reset、task reuse、batch size、update timing）來表徵不同的 self-evolution 模式（single-task adaptation、online transfer、epoch-based batch learning），而不是用不同的 benchmark 格式。

4. **實證結果**：在 Terminal-Bench 2.0 和 HLE 上比較 ACE、TF-GRPO、AHE，發現：(a) 頻繁更新不一定改善 held-out performance、(b) 有用的中間 snapshot 之後可能 collapse、(c) source diversity 和 model backend 影響 harness reliability。

### 方法 / pipeline

SEAGym 的核心架構：

1. **MDP formulation**：ℳ = (S, A, P, R, ρ)，其中 state s_t 包含當前 agent snapshot、schedule position、和 task context。Agent snapshot A_t = (M, H_t)，M 是不可變的 base model，H_t 是可變的 harness state。

2. **Harbor 整合**：SEAGym 用 Harbor 做 task runner（容器化執行、verifier、parallel jobs），自己加 self-evolution schedule：train batches、frozen validation views、final held-out views、snapshot timing、metric computation。不改 benchmark 本身。

3. **Rollout/Update 分離**：rollout component 在當前 harness state 下跑任務、返回 trajectory batch；update component 消費 trajectory batch 並 apply method-specific update rule。不同方法（ACE、TF-GRPO、AHE）只寫 thin wrapper，保持 native update rule。

4. **Evaluation views**：
   - Update-validation：每個 epoch 結束後，用 frozen validation set 評估當前 snapshot
   - ID transfer：同分布 held-out test
   - OOD transfer：跨分布 held-out test
   - Replay：回到之前保存的 snapshot，測是否遺忘

### 實驗設計

- **Benchmarks**：Terminal-Bench 2.0（terminal task benchmark）和 HLE（Human-Level Evaluation，Math/Physics、CS/AI、Engineering domains）
- **Methods**：ACE、TF-GRPO、AHE，在 shared epoch/batch protocol 下比較
- **Schedule**：persistent state、repeated train batches、train-batch updates、epoch-end frozen update-validation
- **主要發現**：
  - 不同 self-evolution 機制產生不同的 update dynamics
  - Validation gains 不一定 transfer 到 held-out tasks
  - 有用的 intermediate snapshot 可能之後 regress 或 recover
  - Batch size、source diversity、和 rollout backend 影響 harness reliability
  - 頻繁更新 ≠ 持續改善

### かに讀後判斷

SEAGym 填補了 self-evolving agent 評估的重要缺口：現有 benchmark 都是靜態的，但 self-evolving agent 的核心恰恰是 harness state 的持續演變。SEAGym 的 schedule 參數化設計讓不同 self-evolution 方法可以在同一環境下公平比較，而 evaluation views 的分離讓你可以看到 update 過程的不同面向。

跟 HOB（同日收錄）的關係：HOB 聚焦在 behavioral and procedural failures（phantom calls、policy drift 等），SEAGym 聚焦在 harness update dynamics（forgetting、regression、transfer）。兩者互補：HOB 測 agent 行為是否可靠，SEAGym 測 agent 更新過程是否健康。
