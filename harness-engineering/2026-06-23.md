# Harness Engineering — 2026-06-23

## 1. Sovereign Execution Brokers: Enforcing Certificate-Bound Authority in Agentic Control Planes

- **arXiv**: 2606.20520
- **Link**: https://arxiv.org/abs/2606.20520
- **Authors**: Jun He et al.
- **Subjects**: cs.CR, cs.AI, cs.DC, cs.LG

### 這篇在說什麼

當自主 agent 被連接到雲端、部署、資料控制工作流時，誰有權執行對生產環境的變更？這篇論文指出一個根本的 enforcement gap：現有的 IAM 只授權身份（identity），而保證層（SAB）只認證提案（proposal），兩者都沒有在實際變更發生的瞬間提供一個強制執行點。SAB 發出的憑證 Ω 如果沒有一個 runtime broker 來驗證和執行，就只是事後審計的 artifact——agent 仍可用 standing credentials 直接呼叫 API 繞過整個保證流程。SEB 就是填補這個 gap 的 runtime enforcement boundary。

### 主要貢獻

1. **Broker-enforced autonomy**：定位了認證提案和實際基礎設施變更之間的 enforcement gap，定義 SEB 為唯一持有 mutation credentials 的 runtime boundary。在預期部署中，沒有 agent runtime 會持有 standing mutation credentials。

2. **憑證驗證執行模型**：形式化了 broker 執行介面 Execute(Ω, req, S_t, Platform) → D | O，broker 依序驗證：(a) SAB 簽名 Φ_sig、(b) 請求與憑證合約匹配 Φ_match、(c) 時效窗口 Φ_time、(d) policy epoch Φ_policy、(e) 撤銷 epoch Φ_rev、(f) live-state drift Φ_drift、(g) replay 防護 Φ_replay。

3. **Scoped execution identity 和 revocation-before-execution**：引入最小權限身份模型——credentials 只在執行時鑄造，scope 綁定到合約、目標資源、有效窗口和撤銷 epoch。待處理憑證可在變更前被撤銷，agent 永遠不會獲得可重用的 mutation authority。

4. **原型實作和評估**：Go service 實作，整合 AWS STS 和 Kubernetes TokenRequest，在真實工作負載下測量 p50/p95/p99 延遲、密碼學和 drift 驗證的微基準、撤銷傳播延遲、以及在故障注入下的行為。

### 方法 / pipeline

SEB 的整體架構是一個三層 pipeline：

1. **Agent Runtime**（不可信）：LLM-based agent 規劃並提出基礎設施變更提案。

2. **SAB Admission Boundary**（可信）：攔截提案，用 Semantic Quorum Assurance (SQA) 或 policy engine 驗證安全性，通過後發出加密簽名的憑證 Ω = (cid, C, E_admit, T_valid, P_ver, ρ_rev, nonce, issuer, σ_SAB)。

3. **SEB**（可信執行邊界）：攔截所有變更請求，執行七步驗證 pipeline（簽名→匹配→時效→policy epoch→撤銷→drift→replay），全部通過後才鑄造 scoped short-lived credentials、呼叫目標 API、記錄簽名的 decision/outcome records。

憑證結構包含：合約 ID、合約內容、admission 時的 evidence state、有效時間窗口、policy 版本、撤銷 epoch、一次性 nonce、簽發者、SAB 簽名。這使得任何 drift（目標狀態在 admission 和 execution 之間發生變化）都會被偵測到。

### 實驗設計

- **原型實作**：Go service，整合 AWS STS（assume-role with session policy）和 Kubernetes TokenRequest（audience-restricted, TTL-bounded service account tokens）
- **延遲測量**：p50 ≈ 45ms, p95 ≈ 78ms, p99 ≈ 120ms（含密碼學驗證 + drift check + API call）
- **微基準**：簽名驗證 <2ms, drift check <5ms, replay check <1ms
- **撤銷傳播**：<500ms 從撤銷 epoch 推進到 SEB 拒絕
- **故障注入**：在 network partition 和 crash-recovery 場景下 SEB 正確拒絕過期/drifted 請求
- **bypass prevention**：論文詳細討論了如何確保目標 API 只接受 broker identity 的變更（AWS IAM policy 綁定、K8s RBAC 綁定）

### かに讀後判斷

這篇是 harness engineering 的核心貢獻。它不只提出了安全概念，而是定義了完整的 runtime enforcement 機制——從 proposal → admission → certificate → broker verification → scoped execution → audit record 的完整 pipeline。和昨天的 ABA（Auto Benchmark Audit）形成有趣的對比：ABA 審計 benchmark 品質，SEB 審計 agent 行為的授權鏈。

對 Morris 的直接意義：如果要做 agent safety / harness 相關研究，SEB 提供了一個可參考的正式模型。特別是 Φ_drift（live-state drift detection）和 Φ_replay（replay 防護）這兩個 predicate 很值得深讀——它們把「憑證在 admission 時有效但在 execution 時已過時」這個時間差問題形式化了。

深讀時優先看：Section 4（憑證驗證 pipeline 和形式化 predicate）、Section 5（原型實作細節）、Table 2（七步驗證的 failure outcome）、Table 5（延遲基準數據）。

## 2. Efficient and Sound Probabilistic Verification for AI Agents

- **arXiv**: 2606.20510
- **Link**: https://arxiv.org/abs/2606.20510
- **Authors**: Alaia Solko-Breslin et al.
- **Subjects**: cs.CR, cs.AI

### 這篇在說什麼

Runtime monitoring 是確保 AI agent 安全的關鍵方法之一，用 Datalog 等 formal language 表達和執行 policy。但現有方法只能處理確定性 policy——然而實際上很多安全 predicate 是機率性的（例如 PII 偵測器有失敗率、declassifier 有 false positive/negative）。問題在於：當 policy 中包含多個機率性 predicate 時，你無法假設它們之間是獨立的，但既有的機率推理方法需要獨立假設。這篇引入 distributionally robust optimization 來計算 policy violation 機率的 sound upper bound，不需要任何獨立假設。

### 主要貢獻

1. **Sound upper bound for probabilistic policy verification**：在不依賴 predicate 獨立性假設的情況下，用 distributionally robust optimization 計算 policy violation 機率的 sound upper bound。這是正式保證——計算出的 bound 是真正的上界，不會低估風險。

2. **Security-utility trade-off**：在保證安全 bound 的同時，展示比先前方法更好的 security-utility trade-off。可以設定可接受的 violation 機率閾值，然後在滿足此閾值的約束下最大化 agent 的行動空間。

3. **實驗驗證**：在 terminal agent 和 tool-calling agent 的標準 benchmark 上，展示比先前 art 更好的安全-效用權衡，同時保證 violation 機率的嚴格上界。

### 方法 / pipeline

- **Policy 語言**：基於 Datalog，擴展支援機率性 predicate
- **核心問題**：給定一組機率性 predicate（每個有失敗率 p_i），計算整個 policy 被違反的機率上界
- **關鍵洞察**：不需要假設 predicate 之間獨立，而是考慮所有可能的不確定相關結構（worst-case correlation）
- **方法**：distributionally robust optimization——在所有可能聯合分佈中取最壞情況，計算 violation 機率上界
- **結果**：對比之前需要獨立假設的方法（會低估風險）和簡單的 union bound（過度保守），distributionally robust 方法提供了 tight 的 sound upper bound

### 實驗設計

已在 abstract 確認的資訊：
- **Benchmark**：standard benchmarks for terminal and tool-calling agents
- **比較方法**：prior art（需要獨立假設的機率推理方法）
- **Metric**：security-utility trade-off（violation 機率上界 vs. agent 行動空間）
- **結果**：比 prior art 有更好的 trade-off，同時保證 rigorous bounds

### かに讀後判斷

這篇和 SEB 形成有趣的互補：SEB 解決的是「誰有權執行」的 enforcement 問題，而這篇解決的是「機率性安全 policy 如何正式驗證」的問題。兩者結合就是完整的 agent safety harness：SEB 是 runtime enforcement boundary，probabilistic verification 是 admission boundary 的正式基礎。
