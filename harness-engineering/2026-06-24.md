# Harness Engineering — 2026-06-24

## 1. What makes a harness a harness: necessary and sufficient conditions for an agent harness

- **arXiv**: 2606.10106 | cs.AI, cs.MA, cs.SE, cs.PL
- **Link**: [arXiv HTML](https://arxiv.org/html/2606.10106v1)
- **深度**: 全文 HTML（~25K chars），已讀至 Section 6（六個真實 harness 的案例分析）

### 這篇在說什麼

「Harness」這個詞在軟體工程 + 生成式 AI 的圈子裡到處出現，但意思很亂——有時指整個產品（Claude Code, Codex CLI），有時指 evaluation scaffold（SWE-bench harness），有時又跟 agent framework、SDK、IDE plugin、orchestrator 混在一起。這篇論文不是提出新的 agent 或跑 benchmark，而是做了一件更基礎的事：給「agent harness」一個可操作的本質定義，附帶一個 inclusion/exclusion test，可以對任何系統判定「這是不是 harness」。

作者追了 harness 這個詞從馬具（tack）→ 測試 harness → ML evaluation harness → agent harness 的語意遷移，然後提出構成性定義（constitutive definition）：四個必要且充分條件。接著用六個真實系統（Claude Code, Codex CLI, Aider, Cline, OpenHands, SWE-agent）和五個邊界案例（agent framework, SDK, IDE plugin, eval harness, orchestrator）驗證定義的一致性。

### 主要貢獻

1. **Constitutive definition of agent harness**：一個系統是 agent harness，若且唯若它在 runtime 滿足四個條件：(i) Agent loop（交錯推理、行動、觀察）；(ii) Tool interface（讓模型感知和改變環境）；(iii) Context management（決定什麼進出 context window）；(iv) Control mechanisms（限制、驗證、確定性動作，讓執行更可信、可審計、可控）。

2. **Inclusion/exclusion test**：把定義變成一個可重複的判定程序。對每個系統，逐條檢查四個條件是否在 runtime 成立。結果：Claude Code、Codex CLI、Aider、Cline、OpenHands、SWE-agent 全部通過；LangGraph（只是 framework，沒有 runtime control）不通過；SWE-bench eval scaffold（只做事後評估，不是 runtime）不通過。

3. **Genealogy of the term**：從古法語 harneis（盔甲和馬具）到軟體工程的 test harness，到 ML 的 evaluation harness，到現在的 agent harness。關鍵轉變：前三種 harness 都是「事後觀察」，agent harness 則是「runtime 控制」——這是定義的 temporal clause，也是與 eval harness 的根本區別。

4. **Boundary delimitation**：清楚劃出 harness 和五個鄰近概念的邊界——agent framework（提供抽象但不控制 runtime）、SDK（提供 API 但不包含 loop 和 control）、IDE plugin（嵌入 IDE 但缺乏獨立的 context management）、eval harness（做事後評估不是 runtime control）、orchestrator（調度但不做 verification）。

### 方法 / pipeline

論文的方法是概念分析（conceptual analysis），不是實驗。但它的分析對象是六個真實系統，每個都做了詳細的 anatomy：

- **Claude Code**：Anthropic 的 coding agent。四個條件全部滿足：agent loop（ReAct loop with tool calls）、tool interface（file read/write/edit, bash execution, web fetch）、context management（dynamic context window management, file summarization）、control mechanisms（permission system, diff verification, command filtering）。

- **Codex CLI**：OpenAI 的 coding agent。四個條件滿足：agent loop、tool interface（similar to Claude Code）、context management（session management）、control mechanisms（sandbox execution, approval gates）。

- **Aider**：開源 coding assistant。四個條件滿足但 control 偏弱（no sandbox by default, relies on git diff for verification）。

- **Cline**：VS Code extension 但有獨立的 agent loop 和 control layer。

- **OpenHands**：開源 coding agent 平台。四個條件滿足。

- **SWE-agent**：為 SWE-bench 設計的 agent。四個條件滿足但 context management 較簡單。

### 實驗設計

這篇沒有傳統的實驗。它的驗證方式是：

1. **Inclusion test**：對六個真實 harness 逐條檢查四個條件，全部通過。
2. **Exclusion test**：對五個邊界概念逐條檢查，每個都至少缺少一個條件。
3. **Edge cases**：Aider 的 control 偏弱但仍滿足；LangGraph 只是 framework 不滿足 control；SWE-bench eval scaffold 不滿足 temporal clause。

### かに讀後判斷

這篇是 harness engineering 領域的基礎性概念工作。對 Morris 來說特別相關的幾點：

1. **定義了 control mechanisms 是 harness 的必要條件**：這跟昨天的 SEB（Sovereign Execution Broker）呼應——SEB 就是在填補「從認證到執行的最後一哩路」，是 harness 的 control layer 的一個具體實作。

2. **Temporal clause 很重要**：harness 在 runtime 控制，eval harness 在事後評估。這意味著當我們說「SWE-bench harness」時，我們說的是兩個不同的東西——SWE-bench 本身是 eval harness，但跑 SWE-bench 的那個 agent wrapper 是 agent harness。

3. **研究議程**：Section 7 提出了設計張力軸（design tension axes），包括 autonomy vs. control、context window management、verification scope 等，這些都是當前 harness 工程的核心問題。

建議深讀 Section 4（constitutive definition）和 Section 6（六個真實 harness 的應用），特別是每個系統的 anatomy figure。Section 5 的 boundary delimitation 也很值得看，釐清了 harness 和 framework/SDK/plugin/orchestrator 的差異。

## 2. Specifying AI-SDLC Processes: A Protocol Language for Human-Agent Boundaries

- **arXiv**: 2606.20615 | cs.AI, cs.MA, cs.PL, cs.SE
- **Link**: [arXiv](https://arxiv.org/abs/2606.20615)
- **深度**: 僅 abstract（已確認全文 HTML 存在，但未深入讀取）

### 這篇在說什麼

AI agent 現在是 SDLC 的 first-class team member，但沒有規範語言來表達人類-agent 之間的責任邊界、審批閘門和治理約束。現有做法把流程寫在 agent prompt 裡（會 drift），或者只覆蓋片段（access control、approval gates）。這篇提出一個 domain-specific language（DSL），用 protocol 的形式規範 AI-SDLC 流程，有形式語法、良好條件、操作語義和強制不變量。

### 主要貢獻

1. **Protocol language for AI-SDLC**：區分 policy（宣告意圖）和 mechanism（結構性強制），用 validation token 和 capability boundary 來約束流程非確定性。

2. **Failure rate analysis**：結構性強制的系統失敗率是 agent 和 validator 失敗率的加權乘積；行為性遵從則允許累積或近乎飽和的成長。

3. **2+N team pattern**：兩個人類 in-control 角色加 N 個專門化 agent member，形式化了經典的 Separation of Duties for AI-SDLC。

### 方法 / pipeline

這是一篇 position paper，有形式規範、失敗率分析和可行性演示。有 working implementation 但完整的實證評估是 future work。

### 實驗設計

目前只從 abstract 和 landing page 能確認：有 failure rate 的形式分析，有可行性演示，但沒有完整的實驗。明確標記為「position paper with formal specification, failure rate analysis, and feasibility demonstration」。

### かに讀後判斷

這篇和今天的 harness 定義論文有互補關係：harness 定義的是「什麼是 harness」，protocol language 定義的是「harness 內的人類-agent 邊界怎麼規範」。2+N team pattern 和 validation token 的想法對設計安全 harness 有參考價值。但因為是 position paper 且缺乏完整實驗，建議先快速掃過 abstract 和形式定義，不需要深讀。

## 3. Confidence Laundering in Agent Systems: Why Uncertainty Needs a Latent Carrier

- **arXiv**: 2606.20662 | cs.AI, cs.MA
- **Link**: [arXiv](https://arxiv.org/abs/2606.20662)
- **深度**: 僅 abstract

### 這篇在說什麼

現代 agent 系統把不確定性變成過度自信：脆弱的上游決策被包裝成「乾淨的中間產物」傳給下游，不確定性在介面交接處被洗掉（confidence laundering）。作者提出 latent uncertainty 作為不確定性載體，附著在決策交接點上，讓下游可以感知上游的脆弱性。

### 主要貢獻

1. **Confidence laundering**：定義了這個 failure mode——脆弱的上游狀態被重新包裝為程序上有效的產物，下游過度信任。
2. **Latent uncertainty carrier**：不取代文本，而是在決策交接點附著不確定性載體，保留 pre-commitment fragility。
3. **從 step-wise uncertainty estimation 轉向 uncertainty-preserving interface design**。

### 方法 / pipeline

Position paper 層級。提出概念框架，沒有實驗。

### 實驗設計

目前只有概念框架，沒有實驗數據。

### かに讀後判斷

概念很重要——跟今天的 Context Drift 那篇（2606.21666）形成有趣的對話：那篇講 agent 之間的 context 不同步造成幻覺，這篇講 agent 之間的不確定性在交接點被洗掉。兩篇合在一起，指向同一個設計原則：agent 之間的介面需要保留不確定性資訊，而不是假裝所有中間產物都是確定的。但這篇目前只有概念，不需要深讀。
