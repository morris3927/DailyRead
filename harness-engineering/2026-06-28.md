## 1. ActPlane: Programmable OS-Level Policy Enforcement for Agent Harnesses

- **arXiv**: 2606.25189
- **Link**: https://arxiv.org/abs/2606.25189

### 這篇在說什麼

AI agent 的 harness（模型之外的軟體層）需要 policy engine 來強制執行安全和有效性政策，例如「commit 前必須跑測試」。但現有方法有一個語義差距（semantic gap）：政策意圖用自然語言表達（「跑測試」），執行必須作用在具體系統行為上（哪個 test command）；而且許多政策涉及事件順序或資料流。Tool-call guardrails 只能攔截經過 tool layer 的行為，miss 掉 script 裡的 git commit 這種間接路徑；OS sandbox 控制資源存取而非行為，且返回不透明的 EPERM 錯誤讓 agent 無法理解。

ActPlane 的核心洞見：政策語境存在最接近任務的 agent 身上（agent 已經在讀 repo、理解任務、解析抽象引用），但強制執行必須在 OS 層（所有執行路徑都可見）。所以讓 agent 自己宣告政策，然後在 OS kernel 用 eBPF 強制執行。

### 主要貢獻

1. **64 個專案的實證研究**：分析 CLAUDE.md 和 AGENTS.md 指令檔中的 2,116 條陳述。64% 是政策（而非描述性語境）、83% 涉及系統行為、74% 依賴無法靜態預定義的語境。這量化了 tool-call interception 和 static policy 的不足。

2. **ActPlane 系統設計**：agent 用簡單 DSL 宣告政策（如 `kill exec "git" "commit" unless after exec "go" "test" exits 0`），ActPlane 編譯成 eBPF engine，用 information-flow control (IFC) 標記跨進程、檔案、網路操作的資料流，並用 policy domain 隔離不同 agent 的政策。政策可以有兩種執行模式：block/kill（拒絕並給語義回饋）和 notify（引導 agent）。

3. **Decision-compliance 和 safety benchmark 評估**：在 decision-compliance benchmark 上，ActPlane 比 prompt-filter、tool-regex、FIDES（tool-level IFC）和 feedback-free kernel IFC 多解決 2.0–3.2× 的政策違規，主要是因為涵蓋了 tool-call interception 看不到的間接執行路徑。在 361 個 personal-assistant 任务的 safety benchmark 上，agent 自己產生的安全政策作為 higher-authority rules 載入後，防止了 74% 的 baseline-unsafe 行為。End-to-end 開銷 1.9%，kernel build 開銷最高 8.4%。

### 方法 / pipeline

ActPlane 的設計邏輯：

- **Agent-authored policy**：agent 讀取 repo / task 語境後，把自然語言政策編譯成具體的 DSL 規則。例如「跑測試再 commit」→ `kill exec "git" "commit" unless after exec "go" "test" exits 0`。
- **IFC-based enforcement**：eBPF engine 維護 IFC labels，標記哪些資料來源影響了哪些物件，跨 process / file / network propagation。這讓跨事件政策（如「不能把 API key 寫到 log」）可以被強制執行。
- **Policy domains**：每個 agent process subtree 綁定一個 policy domain，隔離不同 agent 的政策，防止 sub-agent 弱化 parent 的安全約束。
- **Semantic feedback**：違規時不只返回 EPERM，而是返回具體的語義回饋（如「blocked: commit without tests; run npm test first」），讓 agent 可以修正行為。

### 實驗設計

- **Empirical study**：64 個含 CLAUDE.md / AGENTS.md 的 GitHub repo，2,116 條陳述，4 個 label（content type, topic, enforcement level, context requirement）。
- **Decision-compliance benchmark**：基於實證研究中的政策建構，比較 prompt-filter、tool-regex、FIDES、feedback-free kernel IFC。ActPlane 多解決 2.0–3.2× 違規。
- **Safety benchmark**：361 個 personal-assistant 任務，agent-generated 安全政策作為 higher-authority rules。74% baseline-unsafe 行為被防止。
- **Overhead**：End-to-end 1.9%（agent workload），kernel build 8.4%。
- **間接路徑覆蓋**：tool-call interception 看不到的路徑（如 agent 寫的 script 裡的 git commit）是 ActPlane 相對優勢的主要來源。

### かに讀後判斷

這篇是 harness engineering 領域的一個重要進展，因為它把政策強制執行從 tool layer 提升到 OS kernel，同時保留了 agent 語境的靈活性。agent-authored + OS-enforced 的設計是對現有 tool-call guardrails 和 static sandbox 的雙重超越。

和 2026-06-27 的 HarnessAudit（2605.14271，今天也收錄）直接互補：HarnessAudit 診斷 harness 的安全失敗模式，ActPlane 提供解決方案。和昨天 TMA-NM（2606.24322）的 write-time origin binding 也有呼應——兩者都在把信任標記下推到不可偽造的執行層（TMA-NM 在 memory 層，ActPlane 在 OS kernel 層）。

**值得 Morris 點開**。優先看 §2.2 的實證研究（量化了政策執行的需求層次）、§4 的 IFC 和 eBPF 實作細節、和 §5 的間接路徑覆蓋分析。如果對 agent safety 的系統面感興趣，這篇是必讀。

## 2. HarnessAudit: Auditing Agent Harness Safety

- **arXiv**: 2605.14271
- **Link**: https://arxiv.org/abs/2605.14271

### 這篇在說什麼

LLM agent 的 harness 可以在返回正確答案的同時，沿路存取未授權資源、洩漏語境給錯誤 agent、或觸發不可逆副作用——這些 mid-trajectory 違規在只評估最終輸出的 benchmark 上完全不可見。HarnessAudit 提出：agent safety 應該在 harness 層面而非 response 層面評估，且應該審計完整執行軌跡而非最終狀態。

### 主要貢獻

1. **Harness-centric safety formulation**：把 agent harness 定義為 policy-constrained execution system，在三個維度上審計——boundary compliance（是否遵守權限和資訊流邊界）、execution fidelity（是否通過合法中間步驟達成目標）、system stability（是否在擾動下維持安全和正確）。使用 hidden, agent-independent evidence channels（tool call logs、resource access、inter-component messages）。

2. **HarnessAudit-Bench**：210 個任務跨 8 個真實場景（金融、醫療、程式開發等），內嵌安全約束，同時在 single-agent 和 multi-agent 配置下實例化。這是目前最全面的 harness safety stress test。

3. **十個 harness 配置的實證分析**：跨 frontier models 和三個 multi-agent 框架。主要發現：(i) task completion 和 safe execution 不對齊，違規隨軌跡長度累積；(ii) 安全風險跨 domain、task type、agent role 變化；(iii) 大多數違規集中在 resource access 和 inter-agent information transfer；(iv) multi-agent collaboration 擴大安全風險面，但 harness design 設定了安全部署的上限。

### 方法 / pipeline

- **Three audit dimensions**：boundary compliance（是否越過權限/資訊流邊界）、execution fidelity（是否通過合法步驟達成目標）、system stability（是否在擾動下保持安全）。
- **Hidden evidence channels**：agent-independent 的軌跡記錄（tool calls、resource access、inter-agent messages），不依賴 agent 自報告。
- **Benchmark construction**：8 個真實 domain、210 任務、每個任務有顯式安全約束。single-agent 和 multi-agent 雙重配置。
- **Multi-agent focus**：特別關注 inter-component communication channels 的安全風險，這是 single-agent benchmark 忽略的。

### 實驗設計

- **Harness configurations**：10 個（跨 frontier models + 3 個 multi-agent frameworks）。
- **Key findings**：(i) 任務完成和安全執行不對齊；(ii) 違規隨軌跡長度累積；(iii) 資源存取和 agent 間資訊轉移是違規集中點；(iv) multi-agent 系統的安全風險面更大，但 harness design 決定安全上限。
- **目前從 HTML 前段和 abstract 能確認到以上結果**；詳細的 per-model 和 per-framework breakdown 需要看完整 PDF。

### かに讀後判斷

這篇和 ActPlane 是今天 harness engineering 的雙核心：HarnessAudit 診斷問題，ActPlane 提供一種解法。HarnessAudit 的貢獻不在於提出新方法，而在於系統性地定義了「harness safety」的三個審計維度，並提供了第一個跨 domain、跨 single/multi-agent 的 harness safety benchmark。

和昨天 2606.10749（Toward Secure LLM Agents survey）的關係：HarnessAudit 把 survey 中指出的「persistent state corruption 和 multi-agent propagation 是新興威脅」具體化為可測量的 benchmark 維度。和 ActPlane 的關係：HarnessAudit 的 boundary compliance 維度恰好是 ActPlane 的 IFC 標籤要強制執行的東西。

如果對 agent safety 的評估面感興趣，值得和 ActPlane 一起看。優先看 Figure 2（不同 harness 下的安全風險對比）和 §4 的 multi-agent 違規模式分析。

## 3. From Question Answering to Task Completion: A Survey on Agent System and Harness Design

- **arXiv**: 2606.20683
- **Link**: https://arxiv.org/abs/2606.20683

### 這篇在說什麼

這是一篇大型 survey，核心問題是：agent 的效能瓶頸在哪裡——在基礎模型、在執行 harness、還是在兩者的耦合？作者用 model–harness lens 來組織整個 survey，把 agent 定義為 foundation model + execution harness，然後追蹤四個範式（prompt engineering → workflow → context engineering → harness engineering + agent-native training with co-evolution），分解 harness 的六個執行期職責（observation, context, control, action, state, verification/governance），最後識別開放挑戰。

### 主要貢獻

1. **Model–harness decomposition**：把 agent 系統分析框架化為 foundation model × execution harness，明確區分模型能力和執行基礎設施對效能的貢獻。這不是新概念（SWE-agent、Codex、Claude Code 都已經這樣做），但這是第一次系統性 survey 把整個領域用這個 lens 組織起來。

2. **Four paradigms of agent engineering**：prompt engineering → workflow → context engineering → harness engineering + agent-native training。每個範式對應 harness 職責的不同分配方式。

3. **Six runtime responsibilities of the harness**：observation（感知環境）、context（管理上下文）、control（決策路由）、action（執行動作）、state（狀態管理）、verification/governance（驗證和治理）。這個分解比以往的 tool-use 或 agent-loop 描述更精細。

4. **Open challenges**：value-aware evaluation、safety、harness generalization、model–harness co-evolution。

### 方法 / pipeline

這是一篇 survey，沒有實驗方法。作者收集和組織了大量相關工作（GitHub repo 有完整列表），用 model–harness lens 統一解讀。

### 實驗設計

不適用（survey）。但作者系統性地回顧了從 SWE-agent 到 ActPlane 的 harness 設計演進，並識別了每個範式的主要代表作和局限。從 HTML 前段能確認 survey 的組織結構和主要論點，但完整的參考文獻和細節需要看 PDF。

### かに讀後判斷

這篇 survey 對 harness engineering 領域的定位非常及時。model–harness lens 把目前分散的 agent engineering 工作統一到一個可分析的框架下，六個 runtime responsibilities 的分解也比籠統的「agent loop」更有指導性。

和今天 ActPlane 的關係：ActPlane 的 DSL + eBPF + IFC 主要對應 harness 的 control 和 verification/governance 職責，而 ActPlane 的 agent-authored policy 設計呼應了 survey 中提到的「harness 作為可學習、可優化的物件」趨勢。和 HarnessAudit 的關係：HarnessAudit 的三個審計維度（boundary compliance, execution fidelity, system stability）對應了 harness 的 verification/governance 職責。
