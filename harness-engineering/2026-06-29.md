# Harness Engineering — 2026-06-29

## 1. Harness-MU: A Safe, Governed, and Effective Harness for Multi-User LLM Agents (2606.21856)

- **arXiv**: 2606.21856
- **Link**: https://arxiv.org/abs/2606.21856
- **Authors**: YuanJr Shiuan et al.
- **GitHub**: https://github.com/YuanJrShiuan/Harness-MulUser

### 這篇在說什麼

LLM agent 越來越多被部署在多人協作環境裡，但目前 LLM 的訓練範式是 single-principal（只服務一個用戶），所以當多個用戶同時和一個 agent 互動時，三個系統性失敗模式必然出現：未授權存取敏感資訊、衝突指令的混亂解決、高權限指令無法優先於低權限請求。Yang et al. (2026) 的 Muses-Bench 測了 20+ 個 frontier LLM，除了 GPT-5.2 外沒有一個能完全保護隱私。作者的核心洞見是：治理約束（誰有權、什麼被限制、誰的指令優先）是確定性的 runtime 變數，應該由執行掛鉤（execution hooks）強制執行，而不是交給 LLM 的機率性 safeguard。Harness-MU 是第一個 model-agnostic、zero-tuning 的多用戶 LLM agent harness 框架。

### 主要貢獻

1. **Harness-MU 框架**：第一個為 MPA（Multiple Principal–Agent）場景設計的全棧執行 harness，完整實例化了 Meng et al. (2026) 的六元素 tuple 形式化框架。
2. **四模組解耦架構**：Gatekeeper（存取控制）、Mediator（衝突解決）、per-user parallel Workers（並行處理）、ComplianceChecker（合規驗證），把語言生成和安全編排完全分離。
3. **Muses-Bench 上的全面驗證**：四個 frontier 模型上，Harness-MU 保證所有存取控制攻擊的隱私保護，同時 utility score 比 baseline 高 0.28–0.39，instruction-following accuracy 提升最高 48.9 個百分點。
4. **開源完整實現**：程式碼和資料全部公開。

### 方法 / pipeline

Harness-MU 的核心設計是「語言生成和安全編排分離」。四個模組的資料流：

1. **Gatekeeper**：接收所有用戶請求，根據存取控制策略（$\mathcal{A}uth: \mathcal{U} \times \mathcal{S} \to \{0,1\}$）過濾敏感資訊。這是確定性的、fail-closed 的邊界層，不依賴 LLM 的判斷。
2. **Mediator**：根據用戶權限層級（$\alpha_k$）解決衝突指令，確保高權限指令優先。
3. **Workers**：為每個用戶分配獨立的平行 LLM call，輸入是經過 Gatekeeper 過濾的上下文。
4. **ComplianceChecker**：驗證 LLM 輸出是否符合隱私和權限約束，不合規的回應被攔截。

形式化框架：每個用戶 $u_k$ 有治理配置 $\mathcal{P}_k = \langle \alpha_k, \mathcal{I}_k, \mathcal{C}_k \rangle$（權限、指令、隱私上下文）。環境狀態 $\mathcal{S} = \mathcal{S}_{share} \times \mathcal{C}_1 \times \cdots \times \mathcal{C}_N$，實現選擇性上下文可見性。多主體最佳化目標是權限加權效用最大化，同時滿足硬約束（隱私不洩漏、權限層級優先）。

這個設計直接繼承了 Meng et al. (2026) 的六元素 tuple $H = (E, T, C, S, L, V)$：
- $E$（execution loop）→ 四模組的運行循環
- $T$（tool registry）→ per-user 工具存取控制
- $C$（context manager）→ 選擇性上下文可見性
- $S$（state store）→ per-user 隔離狀態
- $L$（lifecycle hooks）→ Gatekeeper/Mediator/ComplianceChecker 掛鉤
- $V$（evaluation interface）→ Muses-Bench 評估

### 實驗設計

- **Benchmark**：Muses-Bench（Yang et al. 2026），三個壓力測試任務：多用戶指令遵循、跨用戶存取控制、會議協調。
- **模型**：四個 frontier open-weight 和 proprietary 模型家族。
- **主要結果**：
  - Privacy preservation：Harness-MU 在所有存取控制攻擊向量上保證完全隱私，baseline（直接 LLM + system prompt）全部失敗。
  - Utility score：比 baseline 高 0.28–0.39。
  - Instruction-following accuracy：提升最高 48.9 個百分點。
- **Ablation**：系統性分析四個模組的貢獻，Gatekeeper 是隱私的關鍵元件，Mediator 對衝突解決必不可少，ComplianceChecker 在多輪對話中防止隱私洩漏的累積效應。

### かに讀後判斷

這篇是 harness engineering 領域本週最重要的論文。它直接延續了 Meng et al. (2026) 的形式化框架（六元素 tuple），把 harness engineering 從 single-principal 擴展到 multi-principal 場景，並且用完整的四模組解耦架構展示了「語言生成和安全編排分離」的工程原則。對 Morris 的價值：

- 和 2026-06-28 的 ActPlane 形成互補：ActPlane 用 DSL + eBPF 在 OS kernel 層面做政策執行，Harness-MU 在 harness 層面做存取控制和衝突解決。兩者都在做「確定性的 runtime 約束 > 機率性的 LLM safeguard」。
- 和昨天的 HarnessAudit 形成對照：Audit 說「要審計 harness 的安全性」，Harness-MU 說「直接用解耦架構保證安全性」。
- MPA 場景是 agent 部署的真實需求——企業環境裡一個 agent 服務多個用戶是常態，不是邊緣案例。

## 2. NOVA: A Verification-Aware Agent Harness for Architecture Evolution in Industrial Recommender Systems (2606.27243)

- **arXiv**: 2606.27243
- **Link**: https://arxiv.org/abs/2606.27243

### 這篇在說什麼

工業級推薦系統的架構演化（比如從 RankMixer 升級到 MixFormer）需要跨模組的拓撲變更，但現有 AutoML 只調超參數、通用 coding agent 只管「程式能跑」，兩者都抓不到一類關鍵問題：程式能跑但推薦語義被破壞的「靜默失敗」（silent failure），比如誤刪 sequence masking、退化 self-attention 成 MLP、改壞 logit-fusion 路徑。NOVA 是一個 level-aware 的 agent harness，用 architecture gradient（一個受 SGD 啟發的非可微分更新信號）引導架構搜索，同時用多級驗證瀑布（verification cascade）攔截靜默失敗。

### 主要貢獻

1. **Architecture gradient**：聚合先前的修改、驗證診斷、metric 回饋和軌跡記憶，形成下一個修改方向的更新信號——不是隨機搜索，而是有方向性的演化。
2. **Silent-failure-aware verification cascade**：結構語義檢查 → 局部可執行性 → 離線效果 → 線上影響，四級驗證。無效候選被提前攔截，失敗模式記錄為「禁止方向」。
3. **L1–L4 task-level control**：根據任務複雜度和風險匹配自動化等級，高風險任務路由到 Copilot（人類監督）。
4. **工業部署驗證**：在服務超過十億用戶的廣告推薦系統中部署，L2 ScaleUp EPR 54.5%，L3 Literature-to-Production EPR 60.0%，比 coding-agent baseline 高出一倍以上。一個 Literature-to-Production 週期的人力時間縮短 13×。線上 A/B 測試中，選出的 L3 候選在三個 pCVR 目標上 GMV 提升 +1.25%、+1.70%、+2.02%，pCVR bias 降低 58.8%、66.7%、37.3%。

### 方法 / pipeline

NOVA 的架構演化流程：

1. **Architecture state** $A_t = (G_t, \phi_t, F_t)$：模型圖 + 結構超參 + 特徵配置。初始狀態從生產程式碼衍生。
2. **Modification** $e_t \in \mathcal{E}$：對 $A_t$ 做變更（如替換 attention 模組、修改 logit-fusion 路徑等），產生候選 $A_{t+1}$。
3. **Verification cascade**：候選必須通過四級檢查：
   - 結構語義（是否保留推薦語義）
   - 局部可執行性（能否跑通）
   - 離線效果（AUC 等指標）
   - 線上影響（A/B 測試）
   失敗的候選被記錄為「禁止方向」，避免重複搜索。
4. **Architecture gradient**：聚合歷史修改、驗證診斷、metric 回饋、軌跡記憶，作為下一個修改方向的指導信號。
5. **L1–L4 control**：低風險任務 AutoRun，高風險任務路由到 Copilot（人類監督）。

### 實驗設計

- **L2 ScaleUp**：EPR 54.5%（coding-agent baseline 約一半）。
- **L3 Literature-to-Production**：EPR 60.0%，比人類專家流程的 EPR 高出一倍以上。
- **人力時間**：一個 Lit-to-Prod 週期縮短 13×。
- **線上 A/B**：三個 pCVR 目標的 GMV 提升 +1.25%/+1.70%/+2.02%，bias 降低 58.8%/66.7%/37.3%。
- **Ablation**：feedback-ablated variant 隔離了 architecture gradient 中回饋信號的價值。

### かに讀後判斷

NOVA 是 harness engineering 在工業場景的紮實應用。它的核心洞見「可跑 ≠ 推薦語義正確」對所有 agent harness 設計都有啟示：評估不只是「程式能跑」，而是要在正確的層級驗證正確的語義約束。architecture gradient 的設計（把驗證失敗轉為禁止方向）是一個優雅的搜索策略，和 ActPlane 的「把 OS kernel 回饋轉為 DSL 策略更新」異曲同工。
