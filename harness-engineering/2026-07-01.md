# Harness Engineering — 2026-07-01

## 1. LemonHarness: Integrated Execution Framework for Long-Horizon Agents

- **arXiv**: 2606.24311
- **Link**: https://arxiv.org/abs/2606.24311
- **Authors**: Kailong Ren, Fubo Sun, Jiachen Liu, et al. (Lenovo AI Lab + Tianjin Univ + Anhui Univ + Tsinghua)

### 這篇在說什麼

Long-horizon LLM agent 在終端環境中執行多步任務時，最常見的失敗模式不是單步推理錯誤，而是 state drift：檔案被改、dependency 被裝、temporary artifact 到處散落，而 agent 只看得到 tool output 和 log fragment，不知道 workspace 實際狀態。SABER 的研究顯示只有 14–18% 的步驟是 mutating actions，但一個錯誤的 mutating action 會把成功率降低 57–82%。

LemonHarness 要解決的就是這個問題：把 workspace boundary、rule knowledge、time-aware execution 統一在一個 harness 層裡，讓 agent 的 observation、execution、modification、verification 都在同一個受控的 runtime boundary 內。

### 主要貢獻

1. **整合執行框架**：把 system prompt、tool executor、skill library、execution logs、model-control loop 全部放在一個 runtime boundary 裡管理，而不是讓這些組件散落在 model 周圍。這解決了 state drift 的根本問題——agent 的 belief 和實際 environment state 不再脫節。

2. **Reusable Rule Knowledge Base**：把跨 task family 重複出現的執行規則和 acceptance criteria 轉成 runtime priors。例如 DL task 中 loss 下降不代表完成，還要看 data split、random seed、validation metric。這些 rule 在 task 開始前就告訴 agent，而不是讓 agent 盲目 trial-and-error。

3. **Time-Aware Execution Mechanism**：把 elapsed time 和 remaining budget 當成 runtime state 回饋給 model，分四個 phase（P1 Explore 0–0.3T, P2 Implement 0.3–0.6T, P3 Validate 0.6–0.9T, P4 Reserve 0.9–1.0T），每個 phase transition 有 grace window。這讓 agent 不會在無限探索中 timeout，也不會在最後一刻過度驗證。

### 方法 / pipeline

LemonHarness 的架構分層：

1. **Task Intake**：任務進入系統，建立 controlled workspace，載入 system prompt、tool definitions、rule knowledge。
2. **Model Decision Loop**：模型根據當前 task state（含時間資訊）產生 action intention，轉成 structured tool call。
3. **Structured Tool Execution**：所有 state-changing operations（file write、dependency install、temp artifact creation）透過 structured tool interface 在 controlled workspace 內執行，執行結果作為 observation 回饋給後續決策。
4. **Time-Aware Control**：每個 turn 都告訴 model 當前 phase 和 remaining budget。
5. **Execution Records**：所有 model output、tool call、execution feedback 都記錄在 runtime logs 中，可以回溯。

Key design choice：state-changing operations 被嚴格限制在 workspace 內，不是散落在不同路徑和 process 中。這和之前的 agent harness（如 HARBOR 的 five components）相比，更偏工程實作層面——不是概念框架，而是可以直接 deploy 的 execution boundary。

### 實驗設計

- **Benchmark**: Terminal-Bench 2.0，445 tasks，每個 task 在 sandboxed terminal 環境中執行。
- **Models**: GPT-5.3-CodeX（主要）和 GPT-5.5（額外驗證）。
- **結果**:
  - LemonHarness + GPT-5.3-CodeX: 84.49% accuracy over 445 trials
  - LemonHarness + GPT-5.5: 86.52% average accuracy across 5 jobs (385/445 solved)
- **Ablation**：論文有 time-aware phase 的消融實驗，顯示沒有 time-aware control 時 agent 容易 timeout 或過度驗證。Rule knowledge 的消融也顯示有 rule priors 的版本在 DL task 上更穩定。

### かに讀後判斷

LemonHarness 是 harness engineering 從「概念框架」（如 HARBOR 的 five components、AI Harness Engineering survey 的 runtime substrate）走向「工程實作」的關鍵一步。它把 SABER 發現的「mutating action 是 failure bottleneck」這個洞察直接轉化成設計決策：所有 state-changing operations 都在 controlled workspace 內透過 structured tool interface 執行。

和之前的 harness paper 相比：
- vs. HARBOR（2606.08610，6/24 已推薦）：HARBOR 偏概念框架（五個 harness components），LemonHarness 偏工程實作（workspace boundary + time-aware execution）
- vs. Harness-Bench（2605.27922，6/1 已讀）：Harness-Bench 測量 harness effects，LemonHarness 直接提供一個 harness
- vs. ProofAgent Harness（2605.24134，6/1 已讀）：ProofAgent 偏 adversarial evaluation，LemonHarness 偏 stable long-horizon execution

值得深讀的部分：Section 3 的 method 設計理由（尤其是 SABER 的 mutating action 數據和 LemonHarness 的 design decision 之間的對應）、time-aware phase schedule 的消融結果、以及 rule knowledge base 的具體內容（Table 1）。

## 2. SkillJuror: Measuring How Agent Skill Organization Changes Runtime Behavior

- **arXiv**: 2606.11543
- **Link**: https://arxiv.org/abs/2606.11543
- **Authors**: Zhiyu Chen, Zihan Guo, Bo Huang, et al. (Tongji Univ, Shanghai Innovation Institute, SJTU)

### 這篇在說什麼

Agent Skills（如 SKILL.md + supporting files）是給 LLM agent 在 inference time 提供程序性知識的機制。但目前的 benchmark 只看 Skills 的「有沒有」，不區分「Skills 說了什麼」和「Skills 怎麼組織」。這篇要回答的問題是：同樣的 task knowledge，Progressive Disclosure（簡潔 root file + 按需載入 supporting resources）和 normalized flat baseline 相比，會不會改變 agent 的 runtime 行為？

### 主要貢獻

1. **首次把 Skill organization 當成 controlled runtime variable 來實驗**：不是比不同的 Skills，而是把同一份 task knowledge 用不同方式組織（PD vs. Flat），在知識內容完全相同的情況下測量組織方式的影響。

2. **SkillJuror 框架**：semantically controlled variant construction + matched multi-trial evaluation + trajectory evidence，讓組織方式的效果可以追溯到 runtime 行為。

3. **實證發現**：Progressive Disclosure 改變了 runtime 行為——distinct Skill resources touched per trajectory 從 1.18 升到 3.85，effective uptake events 從 1.33 升到 3.92——但 outcome gain 只有 +4.1%（17/410 trials），而且效果取決於 task type。

### 方法 / pipeline

SkillJuror 的三步 pipeline：

1. **Variant Construction**：從一個 source Skill bundle 出發，在保持 task knowledge 完全相同的 constraint 下，改寫成 PD variant 和 Flat variant。Knowledge preservation 由人工審核確認。

2. **Matched Multi-Trial Evaluation**：每個 task × condition 組合跑多次 trial（用 Harbor sandbox），用 verifier 判定 pass/fail。

3. **Trajectory Evidence Analysis**：不只看 pass rate，還看 resource access breadth 和 Effective Resource Uptake（ERU）——agent 不只是打開了 supporting resource，還是否真的把裡面的知識用到了動作中。

82 個 SkillsBench task，使用 Harbor 作為 containerized sandbox 執行環境。

### 實驗設計

- **Tasks**: 82 tasks from SkillsBench
- **Conditions**: Progressive Disclosure (PD) vs. Normalized Flat (Baseline)
- **Metrics**: verifier pass rate + trajectory evidence (resource access count, ERU)
- **Main results**:
  - Resource access: PD 平均 3.85 distinct resources per trajectory vs. Flat 1.18
  - ERU: PD 3.92 vs. Flat 1.33
  - Pass rate: PD 在 410 matched trials 中多通過 17 trials (+4.1%)
  - 效果 task-dependent：PD 在 implementation/checking/repair 導向的 task 中幫助大，在 output convention / numerical threshold / long artifact generation 的 task 中幫助小

### かに讀後判斷

這篇和 harness engineering 的關聯在於：SkillJuror 用的是 Harbor（之前 DailyRead 讀過的 harness framework）作為 execution sandbox，而且它測量的正是「harness 怎麼呈現 knowledge 給 agent 會影響 runtime 行為」。這是 harness engineering 從「runtime boundary」延伸到「knowledge organization」的視角。

不過這篇的 main finding 比 LemonHarness 弱——+4.1% pass rate 並不大，而且作者自己承認效果高度 task-dependent。核心價值在於方法論：把 Skill organization 當成 controlled variable 來做實驗，而不是像之前 SkillsBench 那樣只看有沒有 Skill。

- 和 6/24 推薦的「What makes a harness a harness」（2606.10106）直接相關——那篇定義了 harness 的必要條件，這篇測量了 harness 內 knowledge organization 的效果
- 和 SkillsBench（li2026skillsbench）是同一系列的工作，但這篇的方法論更嚴謹
