## 1. Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution (2607.13034)

- **arXiv**: [2607.13034](https://arxiv.org/abs/2607.13034)
- **Authors**: (主作者未從 HTML 前段確認，通訊為 Yin, 2026)
- **Submitted**: 2026-07-15（最新，今天發佈）

### 這篇在說什麼

LLM agent 常有一個隱性問題：它們不知道一個任務有多難。面對一個只需要改兩行 icon markup 的簡單任務，最強的 frontier agent 也可能重新讀取整個專案架構、重看 icon library、重跑 dependency——把一個秒級的 locate-and-replace 變成一場小型 codebase audit。這不是知識或記憶的問題，而是一個判斷力的缺失：agent 無法快速判斷任務需要多少資訊、哪些已經看過的資訊與當前任務無關、什麼是最短的可靠路徑。

這篇論文把這個問題形式化為 **minimum-sufficient execution** 和 **Agent Cognitive Redundancy Ratio (ACRR)**，然後提出 **E3（Estimate, Execute, Expand）** 框架：先估計任務需要什麼、用最小可行路徑執行、只在驗證失敗時擴展 scope。在 MSE-Bench（121 個編輯任務的確定性基準）上，E3 在保持 100% 成功率的同時，削減了 85% 成本、91% token、92% inspected files。在真實 gpt-4o agent 上也得到驗證。

### 主要貢獻

1. **Minimum-sufficient execution 和 ACRR**：第一次把「agent 做了多於必要的努力」這個隱性問題形式化。ACRR = actual cost / oracle minimum cost，是一個正規化的冗餘度量。這讓我們可以精確說「這個 agent 花了 5 倍於必要的努力」，而不只是「它很慢」。
2. **E3 框架（Estimate, Execute, Expand）**：核心思想是借鑑電力系統的 flat start——power-flow solver 不會列舉整個狀態空間，而是先計算一個結構化的初始運行點，然後用 Newton-Raphson 迭代精煉。E3 把這個思想搬到 agent 執行：先估計一個最小 scope，執行，只在驗證失敗時擴展。這不是「少想一點」，而是「先判斷需要多少」。
3. **MSE-Bench**：一個確定性、離線的基準，每個任務都攜帶 oracle minimum-sufficient trajectory，所以冗餘可以被精確測量。包含 single-file、cross-file、和 repo-level 編輯。
4. **Real-model 驗證（LLM-Case）**：不只測 simulator，還在真實 gpt-4o agent 上驗證，用真實專案的 pytest suite 打分。E3 是最 lean 且最快的策略，唯一失敗是 provider rate-limit 而非錯誤編輯。

### 方法 / pipeline

- **E3 三步**：
  1. **Estimate**：基於任務描述和先前的經驗，估計一個初始 operating point（哪些 files 需要看、哪些 tools 需要調用、預期的 step count）。這個 estimator 是刻意樂觀的——寧可低估 scope。
  2. **Execute**：用估計的最小 scope 執行。如果成功，節省了所有多餘的 context gathering。
  3. **Expand**：如果驗證失敗（例如 pytest 沒過），逐步擴展 scope——讀更多 files、調用更多 tools——直到成功或達到上限。

- **MSE-Bench 設計**：procedurally generated 編輯任務，每個都有 oracle minimum trajectory。Capability-controlled simulator 保證「agent 能不能做到編輯」被 hold constant，只有「agent 需要多少 context」在變。

- **Baseline 比較**：不只是比 over-cautious default，還比了一個 strong adaptive retrieval-augmented baseline（類似 Ares / BoundaryRouter 的思路），E3 仍然在等成功率的條件下更便宜。

### 實驗設計

- **MSE-Bench 結果**（121 edits, capability-controlled simulator）：
  - E3: 100% success, 85% cost reduction, 91% token reduction, 92% inspected file reduction
  - 比 strong adaptive retrieval baseline 再省 16%
  - Ablation 隔離了 estimation 和 expansion 各自的貢獻
  - Held-out instruction wording 測試：故意打破 estimator 的 lexical cues，E3 仍然 100% success
  - 在幾乎所有 cost weighting 下都是最便宜的 fully-successful 策略

- **LLM-Case 結果**（gpt-4o on real open-source library, real pytest）：
  - Over-reading 確實存在但比 simulator 中溫和
  - E3 是 leanest 和 fastest policy at comparable task success
  - 唯一失敗是 provider rate-limit，不是錯誤編輯

- **Power-system case study**：用真實 Newton-Raphson 測量驗證 flat-start 類比

- **已讀來源**：arXiv HTML 全文前半（含 Introduction、Related Work 完整、Method 大部分），有完整方法論和核心結果描述。實驗細節（具體 benchmark task、數值表格）需進一步確認。

### かに讀後判斷

這篇是 harness engineering 領域近期最重要的論文之一，因為它處理的不是「怎麼建更好的 eval harness」而是「agent 本身需要一個新的能力——判斷任務需要多少 effort」。

幾個關鍵判斷：

1. **ACRR 是一個有用的度量**：之前 harness/eval 領域主要看 success rate 和 cost，ACRR 把「冗餘」本身變成一個可測量的屬性。這對後續 agent 設計有直接影響——不只是要 agent 做對，還要它做適量。
2. **E3 的 flat-start 類比很精準**：不是少想，而是先判斷需要想多少。這和「adaptive compute」路線（Ares, test-time scaling）不同——那些是調整 effort level，E3 是預測 effort scope。概念上的差別很重要。
3. **和 Shared Selective Persistent Memory（今天的 agent memory 篇）形成對照**：那篇是「跨 session 保留什麼 context」，這篇是「同一 session 內需要多少 context」。兩者都是關於 agent 的 context 管理，但方向不同。
4. **值得深讀**：Section 5（MSE-Bench 設計）、Section 7（完整結果和 ablation）、Section 7.6（held-out instruction wording stress test）、以及 power-system case study。
