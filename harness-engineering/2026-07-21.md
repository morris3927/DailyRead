# Harness Engineering — 2026-07-21

## 1. Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable (2607.13285)

- **arXiv**: 2607.13285
- **Link**: https://arxiv.org/abs/2607.13285 | [Project Page](https://ruhan-wang.github.io/Harness-Handbook/)
- **Authors**: Ruhan Wang, Yucheng Shi, Zongxia Li, Zhongzhi Li, Yue Yu, Junyao Yang, Kishan Panaganti, Haitao Mi, Dongruo Zhou 等
- **Affiliations**: Tencent HY LLM Frontier, Indiana University, University of Maryland, University of Georgia, NUS
- **Submitted**: 2026-07-14

### 這篇在說什麼

Harness engineering 的核心問題之一是：當你想要修改一個 agent harness 的行為時，你面臨的第一步不是「怎麼改」，而是「改哪裡」。一個 production-scale 的 harness 可能跨幾百個 function、多個檔案、多個 execution stage，而一個行為可能散佈在這些非相鄰的位置。修改請求描述的是「要做什麼」，但 codebase 組織的是「檔案和函數」，兩者之間有一個 behavior-to-code 的 mapping gap。現有的 repository map、code search、long-context processing 能幫你更容易瀏覽程式碼，但它們還是 leave you to recover this mapping yourself。

Harness Handbook 就是填這個 gap 的。它不是另一個 code search tool，而是一個 behavior-centric representation：用靜態程式分析加上 LLM-assisted behavioral structuring，自動從 harness codebase 合成出一個行為導向的文件樹（L1 system overview → L2 component overview → L3 source-backed unit details），把每個行為連到對應的 source code location。搭配 Behavior-Guided Progressive Disclosure (BGPD)，讓 coding agent 從高層行為描述一路導航到實作細節，並自動驗證候選 location 是否仍對應目前的 source。

### 主要貢獻

1. **定義 behavior localization 問題**：明確把「找到所有實作某個行為的 code location」定義為 harness evolution 的前置瓶頸。這不是 search 問題，是 mapping 問題——你需要的不是找到一段相關 code，而是確認你找到了所有相關的 scattered locations。

2. **Harness Handbook 三層 representation**：L1 system overview（架構、execution model、stages、global data flow）→ L2 component overview（每個 stage 的責任、輸入輸出、dependencies、local state）→ L3 unit deep dive（source-grounded implementation entries）。另外有一個互補的 state-register view 𝒵 記錄跨 stage 的 state 關係。關鍵約束：progressive disclosure（只在需要時深入）和 behavior–implementation alignment（每個 L3 locator 必須能 resolve 到目前 repo 的實際位置）。

3. **Behavior-Guided Progressive Disclosure (BGPD)**：一個 workflow，從行為描述出發，逐步導引 coding agent 到相關 implementation，並自動驗證 candidate location 是否 still valid。每次 repository diff 後，Handbook 會自動重新同步。

4. **實驗證明 Handbook-assisted planning 的效果**：在兩個 open-source agent harness 的多樣 modification request 上，Handbook-assisted planning 在 behavior localization 和 edit-plan quality 上都優於 baseline，且使用更少的 planner tokens。最大收益出現在 scattered implementation sites、rarely executed paths、和 cross-module interactions——這些正是最難手動定位的 case。

### 方法 / pipeline

**Handbook 構建 pipeline**：
1. **Static program analysis**：從 harness codebase 抽出 call graph、data flow、state transitions、tool registrations 等 structural information
2. **LLM-assisted behavioral structuring**：用 LLM 把 structural information 組織成 behavior-centric 的 L1–L3 文件樹
3. **Automated synchronization**：每次 repository diff 後，重新驗證和更新 Handbook

**BGPD workflow**：
1. 從 modification request 出發，在 L1 找到相關的 system-level behavior
2. 在 L2 找到具體的 component 和 stage
3. 在 L3 確認 source code location 仍然 valid
4. 產生 edit plan

**Evaluation design**：
- **Harnesses**: 兩個 open-source agent harness（論文未具名但應為主流 framework）
- **Modification requests**: 多樣化的真實修改需求
- **Baseline**: 不使用 Handbook 的 planning
- **Metrics**: behavior localization accuracy, edit-plan quality, planner token usage
- **Special cases**: scattered sites, rarely executed paths, cross-module interactions

### 實驗設計

論文在兩個 open-source agent harness 上做 evaluation，用多樣的 modification request 來測試 Handbook-assisted 和 baseline planning 的差異。主要發現：

- Handbook-assisted planning 在 behavior localization 和 edit-plan quality 上都優於 baseline
- Planner tokens 使用量減少
- 最大收益出現在 behavior implementation 散佈在多個非相鄰位置的 case
- Rarely executed code paths 和 cross-module interactions 也是 Handbook 特別有幫助的場景

這些結果很合理：Handbook 的核心價值就在於把 scattered 的 implementation 連接到行為描述，而這正是 code search 和 repository map 不直接處理的問題。

### かに讀後判斷

這篇是今天最值得深看的 harness paper。它處理的問題——harness evolution 的第一步不是改 code，而是定位 code——是 DailyRead 之前追蹤的 harness engineering 討論裡一直缺的那塊：之前看了 Harness MDP (2607.05458) 是學會什麼時候採取哪個 structural action，Set-shifting (2607.13396) 是測 agent 在 harness 變動時的適應力，Agent-Reactive Bugs (2607.15684) 是 model–harness interaction 產生的 bug。Harness Handbook 補的是 harness developer/coding agent 面對一個大 codebase 時，怎麼找到要改的地方。這不是一個 sexy RL 或 benchmark 問題，但它是 real-world harness engineering 的 daily pain point。

深讀時值得注意的部分：Section 3 的 Handbook representation 設計（特別是 L1–L3 的 progressive disclosure 結構和 state-register view）、BGPD 的驗證機制、以及 scattered vs. localized modification 的 performance 差異。另外值得追的是它跟之前看過的 HarnessForge / HarnessX 的關係——Handbook 是定位問題，那些是改 code 問題，兩者應該互補。

## 2. Agent-Reactive Bugs at the Model-Harness Boundary: An Empirical Study of LLM Agent Issue Reports (2607.15684)

- **arXiv**: 2607.15684
- **Link**: https://arxiv.org/abs/2607.15684
- **Authors**: Jingyi Chen 等
- **Submitted**: 2026-07-17
- **Depth level**: Abstract + landing page 快速掃描

### 這篇在說什麼

這篇處理的是 harness engineering 裡一個很具體但一直沒被系統性研究的 bug 類型：Agent-Reactive (AR) bugs。AR bugs 不是單純的 model 錯誤或 harness 錯誤——它們只在特定 LLM response 觸發 harness 異常反應時才出現，所以你光看 model 或光看 harness code 都無法理解問題。這篇分析了 255 個來自 Codex、Gemini-CLI、LangChain、CrewAI 的 bug report，建構了兩軸 taxonomy：observable symptoms 和 trigger LLM behaviors。

### 主要貢獻

1. **首次系統性定義和分類 AR bugs**：提出兩軸 taxonomy（symptoms × triggers），清楚區分了 AR bugs 和單純 model failure 或 harness defect。

2. **Silent error 問題**：許多 AR bugs 表現為 silent errors（沒有明確 test oracle），這讓 detection 非常困難。LLM response 的 stochasticity 進一步讓 reproduction 變得不可靠。

3. **User–developer mismatch**：Users 常建議 harness-side guardrails，但 developers 可能歸因於 LLM 本身或回應緩慢。這個 mismatch 指出了目前 agent bug management 的制度性問題。

### 方法 / pipeline

- 從 Codex、Gemini-CLI、LangChain、CrewAI 收集 255 個 bug report
- 手動分析每個 report，分類為 AR bug 或非 AR bug
- 建構兩軸 taxonomy：observable symptoms（如 silent error, wrong output, crash）和 LLM behaviors that trigger them（如 unexpected format, hallucinated tool call, over-long output）
- 分析 fixes：誰修的、修在哪裡、修法是否對應 root cause

### 實驗設計

目前從 abstract 和 landing page 能確認到：
- 四個主流 agent 系統的 255 個 bug report
- 兩軸 taxonomy 的建構方法
- Silent error 比例和 reproduction 困難度的分析
- User–developer fix 方向的 mismatch 分析

還看不到詳細的 taxonomy 內容、每個 category 的 bug 數量分佈、和具體的 fix pattern 分析，需要看全文。

### かに讀後判斷

這篇跟 Harness Handbook 互補：Handbook 處理的是「知道要改哪裡」，AR Bugs 處理的是「知道 bug 在哪裡但難以理解和重現」。兩篇合在一起，揭示了 harness engineering 的兩個核心 debugging 瓶頸。值得注意 AR bugs 的 silent error 特性——這跟之前看過的 context engineering / harness evaluation 討論裡反覆出現的「test oracle 問題」是同一件事的不同面向。

因為目前只讀到 abstract 層級，無法確認 taxonomy 的具體內容和 fix pattern 的細節，判斷強度相對較低。如果 Morris 對 bug taxonomy 和 empirical SE study 有興趣，值得點開看 Section 3–4 的 taxonomy 和 fix analysis。
