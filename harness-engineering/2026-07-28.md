## 1. The Scaffold Effect in Coding Agents: Harness Choice as a Hidden Variable in Coding-Agent Evaluation

![](../assets/2026-07-28/scaffold-effect-coding-agents.png)

- **arXiv / Venue / 類型**: arXiv:2607.22585，cs.AI，evaluation / harness paper
- **Link**: https://arxiv.org/abs/2607.22585
- **查重**: `check_paper_seen.py 2607.22585` → `NOT_SEEN`
- **讀取來源**: arXiv abstract + arXiv HTML full text（Introduction、Related Work、Experimental Setup、Metrics、Results 前段）

### 這篇在說什麼

這篇抓住 coding-agent leaderboard 的一個核心盲點：公開榜單通常用 model name 和 pass rate 排名，但真正讓 agent 能工作的是外面的 harness / scaffold，也就是 tool issuing、context management、stop rule、turn budget、retry policy、verification behavior、tool serialization、preloaded context 等控制層。如果 harness 固定，model-to-model comparison 還算合理；但如果 harness 也跟著變，榜單上的 pass rate 就混在一起，無法分辨是模型能力、工具介面、上下文策略，還是停止條件造成差異。

作者把這個問題轉成 controlled study：固定模型，換三個開源 coding-agent harness，看 pass rate、token cost、latency、turns、no-action turns、failure fingerprints 怎麼變。它的重點不是再證明「scaffold matters」這句口號，而是量化 scaffold matters 到什麼程度，以及它如何以 deployment-relevant metrics（tokens per solved task、等待 / oversight tax）影響人實際使用 agent 的成本。

### 主要貢獻

第一，作者把比較單位從「model」改成「harness–model pair」。這是很實用的觀點：Morris 真正在日常開發裡選的不是裸模型，而是某個模型跑在 OpenCode / Goose / OpenHands / Codex 類 harness 裡的整體行為。

第二，論文在 300 trials（3 harnesses × 2 models × 50 Terminal-Bench Pro tasks）裡顯示 harness choice 可以造成最高 40× tokens per solved task 差異，但 within-model pass-rate differences 只有約 0–8 percentage points，而且多數 bootstrap confidence intervals 包含 0。也就是說，有些 scaffold 未必讓你多解多少題，卻會讓每解一題貴非常多、慢很多、需要更多人類等待。

第三，它提出 failure-mode fingerprint 的觀察：Goose、OpenHands-SDK、OpenCode 在不同模型上會重複出現各自偏好的 failure modes，例如 REASON、VERIFY / MAX_TURNS、idle-loop / TIME。這表示一些失敗不是 model-specific，而是 scaffold-level bias。

第四，它把 no-action turns 定義成 oversight burden proxy。agent 沒有修改檔案也沒有發新 command 的 turn，對使用者來說可能是每題都要等的一種稅，不只是 token 消耗。

### 方法 / pipeline

實驗使用 Terminal-Bench Pro 的 50-task stratified subset，涵蓋 BUG、BUILD、DATA、IMPL、ML、PUZZLE、SEC、SYS 等類型。兩個模型是 Qwen 3.6 Plus 與 MiniMax M2.5，三個 harness 是 Goose、OpenCode、OpenHands-SDK。執行基礎設施用 Harbor，任務 manifest、test suite、Daytona sandbox、900 秒 wall-time cap、OpenRouter gateway 都盡量固定。

標準化 protocol 的做法很仔細：Terminal-Bench Pro instruction 原文、native test suite、sandbox、時間上限、共享 operating principles、non-negotiables、四個 shared skills playbook、task instruction 都保持一致。不可避免的差異則被視為研究對象本身，包括 tool API、automatic context pre-loading、internal retry / sub-agent logic、budget control exposed by harness。Goose 和 OpenHands-SDK 有 40 turn cap，OpenCode 沒有透過 Harbor 暴露 turn-budget flag，只受 900 秒 wall-time cap 限制；作者沒有硬把它抹平，因為 exposed budget control 本身就是 scaffold 行為。

Metrics 包含 solved、turns_used、tokens_total、avg_no_action_turns、hit_turn_budget_count、wall_seconds、post-hoc failure_category。token accounting 用 harness-emitted ATIF 或 Goose total-only field；tokens per solved task 是把 cell 內所有 trial token，包括失敗 trial，除以 solved count，因此是部署者每成功一題實際承擔的攤銷成本。

### 實驗設計

主要結果很明確：pass rate 的差距相對小，cost 的差距巨大。within-model harness range 約 2–8 pp，跨模型 within-harness 約 4–10 pp；但 tokens per solved task 的排序在兩個模型上都一致：Goose 遠低於 OpenHands-SDK，再遠低於 OpenCode。OpenCode 每解一題的 token 可到 Goose 的約 40×，而 pass-rate 差異沒有相應放大。

作者還做了 bootstrap robustness：Goose 的 tokens-per-solved-task CI upper bound 仍遠低於 OpenCode 的 lower bound，表示這不是偶然抽樣差異。對 OpenCode 的 turn-budget sensitivity 也有檢查：大多數 OpenCode trials 的 turn counts 仍低於 40，因此 40× token gap 不是單純因為 OpenCode 可以無限制跑很多 turn，而更可能是 per-turn context growth、tool serialization、token accounting / harness style 造成。

比較可惜的是，這篇仍是 50 tasks subset，且模型、harness、benchmark 都集中在 coding-agent CLI 類型；外推到 browser agents、research agents、多 agent systems 時還需要重做。不過它的 evaluation recipe 很適合直接拿去看其他 agent workflow。

### かに讀後判斷

這篇是今日最值得點開的 harness paper。它和前幾天讀過的 Harness-Bench、scaffolding evolution、自我演化 harness 形成一條很清楚的線：不要再只看「模型 X 在榜上幾分」，要看 model-harness configuration，包括 cost、latency、stop behavior、verification loop、idle/no-action turns、failure fingerprint。

我會建議 Morris 深讀 Section 3–4，尤其是 Standardization Protocol、Metrics、Token Cost per Solved Task、failure category 的定義。這篇對 OpenClaw / Codex / OpenCode 類系統很有啟發：如果我們要比較 agent 改版，不只要看完成率，也要把 token-per-solved-task、no-action wait tax、failure fingerprint 固定記錄下來；否則很容易把「感覺更聰明」其實只是「花更多 context 和等待」誤讀成能力提升。

## 2. Baselines Before Architecture: Evaluating Coding Agents for Autonomous Penetration Testing

- **arXiv / Venue / 類型**: arXiv:2607.13085，cs.CR / cs.AI，controlled evaluation paper
- **Link**: https://arxiv.org/abs/2607.13085
- **查重**: `check_paper_seen.py 2607.13085` → `NOT_SEEN`
- **讀取來源**: arXiv abstract + arXiv HTML full text（Introduction、Background、Motivation / Study Overview）

### 這篇在說什麼

這篇處理的是 autonomous penetration testing agent 裡的 attribution problem。近來很多 pentesting paper 會報很高 benchmark score，同時加入多 agent role decomposition、typed tool interface、persistent memory、reflection、retrieval、browser validation、attack tree search 等安全專用 harness；但這些系統通常也換了更強的 backbone model、不同 benchmark subset、不同 budget 或不同 tool surface。結果就是：我們不知道進步到底來自新 architecture，還是只是模型變強、一般 coding-agent loop 已經足夠好。

作者的主張很直接：在宣稱 pentesting-specific architecture 有用前，應先報 model-matched plain-agent baseline。因為 web exploitation 很多操作其實可以被 operationalize 成 coding task：用 Python requests / httpx 打 HTTP、用 loop 嘗試 payload、解析 response、用資料結構追蹤狀態。一般 coding CLI agent 已經具備 inspect workspace、write scripts、execute commands、iterate from feedback 的能力，因此是衡量 security-specific harness residual value 的必要控制組。

### 主要貢獻

第一，提出 architecture-attribution methodology，把 backbone model capability、general coding-agent scaffolding、pentesting-specific architecture 三者拆開。

第二，在 XBOW 104-task benchmark 上，用同一 GPT-5 model、budget、target interface、scoring rule 跑 Codex、OpenCode、Pi 等 default coding CLI agents，找出最強 same-model plain baseline。

第三，測試 security-specific prompt variants 是否真的提升 plain baseline。摘要與 introduction 指出，測過的安全 prompt variant 沒有改善 shipped default Codex behavior。

第四，將 default Codex scaffold 與 MAPTA、PentestGPT V2 等 published architecture-heavy systems 做 closest available model matches，並再用 GPT-5.2、GPT-5.5 重跑 plain-agent scaffold，測量 model scaling 在相同 scaffold 內能補多少 gap。

### 方法 / pipeline

整體 pipeline 是四個 research questions。RQ1 先固定 backbone model，讓 Codex、OpenCode、Pi 在 XBOW benchmark 上各跑兩輪 full pass，衡量哪個 plain coding-agent baseline 最穩。RQ2 在最強 baseline 上加 security-specific prompt text，看 domain prompt 是否提高 observed score。RQ3 把 plain baseline 與 MAPTA、PentestGPT V2 等架構重的系統做 model-matched 或 closest-match comparison，把剩下的差距稱為 architecture residual。RQ4 則把同一 plain Codex scaffold 換成 GPT-5.2 / GPT-5.5，看模型 scaling 本身能改善多少。

XBOW benchmark 有 104 個 containerized web application challenges，跨 26 vulnerability categories，每題以 hidden flag retrieved / not retrieved 作為 binary success criterion。這個設計避免 false positive ambiguity，適合比較 agent 是否真的完成 exploitation。作者也提醒，XBOW 不是真實 pentest 的完整替代，因為真實環境還有 scoping、reconnaissance、reporting、adaptive defenses、多 host context 等問題。

### 實驗設計

從讀到的全文可確認，這篇的實驗設計重點是 controlled baseline，而不是新 agent architecture。它比較 plain coding agents、prompt condition、published architecture systems、以及 model scaling。結果摘要說 specialized harnesses can add measurable benchmark lift and may improve cost efficiency，但 plain coding agents already solve a large share；repeated plain-agent runs can match or exceed some published architecture scores in union coverage；newer models substantially improve the same scaffold。

我目前讀到的是 HTML 前中段與摘要，已確認研究問題、benchmark、比較對象與主要結論；完整 per-category score、cost tables、union coverage 的細節需要看 Results section / artifact。它仍足以作為 domain note，但我不會把未讀到的細表數字硬寫進判斷。

### かに讀後判斷

這篇和 Scaffold Effect 是同一個大方向的安全版：benchmark claim 要拆成 model、generic scaffold、domain-specific harness 三層。對 harness engineering 來說，它提醒我們不要看到「多 agent security architecture 分數高」就直接相信架構有效，先問：同模型的 plain Codex / OpenCode baseline 是多少？default prompt 是否已經足夠？新模型在同 scaffold 裡提升多少？

如果 Morris 對 agent security / pentest automation 有興趣，這篇值得收藏，但今日我會把它放在第二順位；第一順位仍是 Scaffold Effect，因為那篇的 metrics 對一般 coding-agent evaluation 更通用。深讀這篇時優先看 Results 裡 RQ1–RQ4 tables、MAPTA / PentestGPT V2 comparison、以及 GitHub artifact 的 prompt/config，這些才是判斷 architecture residual 的關鍵。
