# Harness Engineering — 2026-08-08

## 1. LoopsBench: From Harness Engineering to Loop Engineering in Coding Agent Evaluation

- **arXiv**: 2608.00267
- **Link**: https://arxiv.org/abs/2608.00267
- **Authors**: Microsoft（開源：microsoft/Loopsbench）

### 這篇在說什麼

Coding agent 基礎設施正在從 harness engineering 轉向 loop engineering：Codex goal mode、Claude Code goal mode 和 dynamic workflows 都在 harness 之上加了一層 loop control surface，讓目標、進度判斷和工作分配可以跨回合持續。現有基準測試（SWE-bench 系列、FeatureBench 等）幾乎都是 terminal task：給一個 issue，看最終 patch 是否通過測試。這完全無法觀察 agent 是否保留了中間義務、是否避免了 regression、是否按照合理的順序處理相依的子問題。

LoopsBench 是第一個專為 loop engineering 評估設計的基準測試。每個 task 是一個 dependency DAG，節點是 source-grounded development units，邊是 prerequisite 關係。Flow-aware runtime 沿 ready frontier 釋放測試、保留已完成節點作為 regression obligation、記錄 loop trace。最強配置（Opus-4.7 + Claude Code + outer continuation）只解了 25.00% 的 task。

### 主要貢獻

1. **Dependency DAG 作為評估合約**：每個 task 不是 flat issue，而是一組有明確 prerequisite 關係的 development units。這讓 intermediate obligations 和 execution order 變得可觀察。
2. **Flow-aware evaluation runtime**：不是一次性跑全部測試，而是沿 ready frontier 釋放測試。已完成的節點保持活躍作為 regression obligation——如果後續工作破壞了前面的功能，會被偵測到。
3. **112 個 source-grounded tasks**：來自三個真實來源（29 PR Sequences、57 Course Labs、26 Research Evolutions），橫跨 8 種程式語言和 9 個領域。中位數 dependency depth 為 6，總計 5,300+ development units。
4. **Loop trace diagnostics**：記錄 planning、routing、verification、state continuity、obligation retention 的 trace，可以分離 model 和 loop 的效果。
5. **實證發現**：最強配置只解了 25%；evaluated loops 省略了 prerequisite 關係、產生更長的 patches、寫更少的測試；regression events 在所有 loop profile 中都可見。

### 方法 / pipeline

LoopsBench 的構建 pipeline 有五個階段：

1. **Task Collection**：三個真實來源——Course Labs（112 個大學程式作業，來自 30 所大學）、PR Sequences（56 個活躍維護的 GitHub repos 的完整 commit history 和 merged PR stream）、Research Evolutions（212 篇來自 48 個 venues 的論文，經過 load-bearing inheritance edge 分類後保留 95 篇，形成 47 個 candidate tasks）。
2. **Task Preprocessing**：統一語言、重組骨架、用 Claude Code 做 PR 分類和研究論文分類。
3. **Task Selection**：兩個 source-agnostic 閾值——Temporal Span ≥ 2.5 months、Solution Scale ≥ 1,200（source-specific）。
4. **Development Unit Definition & Intra-Task Relation Recovery**：定義每個 development unit，恢復 dependency DAG。
5. **Task Instrumentation**：附加 public instruction、executable environment、per-unit test obligations。

**Evaluation**：每個 run 記錄 loop trace metrics（planning、routing、verification、state continuity、obligation retention），不是只看最終 pass rate。

### 實驗設計

- **模型**：Opus-4.7 等前沿 coding agents
- **Loop 實作**：Claude Code、Codex 等，搭配不同的 outer continuation 策略
- **核心結果**：最強配置（Opus-4.7 + Claude Code + outer continuation）只解了 25.00%
- **Loop trace 分析**：
  - Evaluated loops 省略了 prerequisite 關係
  - Patches 更長
  - Tests 更稀疏
  - Context renewal 因 loop 實作而異
  - Regression events 在所有 loop profile 中可見
- **對照表**：Table 1 比較了 LoopsBench 與 SWE-bench 系列、FeatureBench、MLE-Bench 等基準，清楚顯示 LoopsBench 是唯一同時暴露 separately testable intermediate units 和 explicit prerequisite DAGs 的基準。

### かに讀後判斷

這篇直接延續了 07-28 DailyRead 中「The Scaffold Effect」的討論，但把焦點從 harness 轉向 loop。對 Morris 來說：

1. **Loop engineering 是比 harness engineering 更高階的問題**：Scaffold Effect 說的是同一個 model 在不同 harness 下表現差異大；LoopsBench 說的是即使有了好的 harness，loop 層的 routing、state continuity、obligation retention 仍然是瓶頸。
2. **25% 的解決率非常低**：這說明長 horizon coding task 遠比 SWE-bench 上的單一 issue 難得多。
3. **Regression events 在所有 loop profile 中可見**：這意味著 coding agent 在長 horizon 中會反覆破壞已經完成的功能，這是一個嚴重的可靠性問題。
4. **Open-source 了所有 task、5,300+ development units 和 executable tests**：這讓 LoopsBench 可以成為社群標準。

## 2. Delivery, Not Storage: Cue-Anchored Working Memory as a Harness Property for Coding Agents

- **arXiv**: 2607.20972
- **Link**: https://arxiv.org/abs/2607.20972
- **Authors**: Swapnanil Saha（July 2026）

### 這篇在說什麼

Current coding agents 只有一種記憶：document-style memory（instruction files、plan artifacts、auto-written memory directories）。這些都是必須主動寫入、主動讀取的。但人類專業知識的核心不是 wiki，而是一大堆「從未寫下來的情境綁定操作事實」（gotchas、locations、"how things are done here"）——這些是作為工作的副作用被編碼的，在相關情境出現時自動浮現。

這篇論文的核心主張是：**第二層記憶（cue-anchored working memory）必須是 harness property，不是 agent choice。** 因為 agent 主動使用記憶工具的比率接近零——即使 store 已經預植了任務相關知識，agent 在 114 個 turn 中做了 0 次記憶操作。相反，deterministic injection 在每次需要時都準確送達，零 false alarm。

### 主要貢獻

1. **Two-tier design theory**：從認知科學文獻（memory offloading、incidental encoding、event-based prospective memory）出發，把工程記憶分成兩層：content-plane（文件式、主動存取）和 control-plane（cue-anchored、deterministic injection）。每一個認知機制都映射到一個可證偽的架構需求。
2. **Cue-anchored memory model**：每個 memory 是一個 tuple (content, kind, triggers, scope, decay)。Trigger 使用可組合的詞彙 {path, symbol, semantic, event, temporal}，由 harness deterministically 評估。這個組合性沒有現有學術或商業系統提供。
3. **Controlled evaluation**：在真實 coding task 上做 12 次分級實驗。核心發現：voluntary memory use ≈ 0（即使 store 預植了任務相關知識，114 turns 中 0 次記憶操作）；deterministic injection 在每個 seeded run 中都準確送達，零 false alarm；39% 的 re-reads 是跨 compaction boundary 的重複購買。
4. **Repeated-compaction decay probe**：k=108 和 k=138 的 forced compaction 實驗。只存在對話中的 10 個事實在第一次 summary 後就消失了（108/108 forced compactions 中 106 個不見）；同一個 agent 開始 grep harness 的 session files 來重建記憶——手動建造的正是 harness 沒有給它的那個層。而從 harness-owned store 注入的同一組 10 個事實，在 138/138 次 compact-resume 中完整送達，最終 summary 不包含任何一個——agent 的記憶從不依賴 summarizer 選擇保留什麼。

### 方法 / pipeline

**Memory model**：
- Kinds：directive（standing prospective intention，不可遺漏）、gotcha（cue-anchored caveat）、finding（semantic fact）、task（working state）、reference（pointer）
- Triggers：path（glob over touched files）、symbol（code entity reference，需要 symbol graph）、semantic（current activity similarity above a floor）、event（session start, prompt submit, pre-edit, pre-run, pre-compaction, post-compaction）、temporal（not-before, cooldown）
- 評估是 deterministic、harness-side 的：沒有任何 model judgment 在 delivery path 中

**Delivery vs. Lookup 的區別**：
- Content-plane（文件式）：模型必須選擇寫入和讀取。依賴 model compliance。失敗率很高。
- Control-plane（injection）：harness deterministically 決定什麼時候進入 context window。不依賴模型主動性。

**實驗**：
- 12 次分級 runs，控制 launch posture
- 10 個事實的 forced compaction probe
- Token-level survival curves、provenance forensics

### 實驗設計

- **Voluntary memory use**：預植了任務相關知識的 store，agent 在 114 turns 中 0 次記憶操作
- **Deterministic injection**：每個 injection-equipped seeded run（n=3）都準確送達，0 false alarms
- **Cross-compaction re-reads**：39% 的 re-reads 是重複購買——session 已經付過 token cost 的內容，在 compaction 後又重新從外部 retrieve
- **Decay probe**：
  - Conversation-only：10 個事實在第一次 summary 後消失，106/108 forced compactions 中不存在。Agent 開始 grep harness 的 session files 來重建。
  - Harness-injected：同一組 10 個事實在 138/138 次 compact-resume 中完整送達。最終 summary 不含任何一個事實——記憶從不依賴 summarizer。

### かに讀後判斷

這篇論文同時屬於 Harness Engineering 和 Agent Memory 兩個領域。我把它放在 Harness Engineering 裡，因為它的核心主張是「cue-anchored working memory 必須是 harness property」——這是對 coding agent harness 設計的直接建議。

對 Morris 來說：

1. **和 LoopsBench 互補**：LoopsBench 說 loop engineering 需要處理 state continuity 和 obligation retention；Delivery, Not Storage 說的是同一個問題的一個具體解法——把 cue-anchored memory 放進 harness 的 control plane。
2. **114 turns 中 0 次自願記憶操作**：這是一個非常強的實證結果，直接挑戰了所有讓 agent 主動管理記憶的系統設計。
3. **Deterministic injection vs. voluntary lookup**：這不是一個新想法（Anthropic 的 memory tool 已經 force-injects；ChatGPT 的 memory 已經 auto-captures + auto-injects），但這篇第一次用嚴謹的實驗證明了 deterministic injection 的優越性，並提出了完整的設計理論。
4. **Cross-compaction re-reads 的 39%**：這個數字說明 compaction 是 agent memory 的一大殺手——不是因為資訊丟失，而是因為同樣的資訊被反覆購買。
