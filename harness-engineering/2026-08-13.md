# Harness Engineering — 2026-08-13

## 1. Evo-Bench: Can Language Models Improve Agent Harness?

- **arXiv**: 2608.09096
- **Link**: https://arxiv.org/abs/2608.09096

### 這篇在說什麼

Harness engineering 領域已經從「手動設計 harness」走到「觀察 harness 對 agent 表現的影響」，但這篇問了一個更根本的問題：LLM 本身能不能自己改進 harness？現有 benchmark 要麼只測靜態 task solving，要麼測的是 agent 執行任務的能力，而不是 agent 演化自己 harness 的能力。Evo-Bench 是第一個專門測 harness-evolving capability 的 benchmark——不是測你能不能寫 code，而是測你能不能長期迭代地改進一個控制 agent 行為的 executable harness。

### 主要貢獻

1. **Evo-Bench：第一個 harness-evolving capability benchmark**。橫跨 Search、Office、General 三個 domain，5 個 source benchmark（BrowseComp、HLE、GDPval、APEX-Agents、Claw-Eval），160 個 validation tasks + 448 個 evaluation tasks。

2. **Harness-guided construction framework**：先做 auxiliary-task evolution（讓模型先在輔助任務上演化 harness），然後用 sensitivity-aware 的方式選出真正對 harness 改進敏感的任務，再做 stratified splitting 確保 validation 和 evaluation 的分佈一致。這解決了三個挑戰：harness sensitivity（任務要對 harness 改進有反應）、cross-split generalization（防止 overfitting）、long-horizon evolution（要能持續多輪改進）。

3. **9 個 frontier 模型的系統性評估**：GPT-5.6 Sol 和 Claude Opus 4.8 達到 +16.6 和 +16.1 的絕對增益，接近 human-engineered baseline（47.5）。但行為有明顯的 domain dependency：Search 增益巨大，General 可以超越手寫 harness，Office（需要特定 workflow）則表現困難。

### 方法 / pipeline

Evo-Bench 的核心設計：

- **固定 policy model π**：被演化的是 harness H_t，不是 model 本身。這分離了 harness evolving 能力和 base model 能力。
- **Evolver E**：用一個獨立的固定 evolve harness 操作，看之前的 validation evidence，改 harness code。
- **演化過程**：每輪 evolver 檢查累積的 validation-side evidence（task-level outcomes、policy trajectories、diagnostic feedback），改 harness，然後在 validation suite 上正式評估。budget 限制（iterations、wall-clock time、steps）。
- **最終評估**：演化結束後，凍結最終 harness H_T，在 disjoint evaluation suite 上評估。
- **Harness-sensitive task selection**：先在 auxiliary tasks 上跑多種 harness，只保留那些對 harness 變化有反應的任務（harness sensitivity filter）。
- **Seed harness**：最小的 CodeAct loop，只有 shell-execution tool 和 final-answer tool。

這個設計巧妙地分離了「模型的 coding ability」和「模型能否作為 harness engineer」——同一個 policy model 用不同 harness 可以有完全不同的表現，而 evolver 的目標是找到更好的 harness。

### 實驗設計

- **3 domains × 5 benchmarks**：Search（BrowseComp + HLE）、Office（GDPval + APEX-Agents）、General（Claw-Eval）。
- **9 models**：包括 GPT-5.6 Sol、Claude Opus 4.8、DeepSeek-R1-0528 等。
- **主要數字**：Human baseline 47.5，seed harness 約 30-31。GPT-5.6 Sol 演化後達到 ~47，Claude Opus 4.8 接近。
- **Domain 差異**：Search 增益最大（web navigation 結構可學），Office 增益最小（specific processing workflow 難以從通用演化發現）。
- **Early saturation**：模型在前幾輪就找到好的結構，後面反而會引入有害修改。
- **Transferability**：在一個 policy model上演化的 harness，放到不同 policy model（Qwen、DeepSeek、GLM）上也有一致的增益——演化出的 harness 是 transferable reasoning structures。

目前從 HTML 全文確認到主要實驗數字和 domain 分析；per-model trajectory 的細節和 appendix 的 sensitivity analysis 尚未完全確認。

### かに讀後判斷

這篇是 harness engineering 領域的重要里程碑。之前我們看過 LoopsBench（把評估單位從 terminal task 轉向 dependency DAG + regression obligation）、Delivery Not Storage（把 memory 送達從 agent choice 轉向 harness property）、MemoHarness（harness 自己學習經驗），Evo-Bench 則是把整個問題翻轉：不是人設計 harness，而是測 LLM 能不能自己演化 harness。

幾個值得深讀的重點：
1. **Harness sensitivity filter 的設計**：怎麼確保 benchmark 測的是 harness improvement 而不是 model strength？這是所有 harness benchmark 的基礎問題。
2. **Early saturation 現象**：模型快速找到好結構然後退化，這暗示 harness evolution 可能需要 early stopping 或某種回退機制。
3. **Office domain 的困難**：需要特定 processing workflow 的任務很難從通用演化中發現，這呼應了 harness engineering 中 human domain knowledge 的不可替代性。

建議深讀，特別是 Section 3（benchmark construction）和 Section 5（temporal analysis + transferability）。

## 2. PMCoder: Coupling Planning with Episodic Memory in LLM Agents for Software Issue Resolution

- **arXiv**: 2608.06811
- **Link**: https://arxiv.org/abs/2608.06811

### 這篇在說什麼

這篇同時屬於 harness engineering 和 agent memory 兩個領域。核心觀察是：在軟體 issue resolution 這種長 horizon 任務中，planning 和 memory 不能分開設計——plan 決定什麼記憶相關，而累積的記憶證據決定何時該改 plan。現有 agent 要麼加強 planning、要麼加強 memory，但很少把兩者耦合起來。PMCoder 提出了 bidirectional plan–memory coupling：plan phase conditions memory retrieval，memory-derived trajectory statistics inform stuck detection and replanning。

### 主要貢獻

1. **Bidirectional plan–memory coupling**：hierarchical phase planner（exploration → hypothesis → implementation → verification）和 episodic memory 之間的雙向交互。Plan phase 決定記憶檢索的 filtering，memory 統計（edit failure rate、stuck signal）觸發 replanning。

2. **Execution-grounded verification**：verification phase transition 不靠 agent 自己說「我完成了」，而是靠 issue reproduction 的執行結果。這解決了 self-reported verification 的 fabricate 問題。

3. **SWE-bench Verified 上的實證**：比 harness-matched baseline 多解 25 cases（+5.0pp），在 Claude Haiku 4.5、DeepSeek-V4-Flash、OpenHands port 上至少多解 14 cases（+2.8pp）。Ablation 確認 plan–memory interaction 貢獻 +10.3 instances（+2.1pp, F(1,8)=10.92, p=0.011）。

### 方法 / pipeline

PMCoder 的架構：
- **Hierarchical phase planner**：追蹤兩層 state——current repair phase 和 active sub-task。
- **Episodic memory**：存 observations、attempts、outcomes、file metadata，用 MMR beam search 檢索。
- **Bidirectional coupling**：plan phase → memory retrieval filtering；memory-derived statistics → stuck detection + replanning。
- **Reproduction gate**：當 issue reproduction verdict 可用時，用執行結果取代 self-report 作為 verification signal。
- **Context injection**：plan 和 memory context 都通過 tool outputs 注入，而非獨立的 memory 查詢。

### 實驗設計

- **主實驗**：SWE-bench Verified，Qwen3-Coder-30B + PMCoder vs harness-matched baseline（無 planner、無 episodic memory、無 execution-grounding gates）。
- **重複評估**：3 runs，因為 FP8 temperature=0 不完全可重現。
- **結果**：167.3/500 (33.5%) vs 142.3/500 (28.5%)，+5.0pp，95% CI [+14.3, +35.7]（p<0.001）。
- **Ablation**：2×2 component ablation（planning on/off × memory on/off），interaction term +10.3 instances（+2.1pp, p=0.011）。
- **Behavioral analysis**：PMCoder 減少了 repeated failed actions、empty-patch exits、context-window exhaustion。
- **Transfer**：在 TerminalWorld official sample 上也有正向結果。

### かに讀後判斷

PMCoder 的核心洞察——planning 和 memory 必須雙向耦合，不能分開——直接回應了 Delivery, Not Storage（2607.20972）提出的「harness 應該自動送達記憶」的觀點，但走了一條不同的路：不是 harness 自動 inject，而是 plan 和 memory 互相 condition。兩篇加在一起看，agent memory 的問題既需要正確的送達機制（harness property），也需要正確的時機判斷（plan-conditioned retrieval）。

這篇對做 coding agent harness 的人有直接實用價值。建議深讀 Section III（PMCoder architecture）和 Section V-D（ablation + interaction term）。
