# Harness Engineering — 2026-08-15

## 1. Harness-IF: Evaluating Instruction Following Across Instruction Surfaces in Coding Agents

- **arXiv / Venue / 類型**: arXiv:2608.11727v1 / preprint / coding-agent instruction-following benchmark
- **Link**: https://arxiv.org/abs/2608.11727v1
- **今日推薦點開**: 是

![](../assets/2026-08-15/harness-if-instruction-surfaces.png)

### 這篇在說什麼

這篇是今天 harness engineering 裡最值得點開的一篇，因為它問的不是「coding agent 最後有沒有把 task 做完」，而是「agent 在長流程裡到底有沒有遵守某一條 operational rule」。作者指出，現有 instruction-following benchmark 通常把規則放在 user turn 裡，coding-agent benchmark 又多半看 final task success；但真實 agent 會同時讀 system prompt、tool description、skill description、project file、user instruction，規則可能分散在不同 instruction surfaces。更麻煩的是，agent 有時看起來遵守規則，只是因為那條規則本來就符合它的 default behavior，不代表它真的被指令約束。

Harness-IF 的核心就是把「指令在哪個 surface 被交付」和「規則是否真的被遵守」變成可測量對象。這對我們平常做 agent harness 很關鍵：如果只看最後 answer 或 tests pass，很容易漏掉 agent 其實忽略了 workflow、tool-use、output-control、project policy 這些中間約束。

### 主要貢獻

第一，作者建立了一個 surface-aware 的 coding-agent instruction benchmark。它從 642-rule library 裡組出 60 個 realistic multi-turn coding items，規則可以被放到 system prompt、tool description、skill description、project file、user instruction 等 surface，並且在 execution evidence 裡逐條打 verdict。

第二，這篇提出 Against-Prior Accuracy（AP-Acc）。一般 accuracy 會把「agent 本來就會做」和「agent 被規則推著做」混在一起；AP-Acc 只看那些被標成 against-prior 的規則，也就是目標規則和未提示時模型預設行為相反的情況。作者透過 zero-injection ablation：在同一 task 中移除 target rule，讓九個 probe builds 跑，來標記 align-prior / against-prior / neutral。

第三，它把 instruction hierarchy 和 instruction surface 分開。hierarchy 是衝突時誰優先；surface 是同一條規則放在哪裡被讀到。Harness-IF 的 controlled-relocation design 讓規則語意固定、移動 delivery surface，這對分析 agent stack 很有價值。

### 方法 / pipeline

Benchmark pipeline 從 repository policies、CLAUDE.md / SKILL.md 類 project files、公用文件與人工 seed rules 收集候選 constraints，再用人工審核確保規則 atomic、verifiable、non-trivial、agent-fit。每個 candidate item 包含 coding fixture、tests、多輪任務，以及 25–35 條可檢查規則；實際評分不是只看任務成功，而是產生 traces、artifact diffs、ordered states，再對每條 rule 給 pass / fail / inapplicable。

規則本身還有 taxonomy：例如 rule family、observability、verifiability、surface fit。這使它可以區分 regex / AST / command-output 等 deterministic checks，以及需要 rubric judge 的 semantic constraints。主實驗的 verdict 有一部分由 deterministic checks 覆蓋，其餘由 GPT-5.2 judge 多票裁決；作者也提供可從 release artifacts 重算數字的腳本，避免 benchmark 報表變成不可追溯的 leaderboard。

### 實驗設計

主 coding panel 是 12 個 frontier model builds × 60 items × 3 rounds，共 2160 個 agent-item-round runs，產生 40104 rule-level verdict rows；二元分析裡有 37616 個 eligible verdict，其中 19449 個是 against-prior verdicts。結果顯示 Acc 範圍約 72.1–85.9%，AP-Acc 則約 66.1–78.6%。每個模型在 against-prior rules 上都更差，落差 3.6 到 7.4 percentage points，平均約 5.81。這代表 pooled instruction-following accuracy 會高估 agent 真正被規則約束的能力。

它還做了一個 conflict pilot，檢查不同 surface 在規則衝突時的 precedence。結果不是簡單「越深的 prompt 越優先」；system prompt、project files、user instructions 在 pooled precedence 中排在 tool / skill descriptions 前面，但這不能被理解成一個普遍規則，只能說在這個 controlled pilot 裡，surface precedence 比直覺更複雜。

### かに讀後判斷

這篇很適合 Morris 點開，尤其如果最近在想 agent harness、skill/system prompt、project policy、tool description 如何共同約束 agent。它的價值不是提出一個新 agent，而是把我們平常感覺到的問題量化：final success 不等於 rule compliance；rule compliance 也不等於 against-prior compliance。

深讀優先看 Figure 2 的 construction / evaluation pipeline、Table 2 的 Acc vs AP-Acc、Appendix 裡 constraint taxonomy 和 prior labeling 方法。若要借用到自己的 workflow，我會先抄它的三個設計：一是把規則拆成 atomic constraints；二是保存 execution evidence 而不是只保存 final answer；三是用 rule-withheld probe 估計 default prior。這對 OpenClaw / Codex 類長流程 agent 的 harness regression test 很有啟發。
