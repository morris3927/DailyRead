# Harness Engineering — 2026-08-20

今天 harness engineering 領域有兩篇 NOT_SEEN 的論文。AgentCompass 提出了統一的 agent 評估基礎設施，把 Benchmark、Harness、Environment 三層解耦；Architectural Design Decisions in AI Agent Harnesses 則做了 70 個開源專案的協議引導式原始碼研究，系統性地識別出五個反覆出現的架構決策維度和五個典型模式。另外 A Systematic Evaluation of Agents for Long-Horizon AI Research and Development 雖然是 harness 相關的評估研究，但從摘要層級看主要是評估結果而非架構貢獻，且只讀到 abstract，不做 domain note 收錄。

## 1. AgentCompass: A Unified Evaluation Infrastructure for Agent Capabilities

- **arXiv / Venue**: arXiv:2607.13705 (cs.CL, cs.AI)
- **Link**: https://arxiv.org/abs/2607.13705
- **GitHub**: https://github.com/open-compass/AgentCompass

### 這篇在說什麼

隨著 LLM 從指令遵循模型演進為自主 agent，評估方法必須同步發展。但目前的 agent 評估生態高度碎片化：每個 benchmark 都有自己的執行環境、資料格式和評分協議，研究者必須反覆配置異質環境，這不僅浪費工程資源，更損害了可重複性 — 因為 baseline 實作不一致。現有的通用基礎設施（OpenCompass、VLMEvalKit）缺乏對互動式 agent workflow 的原生支援，而 Harbor 等專注 coding 的框架範圍太窄。

AgentCompass 的核心設計是把評估拆成三個獨立組件：Benchmark、Harness、Environment，讓它們可以任意組合（benchmark × harness × environment），而不需要重寫執行邏輯。

### 主要貢獻

1. **三層解耦架構**：把評估從 monolithic script 拆成 Benchmark（任務和評分）、Harness（agent 互動邏輯）、Environment（執行上下文和隔離），讓研究人員可以在同一個 benchmark 上換 harness、在同一個 harness 上換 benchmark、或在同一個環境上換 benchmark。

2. **協議驅動的組件互操作**：透過兩層嚴格的協議抽象 — 模型作為聲明式 API 規格（而非緊耦合的客戶端），benchmark 和 harness 之間透過標準化的 PreparedTask → RunResult 資料合約交換 — 確保新組件只需本地註冊，不需要修改核心 runtime 或其他模組。

3. **容錯異步 runtime**：基於 asyncio 的異步調度器，支援並行處理長時間運行的 agent 軌跡、部分結果增量儲存、中斷後無縫恢復（跳過已完成任務、只重試失敗任務）。

4. **軌跡分析和行為診斷**：每個任務記錄完整的互動軌跡（推理、工具呼叫、環境回饋、token 消耗、推理延遲、停止原因），並提供可插拔的分析器層自動偵測輸出截斷、延遲尖峰、重複生成迴圈等問題。

5. **原生支援 20+ benchmarks 和多種 harness**：覆蓋 tool use、web & research、scientific reasoning、agentic coding、productivity 五個能力維度，支援從輕量 chat wrapper 到複雜自主框架（OpenHands、OpenClaw、Claude Code）的各種 harness。

### 方法 / pipeline

**Benchmark 組件**
- 載入原始資料為統一的 TaskSpec
- 準備任務材料（prompts、tools、media、expected outputs）
- 評分支援 deterministic matching、execution-based verification、LLM-as-judge
- Scorer 執行模式：none（記憶體內驗證）、reuse（復用 agent workspace）、fresh（乾淨隔離環境）

**Harness 組件**
- 將 LLM 實例化為互動 agent
- 管理 prompt 格式化、互動狀態、多輪工具呼叫、provider API 差異
- 兩種模式：in-process（AgentCompass 原生管理互動迴圈）和 in-environment（外部 agent 框架作為子進程在沙箱中執行）

**Environment 組件**
- 提供隔離的執行上下文
- 統一 session 介面：執行命令、傳輸檔案、操作文字、提供網路服務
- 後端抽象：同一配置可在 local host process、local Docker、distributed cluster 上執行

**GDPVal-AC**
- 一個客製化的 AgentCompass 變體，用 agentic judger（透過 OpenClaw）對 Claude-Opus-4.8 baseline 做 pair-wise 評估

### 實驗設計

已從 HTML 全文確認：

- **評估模型**：Qwen3.5-397B-A17B、DeepSeek-V4-pro(FP4)、Kimi-K2.6、GLM-5.2(FP8)、GPT-5.5、Gemini-3.1-Pro-Preview、Claude-Opus-4.8
- **8 個 benchmark**：τ³-bench、DeepSearchQA、FrontierScience(Research)、SWE-bench-Pro、SWE-bench-Multilingual、PinchBench、SkillsBench、SciCode
- **多種 harness**：τ³-bench 官方 workflow、Naive Search Agent（AgentCompass 內建搜尋 harness）、Mini-SWE-agent、OpenHands、OpenClaw
- **所有結果取 3 次 run 平均**以減少測量方差
- **核心發現**：
  - 同一模型在不同 harness 下表現差異顯著（例如 OpenClaw vs. OpenHands 在 SkillsBench 上的差異）
  - Harness 選擇對 agent 性能的影響可以比模型選擇更大
  - 不同能力維度的相對排名不一致，沒有單一模型在所有維度上都領先

### かに讀後判斷

AgentCompass 填補了 agent 評估基礎設施的一個重要缺口。現有框架（OpenCompass、VLMEvalKit、Harbor）要麼不支援互動式 agent workflow，要麼範圍太窄。AgentCompass 的三層解耦設計（Benchmark × Harness × Environment）讓研究者可以：
1. 在同一個 benchmark 上比較不同 harness
2. 在同一個 harness 上比較不同模型
3. 在同一個環境上比較不同 benchmark

這和 Architectural Design Decisions（今天的另一篇）的發現高度相關 — 那篇發現 harness 的架構選擇對 agent 行為有系統性影響，而 AgentCompass 提供了量化這種影響的工具。

和之前讀過的 Self-Harness（6/9）和 Meta-Harness（3/28）比較：Self-Harness 和 Meta-Harness 關注的是 harness 本身的自我改進和端到端優化，AgentCompass 關注的是 harness 的標準化評估。三者形成一個完整的光譜：如何設計 harness、如何改進 harness、如何公平比較 harness。

值得深讀：Section 3.2 的協議抽象細節、Table 3 的跨模型跨 harness 結果、Appendix 的 benchmark 和 harness 清單。

## 2. Architectural Design Decisions in AI Agent Harnesses

- **arXiv / Venue**: arXiv:2604.18071 (cs.SE, cs.AI)
- **Link**: https://arxiv.org/abs/2604.18071

### 這篇在說什麼

AI agent 系統越來越依賴可重複使用的非 LLM 工程基礎設施 — 那些負責工具調解、上下文處理、委派、安全控制和編排的軟體層。但這些基礎設施的架構設計決策一直缺乏系統性的研究。這篇論文對 70 個公開的 agent-system 專案做了協議引導式的原始碼研究，回答三個問題：哪些設計決策維度跨專案反覆出現？哪些決策之間有共現關係？哪些典型架構模式浮現？

### 主要貢獻

1. **五個反覆出現的設計維度**：透過系統性的原始碼分析，識別出五個跨專案反覆出現的架構決策維度：subagent architecture、context management、tool systems、safety mechanisms、orchestration。

2. **共現和非共現分析**：發現深層協調（subagent hierarchy）配對更明確的上下文服務；更強的執行環境配對更結構化的治理；正式化的工具註冊邊界配對更廣的生態系野心。同時，幾個常見假設（如「程式語言決定架構」、「能力增長自然帶來治理成熟度」）在跨專案比較中不成立。

3. **五個典型架構模式**：
   - Lightweight tools：單一用途、最小架構、直接工具呼叫
   - Balanced CLI frameworks：中等複雜度、CLI 為主、本地執行
   - Multi-agent orchestrators：子 agent 層級、訊息傳遞、上下文路由
   - Enterprise systems：嚴格治理、審計軌跡、沙箱執行
   - Scenario-verticalized projects：垂直場景特化、最小抽象

4. **可稽核的研究包裹**：提供了文件化的 corpus 邊界、搜索和篩選協議、操作化 codebook，讓後續研究可以稽核、修正或擴展。

### 方法 / pipeline

**研究設計**
- 協議引導式原始碼分析：每個專案都根據預先定義的協議進行系統性的原始碼閱讀
- 70 個公開專案的 corpus（含 OpenHands、OpenClaw、Claude Code CLI、docker-agent 等）
- 三個研究問題導向：RQ1（設計空間）、RQ2（共現關係）、RQ3（模式和定位）

**五個設計維度的選項光譜**
- **Subagent architecture**：none / single / flat / hierarchical / dynamic
- **Context management**：session-only / file-persistent / hybrid / structured store
- **Tool systems**：hardcoded / registry / MCP / plugin
- **Safety mechanisms**：none / approval / sandbox / audit / full governance
- **Orchestration**：single-turn / multi-turn / reactive / planned / autonomous

**共現分析發現**
- 深層子 agent 協調 ↔ 更明確的上下文服務
- 更強的執行環境 ↔ 更結構化的治理
- 正式化的工具註冊邊界 ↔ 更廣的生態系野心
- 不成立的假設：程式語言不決定架構、能力增長不自然帶來治理成熟度

### 實驗設計

這是一篇實證研究論文而非實驗論文，沒有傳統意義上的實驗。研究方法包括：

- **Corpus**：70 個公開 agent-system 專案，透過系統性搜索和篩選獲得
- **編碼協議**：每個專案按照五個維度的選項光譜進行編碼，每個決策都有明確的原始碼證據
- **共現分析**：跨專案的決策組合統計分析
- **模式合成**：從共現模式中歸納出五個典型架構模式

### かに讀後判斷

這篇是 harness engineering 領域第一個系統性的架構研究，填補了一個重要的空白：我們對 agent 系統的演算法和行為了解很多，但對「包圍 LLM 的非 LLM 工程層怎麼組織」了解很少。

和 AgentCompass（今天另一篇）的關係非常直接：
- 這篇識別出 harness 的五個架構決策維度，AgentCompass 則是沿著其中三個維度（context management → Benchmark、orchestration → Harness、safety mechanisms → Environment）做出了具體的設計選擇。
- 這篇的共現分析發現「正式化的工具註冊邊界配對更廣的生態系野心」，AgentCompass 的 registry-based 架構正好驗證了這個發現。

和之前讀過的 Self-Harness（6/9, 2606.09498）和 Meta-Harness（3/28, 2603.28052）比較：Self-Harness 和 Meta-Harness 分別關注 harness 的自我改進和端到端優化，這篇則提供了 harness 架構選擇的實證基礎 — 知道哪些設計維度和共現模式存在，才能知道該改進什麼、優化什麼。

值得注意的是，OpenClaw 被列為 corpus 中的專案之一，而且被歸類為「multi-agent orchestrator」和「TypeScript-based execution substrate」— 這對 Morris 的日常使用有直接的參考價值。
