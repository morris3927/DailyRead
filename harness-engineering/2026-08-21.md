# Harness Engineering — 2026-08-21

今天覆蓋兩篇 NOT_SEEN 論文：Living-Harness 提出 rollout–evaluate–update 自演化 harness 框架；MerchantBench 引入 365 天電商模擬基準測試 agent 長期一致性。Living-Harness 是今日推薦點開。

## 1. Living-Harness Is an Interactive-Agent Evolver

- **arXiv / Venue**: arXiv:2607.26598 (cs.CL, cs.AI)
- **Link**: https://arxiv.org/abs/2607.26598

### 這篇在說什麼

LLM agent 可能在一次 episode 中從錯誤恢復，或在重試後修正，但同一個執行失敗會在後續任務中反覆出現 — 因為 episode 後的反饋很少修訂引導未來互動的持久 harness。靜態 harness 通過固定工具、上下文、記憶和工作流結構提升可靠性，但部署後不會改變。Living-Harness 的核心問題是：如何把 episode 後的失敗證據轉化為持久的程序性修復？

作者提出的答案是：一個自演化的 harness，把每個完成軌跡和其評估信號轉為有界更新（bounded updates）的後驗證據。關鍵設計約束是：tools 和 base context 保持凍結，只有 episodic memory 和 state graph 在演化 — 這避免了累積損壞。

### 主要貢獻

1. **持久程序性修復的概念澄清**：作者區分了 task-local correction（一次重試中的修正）和 cross-episode adaptation（跨 episode 的持久修復），指出後者才是 harness evolution 的核心問題。一個 textual lesson 如「transfer the user to a human」本身不指定觸發條件、所需工具動作和工作流轉換 — 缺少的是從失敗到可重用程序修復的轉換。

2. **Living-Harness 框架**：rollout–evaluate–update 循環，由 domain-level Evolution-SOP 引導。每次 episode 完成後，從軌跡和評估信號提取 episode abstraction 和 structured update evidence，寫入兩種互補的程序性知識：
   - **Episodic memory**：記錄觸發條件、失敗模式和恢復動作。
   - **State graph**：記錄狀態節點、修復邊和轉換規則。

3. **Program-state POMDP 形式化**：把 agent 的跨 episode 適應形式化為 program-state POMDP — 不僅環境狀態不確定，harness 本身的程序性知識也部分可觀測，需要通過互動和評估逐步更新。

4. **Recovery accumulation 和跨模型 reuse**：在 τ²-Bench 和 MultiWOZ-2.4 衍生的八個環境上，Living-Harness 比最強互動基線提升 10.07 和 9.91 百分點。更值得注意的是，演化的 harness state 可以 retrieval-only 地跨模型 backbone 複用。

### 方法 / pipeline

**Episode n 的流程**：

1. **Rollout**：Agent 在當前 harness state S^(n) 下與環境互動，產生軌跡 τ_n。
2. **Evaluate**：Evaluator 對軌跡打分，產生評估信號 y_n。
3. **Update**：Evolution-SOP ψ_d 把 (τ_n, y_n) 轉換為後驗證據：
   - 提取 episode abstraction（失敗模式摘要）
   - 生成 structured update evidence（觸發條件、缺失動作、修復策略）
   - 更新 episodic memory R 和 state graph G
   - 產生 S^(n+1)，寫回持久狀態

4. **下一 episode**：新 harness state S^(n+1) 被檢索，引導未來互動。

**關鍵設計約束**：
- Tools 和 base context 凍結 — 只修改 episodic memory 和 state graph。
- Evolution-SOP 是 domain-level 的 — 它指定如何解讀失敗、哪些修復可以提交。
- 狀態更新是有界的（bounded）— 不是無限制的任意修改。

### 實驗設計

已從 HTML 全文確認方法、框架設計和實驗細節：

- **八個互動環境**：從 τ²-Bench 和 MultiWOZ-2.4 衍生。
- **評估指標**：Pass@1（主要）、dialogue success rate、task completion。
- **基線**：靜態 harness（ReAct、Reflexion）、interactive baseline（帶 episode-level feedback 但不持久化修復）。
- **核心結果**：
  - τ²-Bench：Living-Harness 比 interactive baseline 提升 10.07 個百分點（Pass@1）。
  - MultiWOZ-2.4：提升 9.91 個百分點。
  - Recovery accumulation：隨 evolution cycles 增加，累積修復逐漸改善。
  - 跨模型 reuse：演化後的 harness state 可以 retrieval-only 方式複用到不同模型 backbone。

### かに讀後判斷

這篇是 harness engineering 領域一個重要的概念和方法貢獻。和之前 DailyRead 覆蓋的 AHE（5/10，可觀察性驅動演化）、Evo-Bench（8/13，測 harness evolution 能力）、Self-Harness（6 月，自改 harness）相比，Living-Harness 的獨特之處是：

1. 明確區分 task-local correction 和 cross-episode procedural repair。
2. 把 harness state 分成凍結層（tools, base context）和演化層（episodic memory, state graph），避免累積損壞。
3. Program-state POMDP 形式化為理解 harness evolution 提供了理論基礎。

值得深讀的部分：Section 3 的 Evolution-SOP 設計（具體如何從失敗軌跡提取結構化修復證據）、跨模型 reuse 的實驗細節、以及和 Reflexion 的 ablation 比較。

## 2. MerchantBench: Benchmarking LLM Agents for Long-Term Coherence in E-Commerce Operations

- **arXiv / Venue**: arXiv:2607.28956 (cs.CL, cs.AI)
- **Link**: https://arxiv.org/abs/2607.28956

### 這篇在說什麼

現有 agent 基準大多測 bounded tasks（有明確完成標準的短期任務），但真實部署需要的是長期一致性（Long-Term Coherence）：跨長時間範圍保持有目的的行為，同時根據累積證據調整決策。MerchantBench 用賣方電商場景來測試這個能力 — 代理需要管理進貨、定價、現金流、處理延遲回饋，365 天模擬中每個決策都影響後續選項。

### 主要貢獻

1. **Long-Term Coherence 的形式化定義**：把長期一致性定義為 POMDP 下的持續決策問題，而非 bounded task completion。

2. **365 天訂單級模擬環境**：基於 1688 平台 98,843 個真實商品記錄，包含需求軌跡、供應商事件、訂單生命週期。

3. **異質延遲回饋設計**：上游供應商事件（價格變動、斷貨、延遲發貨）可立即觀察，但下游訂單結果（退款、差評、罰款）延遲到貨 — agent 必須把後來的結果和先前的決策關聯起來。

4. **四個相互依賴的決策組件**：Product Sourcing、Listing and Pricing Control、Cash-Flow Management、Mixed-Latency Feedback Adaptation。

### 方法 / pipeline

- **環境建模**：POMDP，8,760 個 hourly steps（365 天），agent 每 12 步有一個決策窗口。
- **上游模擬**：供應商價格、庫存、可用性、發貨時間隨時間變化，觸發事件（價格變動、商品下架、發貨延遲）從真實平台信號校準。
- **下游模擬**：每個商品的每小時需求強度從真實 365 天需求軌跡推導，轉為個別訂單並走完履約和售後流程。
- **26 個工具**：供應商搜索、商品上架、價格調整、庫存管理、訂單追蹤等。

### 實驗設計

已從 HTML 全文確認方法設計和初步結果：

- **8 個 LLM × 2 個 agent framework = 48 runs**，每個 run 模擬 365 天。
- **真實資料**：1688 平台 98,843 商品、36,576 供應商，2025-06-01 到 2026-05-31 的 365 天需求。
- **核心發現**：最好的 LLM 配置只達到人類參與者平均最終淨資產的 27.3%。
- **評估**：最終淨資產（cash balance + security deposit + funds in transit + receivables）、決策軌跡分析、long-term coherence 指標。

### かに讀後判斷

MerchantBench 在 harness engineering 的定位比較特殊 — 它不是測 harness 本身，而是測 agent 在長期、多延遲回饋環境中的行為一致性。和 Vending-Bench、RetailBench 相比，MerchantBench 的獨特之處是：

1. 訂單級模擬（而非 aggregate demand）— agent 需要追蹤個別訂單生命週期。
2. 異質延遲回饋 — 上游即時、下游延遲，測試 agent 的時序推理能力。
3. 98,843 個真實商品記錄帶來的非平穩需求 — agent 需要持續發現新機會。

這篇和 harness engineering 的關聯是：如果 agent 的 harness 不支援長期狀態追蹤和決策修訂，在 MerchantBench 這種環境中就會系統性地失敗。值得深讀的部分：Section 4 的環境設計（POMDP 形式化）、Section 5 的實驗結果（特別是 LLM vs 人類的差距分析）、以及 Appendix 的需求校準細節。
